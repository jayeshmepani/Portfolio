Below is a current, standards-based CSS performance guide focused especially on **`content-visibility`**, **CSS containment**, **`contain-intrinsic-size`**, **`will-change`**, and the surrounding CSS mechanisms that actually affect rendering cost.

I checked current MDN guidance, the CSSWG containment and Will Change specifications, and current web.dev/Chrome performance guidance. One important theme emerges consistently: **the best CSS optimization is usually not “make the browser work faster”; it is “make the browser do less work.”** ([CSS Drafts][1])

---

# 1. First understand what CSS performance actually means

A browser does not simply "apply CSS."

A simplified rendering pipeline looks like:

```text
HTML / DOM
   ↓
CSS / CSSOM
   ↓
Style calculation
   ↓
Layout
   ↓
Paint
   ↓
Composite
   ↓
Screen
```

Not every visual change requires every stage.

For example:

```text
width: 500px
```

can require:

```text
Style → Layout → Paint → Composite
```

Whereas:

```css
transform: translateX(100px);
```

may be handled much more cheaply:

```text
Style → Composite
```

when the element is composited appropriately. Likewise, `opacity` can often follow a compositor path. ([web.dev][2])

So there are **four fundamentally different optimization strategies**:

| Strategy                            | What you are trying to do                                   |
| ----------------------------------- | ----------------------------------------------------------- |
| **Reduce work**                     | Render fewer elements / less content                        |
| **Restrict work**                   | Prevent changes from propagating through the whole document |
| **Avoid expensive pipeline stages** | Prefer transform/opacity over layout-triggering animation   |
| **Prepare for expensive work**      | `will-change`, used carefully                               |

This distinction is extremely important.

`content-visibility` primarily belongs to **"do less work."**

`contain` primarily belongs to **"restrict work."**

`transform`/`opacity` primarily belong to **"avoid layout/paint during animation."**

`will-change` belongs to **"prepare the browser for an imminent change."**

They are not interchangeable.

For modern web development, the properties/mechanisms worth knowing deeply are:

```text

contain
contain-intrinsic-size
contain-intrinsic-width
contain-intrinsic-height
contain-intrinsic-inline-size
contain-intrinsic-block-size

will-change

transform
translate
scale
rotate
opacity

visibility
display
overflow / overflow: clip
isolation

filter
backdrop-filter
mix-blend-mode

aspect-ratio

font-display
size-adjust
ascent-override
descent-override
line-gap-override

container-type
container-name
container
```

Some of those are **direct rendering-performance tools**; others primarily prevent layout shifts, reduce CSS loading cost, isolate rendering, or avoid expensive visual effects.

There is also a very important class of things that are **not optimization properties at all**, despite being frequently advertised as such.

For example:

```css
transform: translateZ(0);
```

should not be treated as a universal "GPU acceleration switch."

Modern browsers already perform extensive compositing heuristics, and `will-change` itself does **not** guarantee a GPU layer. The CSSWG explicitly says browsers can use `will-change` differently and may even avoid creating layers when too many elements request them. ([CSS Drafts][3])

# 3. `content-visibility`: the big one

## What it actually does

```css
content-visibility: auto;
```

tells the browser:

> "This element's contents are allowed to be skipped when they're not relevant to the user."

This is much more powerful than ordinary visual hiding.

It can allow the browser to omit substantial rendering work—including descendant layout and painting—until that content is needed. ([MDN Web Docs][4])

For a long page:

```html
<section class="article-section">...</section>
<section class="article-section">...</section>
<section class="article-section">...</section>
<section class="article-section">...</section>
<section class="article-section">...</section>
```

you can use:

```css
.article-section {
    content-visibility: auto;
}
```

The off-screen sections can effectively behave like "boxes whose internals do not need to be rendered yet."

This is why it can dramatically reduce initial rendering work on pages with large amounts of below-the-fold content. Google's published example saw rendering time drop from roughly 232 ms to 30 ms—a 7× improvement—but that is an example workload, **not a universal benchmark**. ([web.dev][5])

---

# 4. `content-visibility` has only three values

```css
content-visibility: visible;
content-visibility: hidden;
content-visibility: auto;
```

## `visible`

```css
content-visibility: visible;
```

Normal rendering.

Essentially:

```text
No content skipping
No special containment
Normal rendering
```

It is the default. ([MDN Web Docs][4])

---

# 5. `content-visibility: hidden`

This is substantially more interesting.

```css
.panel {
    content-visibility: hidden;
}
```

The contents are skipped regardless of whether the element is on screen.

That makes it useful for things such as:

* inactive SPA views
* hidden application panels
* expensive tab panels
* virtualized UI
* advanced virtual scrolling
* temporarily inactive rendering-heavy components

The important distinction is that `content-visibility: hidden` is intended to preserve rendering state so that revealing the content can be cheaper than constructing and rendering it from scratch. ([web.dev][5])

### But it is NOT equivalent to `visibility: hidden`

This is a common mistake.

`content-visibility: hidden` causes strong containment and skipped contents.

The skipped subtree is unavailable to user-agent features such as:

* Find in Page
* tab navigation
* selection
* focus

whereas `content-visibility: auto` behaves differently. ([MDN Web Docs][4])

---

# 6. `content-visibility: auto`

This is generally the most interesting performance value.

```css
.article-section {
    content-visibility: auto;
}
```

The browser decides whether the content is currently relevant.

When it is sufficiently far away:

```text
Skip subtree rendering
      ↓
avoid expensive descendant work
```

When it approaches the viewport:

```text
Render subtree
      ↓
content becomes visible normally
```

This is adaptive rather than a developer-controlled "show/hide" switch.

The specification defines "close to the viewport" using the paint containment box intersecting the viewport **or a user-agent-defined margin around it**; the spec notes that a 50% margin is a reasonable suggested default, but this is not a promise that every browser uses exactly 50%. ([CSS Drafts][1])

So do **not** write application logic assuming:

```text
viewport edge = exact rendering activation point
```

The browser controls that decision.

---

# 7. `content-visibility: auto` automatically implies containment

This is one of the most important facts.

For `auto`, the browser enables:

```text
layout containment
style containment
paint containment
```

and when the content is not relevant to the user, size containment is also involved while the subtree is skipped. ([CSS Drafts][1])

Conceptually:

```css
content-visibility: auto;
```

is therefore much closer to:

```css
/* conceptual, NOT a literal replacement */
contain: layout paint style;
/* + conditional skipping / size containment */
```

than it is to:

```css
visibility: hidden;
```

That is why it can be powerful.

---

# 8. The ideal `content-visibility` use case

Think:

> **Many independent chunks of content, most of which are outside the viewport.**

Excellent examples:

```text
Long documentation page
Blog listing
News feed
Search results
Product listing
Large portfolio page
Long article
Large dashboard
Long comments/reviews
Infinite-scroll-like feed
Many independent cards
```

Example:

```css
.card {
    content-visibility: auto;
    contain-intrinsic-block-size: auto 30rem;
}
```

This is far more meaningful than putting it on:

```css
body {
    content-visibility: auto;
}
```

because `body` is almost always relevant to the viewport.

The CSSWG explicitly notes that putting `content-visibility: auto` on an entire timeline, for example, may accomplish little because the container itself remains on-screen and therefore never skips its contents. ([CSS Drafts][1])

---

# 9. Granularity matters enormously

Bad:

```css
main {
    content-visibility: auto;
}
```

if `main` contains the whole page.

Better:

```css
article {
    content-visibility: auto;
}
```

Better still for a very large article:

```css
.article-section {
    content-visibility: auto;
}
```

Why?

Because `auto` only helps where the **entire contained subtree becomes irrelevant**.

If your giant container is always partially visible:

```text
┌──────────────────────────────┐
│ visible portion              │
│                              │
│ visible                      │
│ ──────────────────────────── │ ← viewport
│ offscreen content            │
│ offscreen content            │
└──────────────────────────────┘
```

the whole container may remain relevant.

Chunking:

```text
Section 1 → independent
Section 2 → independent
Section 3 → independent
Section 4 → independent
...
```

lets the browser skip individual sections.

The specification specifically recommends using `content-visibility: auto` at a reasonably fine granularity. ([CSS Drafts][1])

---

# 10. The catch: size estimation

Here is where many implementations go wrong.

When an off-screen `content-visibility: auto` element is skipping its contents, the browser needs to know:

> "How tall is this thing supposed to be?"

But if its children aren't laid out, their natural height isn't available.

Therefore the browser needs a substitute intrinsic size.

Enter:

# `contain-intrinsic-size`

---

# 11. `contain-intrinsic-size`

Example:

```css
.article-section {
    content-visibility: auto;
    contain-intrinsic-size: auto 800px;
}
```

Think of it as:

> "When you are skipping this element's contents, pretend the element's content has approximately this intrinsic size."

This prevents the page from behaving as if every skipped section has zero height.

Without a suitable intrinsic size, you can get:

```text
initial page
    ↓
sections appear tiny / collapsed
    ↓
user scrolls
    ↓
section becomes rendered
    ↓
real height appears
    ↓
scrollbar/page geometry changes
```

That can create visible jumping and reflow. `contain-intrinsic-size` exists specifically to provide a placeholder intrinsic size under size containment. ([MDN Web Docs][6])

---

# 12. Prefer the logical intrinsic properties when appropriate

You now have:

```css
contain-intrinsic-width
contain-intrinsic-height

contain-intrinsic-inline-size
contain-intrinsic-block-size
```

The logical versions are often particularly useful.

For a conventional horizontal writing mode:

```text
inline-size ≈ width
block-size  ≈ height
```

So for a vertically flowing article section, instead of unnecessarily estimating both dimensions:

```css
contain-intrinsic-size: 800px;
```

consider:

```css
contain-intrinsic-block-size: 800px;
```

Or, where remembering the rendered size is useful:

```css
contain-intrinsic-block-size: auto 800px;
```

The logical properties are Baseline widely available in current browsers. ([MDN Web Docs][7])

---

# 13. Why `auto <length>` is particularly useful

This is a very good modern pattern:

```css
.article-section {
    content-visibility: auto;
    contain-intrinsic-block-size: auto 800px;
}
```

The logic is:

```text
First rendering:
    use approximately 800px

After actual rendering:
    remember actual rendered size

Later while skipped:
    use remembered size
```

The `auto <length>` form allows the browser to remember the normally rendered size and use it when the contents are subsequently skipped. ([MDN Web Docs][6])

This is particularly useful for feeds and progressively explored content.

---

# 14. Picking a good intrinsic size

Suppose your cards generally look like:

```text
300–450px
```

Do not use:

```css
contain-intrinsic-block-size: 5000px;
```

Just because "larger avoids collapse."

That creates the opposite problem:

```text
estimated page geometry
        ↓
huge fake blocks
        ↓
incorrect scrollbar size
        ↓
large correction when rendered
```

Use an estimate reasonably close to the actual typical block size.

For highly variable components:

```css
.item {
    content-visibility: auto;
    contain-intrinsic-block-size: auto 24rem;
}
```

is often much better than aggressively precise JavaScript measurement.

---

# 15. `contain-intrinsic-size: none`

There is also:

```css
contain-intrinsic-size: none;
```

This means there is no supplied intrinsic placeholder size.

And there is an important modern distinction:

```css
contain-intrinsic-size: auto none;
```

The latter can remember a rendered value and otherwise fall back to `none`; MDN specifically notes that this can behave better than `0px` in grid and multicolumn layouts, where a fake fixed intrinsic size can produce unexpected overflow/layout behavior. ([MDN Web Docs][8])

---

# 16. One of the most useful patterns

For ordinary vertically stacked content:

```css
.content-section {
    content-visibility: auto;
    contain-intrinsic-block-size: auto 40rem;
}
```

For known independent content:

```css
.component {
    contain: content;
}
```

For animation-heavy components:

```css
.animated {
    transform: translate3d(0, 0, 0);
}
```

No—don't automatically add that last line. More on that below.

# 17. `contain`: the underlying mechanism

`contain` is more surgical than `content-visibility`.

Syntax:

```css
contain: none;
contain: size;
contain: inline-size;
contain: layout;
contain: style;
contain: paint;

contain: layout paint;
contain: layout paint style;
contain: strict;
contain: content;
```

Modern CSS containment has four principal containment types:

```text
size
layout
style
paint
```

with `inline-size` providing one-dimensional size containment. ([MDN Web Docs][9])

---

# 18. `contain: size`

```css
.component {
    contain: size;
}
```

This says:

> The element's size can be calculated without examining its descendants.

Conceptually:

```text
parent sizing
    ↓
do not inspect descendants to determine size
```

This can be useful when the component has independently known dimensions.

But it has a major restriction:

```text
children do not contribute to the size
```

So this can collapse:

```css
.box {
    contain: size;
}
```

when the box otherwise derives its dimensions from content.

CSSWG/MDN therefore recommend supplying a size or intrinsic size when size containment is used. ([MDN Web Docs][10])

### Use when

You genuinely know:

```text
component width/height is externally determined
```

### Do not use when

Your design fundamentally relies on:

```text
children determining parent's height/width
```

---

# 19. `contain: inline-size`

```css
.component {
    contain: inline-size;
}
```

This is one-dimensional containment.

The element's inline size can be determined independently of its children. ([MDN Web Docs][9])

It's useful when the width/inline-size relationship is what you want to isolate, without imposing block-size containment.

This is also relevant to container-query architectures.

---

# 20. `contain: layout`

```css
.component {
    contain: layout;
}
```

This is one of the more useful containment values.

It says, conceptually:

> Internal layout changes should not affect layout outside this component.

So:

```text
      PAGE
       │
  ┌────┴─────┐
  │ COMPONENT│
  │           │
  │ changing  │
  │ internals │
  └───────────┘
       │
outside layout insulated
```

MDN describes layout containment as isolating the component's internal layout so recalculations can remain scoped to the contained subtree. ([MDN Web Docs][10])

### Good candidates

```text
Reusable cards
Widgets
Dashboards
Panels
Embeddable components
Independent UI modules
Complex app components
```

### But:

`contain: layout` changes containing-block and formatting behavior.

An ancestor with layout containment can establish the containing block for absolutely/fixed-positioned descendants, so don't blindly add it to ancestors containing overlays, fixed UI, popovers, etc. ([MDN Web Docs][9])

---

# 21. `contain: paint`

```css
.card {
    contain: paint;
}
```

This tells the browser:

> Descendants cannot paint outside this element's containment bounds.

This is powerful for paint isolation.

But it is also a **visual constraint**.

For example:

```css
.card {
    contain: paint;
}

.card .tooltip {
    position: absolute;
    top: 100%;
}
```

If the tooltip needs to escape the card bounds, paint containment can clip it.

Likewise:

```text
box-shadow
overflow effects
badges
dropdowns
tooltips
flyouts
```

can be affected depending on their geometry.

MDN explicitly states that paint containment clips overflowing descendants to the containment box. ([MDN Web Docs][10])

### Therefore:

Use `contain: paint` when:

```text
the component is visually self-contained
```

Avoid it on:

```text
dropdown ancestors
tooltip ancestors
popover ancestors
flyout containers
UI where decorative content intentionally escapes bounds
```

---

# 22. `contain: style`

This is frequently misunderstood.

```css
.component {
    contain: style;
}
```

does **not** mean:

> "my CSS is scoped to this component."

It is not equivalent to:

```text
Shadow DOM
@scope
CSS Modules
component encapsulation
```

Style containment principally isolates effects such as counters and quotes. MDN specifically describes `counter-*` and quotes behavior. ([MDN Web Docs][10])

Therefore:

```css
contain: style;
```

is not something you should sprinkle everywhere as a generic "faster CSS" declaration.

Its usefulness is more specialized.

---

# 23. `contain: content`

This is:

```css
contain: content;
```

which is equivalent to:

```css
contain: layout paint style;
```

It does **not** include size containment. ([MDN Web Docs][9])

This can be a good default for a genuinely isolated dynamic component where:

```text
internal layout
paint
style-scoped effects
```

can be isolated, but the element still needs its natural size to participate in the parent layout.

Example:

```css
.widget {
    contain: content;
}
```

---

# 24. `contain: strict`

Equivalent to:

```css
contain: size layout paint style;
```

This is extremely strong containment. ([MDN Web Docs][9])

Use it only when the component really satisfies all the requirements.

Do not interpret:

```css
contain: strict;
```

as:

> "strict = fastest."

More containment is not automatically better.

A component can become incorrect because you've imposed restrictions it didn't satisfy.

---

# 25. A practical containment decision tree

Think like this:

### Need to isolate layout?

```css
contain: layout;
```

### Need to stop descendants painting outside?

```css
contain: paint;
```

### Need to stop descendants from contributing to size?

```css
contain: size;
```

### Need only inline-size isolation?

```css
contain: inline-size;
```

### Need an independently contained dynamic widget?

```css
contain: content;
```

### Need every containment dimension and you understand the consequences?

```css
contain: strict;
```

---

# 26. `content-visibility` vs `contain`

This distinction is crucial.

### `contain`

You tell the browser:

> "This subtree is independent in these specific ways."

### `content-visibility`

You tell the browser:

> "This subtree can be skipped when it's not relevant."

So:

```css
.widget {
    contain: layout paint;
}
```

is an **isolation optimization**.

Whereas:

```css
.widget {
    content-visibility: auto;
}
```

is a **conditional rendering-skipping optimization**.

---

# 27. `will-change`: completely different purpose

Now we reach the property people misuse the most.

```css
will-change: transform;
```

does **not** mean:

> "Make transform faster."

It means:

> "I expect this feature to change soon; prepare for it."

The CSSWG describes it as a rendering hint allowing the browser to perform ahead-of-time optimizations. ([CSS Drafts][3])

---

# 28. Valid `will-change` values

Modern syntax includes:

```css
will-change: auto;
will-change: scroll-position;
will-change: contents;

will-change: transform;
will-change: opacity;

will-change: left, top;
```

and other property names via `<custom-ident>`. ([MDN Web Docs][11])

---

# 29. `will-change: transform`

A reasonable use:

```css
.sidebar {
    will-change: transform;
}
```

when:

```text
sidebar is about to slide in/out
```

For example:

```css
.sidebar {
    transform: translateX(-100%);
}

.sidebar.is-opening {
    transform: translateX(0);
}
```

The hint tells the browser that `transform` is expected to change.

But `will-change` is not required for every transform animation.

Browsers already optimize many animations automatically. web.dev explicitly recommends starting with normal compositor-friendly animation rather than adding `will-change prematurely. ([web.dev][12])

---

# 30. `will-change: opacity`

Same idea:

```css
.modal {
    will-change: opacity;
}
```

when:

```text
a modal is about to fade in/out
```

Potentially:

```css
.modal.is-opening {
    opacity: 1;
}
```

But don't put this on:

```css
* {
    will-change: opacity;
}
```

Obviously catastrophic.

But this is also bad:

```css
.card {
    will-change: transform;
}
```

for 800 cards that rarely animate.

---

# 31. Why too much `will-change` can make things worse

The CSSWG is very explicit about this.

Some optimizations associated with `will-change` can consume significant resources.

Too many elements can therefore:

```text
increase memory
increase compositing complexity
increase rendering overhead
cause worse performance
```

and potentially even cause failures under resource pressure. ([CSS Drafts][3])

This is why the spec effectively says:

> use it sparingly.

---

# 32. `will-change` can alter visual behavior

This is another subtle issue.

`will-change` may establish conditions earlier than they would normally appear.

For example, if you use:

```css
will-change: opacity;
```

the browser may establish a stacking context ahead of time.

Likewise, some `will-change` values can influence containing-block behavior. MDN documents these effects. ([MDN Web Docs][11])

So this isn't purely a performance hint with zero semantic consequences.

---

# 33. The correct lifecycle for dynamic `will-change`

Suppose you have:

```text
mouse approaches button
       ↓
animation is likely
       ↓
prepare
       ↓
animation
       ↓
cleanup
```

A good pattern is:

```js
element.style.willChange = "transform, opacity";

// start interaction shortly afterward

element.addEventListener("transitionend", () => {
    element.style.willChange = "auto";
}, { once: true });
```

The CSSWG specifically recommends giving the browser time to prepare and removing `will-change` afterward. ([CSS Drafts][3])

---

# 34. This is a bad pattern

```js
element.style.willChange = "transform";
element.style.transform = "...";
```

immediately in the same moment.

Why?

Because the optimization may need time to be established.

The spec explicitly warns that applying `will-change` immediately before the change may give the browser insufficient setup time. ([CSS Drafts][3])

---

# 35. A useful prediction window

For example:

```css
.card-container:hover .card {
    will-change: transform;
}
```

Then:

```css
.card:hover {
    transform: scale(1.03);
}
```

The ancestor hover can provide advance warning before the actual element changes.

The CSSWG gives essentially this pattern as an example of providing sufficient lead time. ([CSS Drafts][3])

---

# 36. `will-change: contents`

This one is very different.

```css
will-change: contents;
```

means:

> The contents of this element's subtree are expected to change.

This is primarily useful for cases involving dynamic, frequently changing content.

The specification says this can help browsers decide not to maintain rendering caches too aggressively for a subtree whose contents are constantly changing. ([CSS Drafts][3])

It is not something most normal websites need.

---

# 37. `will-change: scroll-position`

```css
will-change: scroll-position;
```

is a specialized hint for scrolling behavior.

It says the element's scroll position is expected to change soon.

This is much more specialized than:

```css
will-change: transform;
```

and should not be added to arbitrary scroll containers.

The CSSWG describes it as a hint that can influence how much content around the scrolling window gets prepared. ([CSS Drafts][3])

---

# 38. `will-change` does NOT guarantee a GPU layer

This deserves its own section because the internet is full of outdated advice.

Bad explanation:

> "`will-change: transform` sends it to the GPU."

Not guaranteed.

Correct explanation:

> `will-change` informs the browser that a property is expected to change so the browser can choose suitable optimizations.

The CSS specification explicitly says different browsers—and even the same browser at different times—can respond differently. It gives layer promotion as only one possible implementation strategy. ([CSS Drafts][3])

---

# 39. Don't use `translateZ(0)` as a universal hack

You will frequently see:

```css
transform: translateZ(0);
```

or:

```css
transform: translate3d(0, 0, 0);
```

used as an old "force GPU acceleration" trick.

Do not build a modern CSS architecture around this.

The real goal is:

```text
choose an appropriate animation property
measure
let the browser optimize
use will-change only when evidence justifies it
```

not:

```text
add mysterious 3D transforms everywhere
```

---

# 40. `transform` is important—but understand why

For animation:

```css
transform: translateX(...);
transform: translateY(...);
transform: scale(...);
transform: rotate(...);
```

is generally preferable to:

```css
left: ...;
top: ...;
width: ...;
height: ...;
margin-left: ...;
```

because geometry-changing properties can trigger layout, whereas compositor-friendly transform animations can often avoid layout and paint. ([MDN Web Docs][13])

Example:

### Less desirable

```css
@keyframes slide {
    from {
        left: 0;
    }

    to {
        left: 300px;
    }
}
```

### Usually preferable

```css
@keyframes slide {
    from {
        transform: translateX(0);
    }

    to {
        transform: translateX(300px);
    }
}
```

---

# 41. Modern individual transform properties

You can also use:

```css
translate
scale
rotate
```

instead of always writing:

```css
transform: translate(...) scale(...) rotate(...);
```

For example:

```css
.card {
    transition: scale 200ms ease;
}

.card:hover {
    scale: 1.03;
}
```

These are still fundamentally transform-like operations and can participate in efficient rendering paths where supported. MDN treats them as individual transform properties. ([MDN Web Docs][11])

---

# 42. `opacity`

For animation:

```css
opacity: 0;
opacity: 1;
```

is usually a good property to animate.

Example:

```css
.fade {
    transition: opacity 180ms ease;
}
```

Because opacity does not change layout geometry.

But don't confuse:

```css
opacity: 0;
```

with:

```css
display: none;
```

They are radically different.

`opacity: 0` leaves the element in the DOM and it remains interactive—pointer events and focus behavior can remain. ([MDN Web Docs][14])

# 43. Visibility/hiding comparison

This is one of the most useful tables to remember.

| Technique                   | Layout space?                                  | Descendants rendered?            | A11y/user-agent behavior         | Typical use                 |
| --------------------------- | ---------------------------------------------- | -------------------------------- | -------------------------------- | --------------------------- |
| `display:none`              | ❌                                              | ❌                                | hidden                           | Truly remove                |
| `visibility:hidden`         | ✅                                              | hidden                           | hidden from a11y tree            | Hide but preserve geometry  |
| `opacity:0`                 | ✅                                              | ✅                                | still exposed                    | Fade animation              |
| `content-visibility:hidden` | Strong containment / may need intrinsic sizing | ❌                                | skipped from user-agent features | Cached hidden UI            |
| `content-visibility:auto`   | ✅                                              | offscreen subtree can be skipped | remains available                | Long pages/lists            |
| off-screen transform        | ✅                                              | ✅                                | still exposed                    | Animation/state positioning |

`display:none` removes the element from layout and its subtree from the accessibility tree. `visibility:hidden` preserves layout but removes it from the accessibility tree. `opacity:0` leaves it interactive. `content-visibility:auto` keeps off-screen content in the DOM and accessibility tree. ([MDN Web Docs][15])

---

# 44. Never use opacity as a hiding mechanism without considering interaction

This is dangerous:

```css
.menu {
    opacity: 0;
}
```

while the menu contains:

```html
<a href="/private-page">...</a>
<button>...</button>
```

The menu might be invisible but still:

```text
focusable
interactive
pointer-event capable
```

because opacity does not remove it from interaction. ([MDN Web Docs][14])

A proper UI state may need:

```css
.menu {
    opacity: 0;
    pointer-events: none;
}

.menu.is-open {
    opacity: 1;
    pointer-events: auto;
}
```

and appropriate keyboard/focus management in the application.

---

# 45. `visibility: hidden`

Use:

```css
visibility: hidden;
```

when:

```text
geometry should remain
but content should not be visible/accessible
```

Good example:

```text
placeholder UI
temporarily hidden table row
visual state transition
```

But it is not a high-performance rendering-skip solution in the same sense as `content-visibility`.

MDN explicitly distinguishes `visibility` from `display` based on whether layout space remains. ([MDN Web Docs][16])

---

# 46. `content-visibility: hidden` vs `visibility: hidden`

This distinction is particularly useful:

```css
visibility: hidden;
```

means approximately:

```text
don't show me,
but preserve geometry
```

while:

```css
content-visibility: hidden;
```

means more like:

```text
don't render this subtree;
apply strong containment;
skip its rendering work;
preserve/use cached state where possible
```

That makes the latter potentially much more valuable for large inactive views—but also substantially more restrictive. ([web.dev][5])

---

# 47. Important accessibility distinction with `content-visibility`

For:

```css
content-visibility: auto;
```

off-screen content remains in:

```text
DOM
Accessibility tree
Find-in-page
Tab/focus interaction
```

subject to its overall state and browser behavior. ([MDN Web Docs][4])

That's a major reason it is attractive as an alternative to crude JavaScript virtualization.

For:

```css
content-visibility: hidden;
```

the skipped contents aren't available to these user-agent features. ([MDN Web Docs][4])

---

# 48. `content-visibility: auto` is NOT traditional virtualization

Traditional virtual scrolling might do:

```text
10,000 records
        ↓
DOM only contains 30 records
```

while `content-visibility: auto` is conceptually:

```text
10,000 records
        ↓
DOM contains all 10,000
        ↓
browser skips rendering work
for irrelevant chunks
```

The CSSWG explicitly mentions `content-visibility: auto` as something that can replace complicated virtual-list techniques **in many cases**. ([CSS Drafts][1])

But not all.

For truly enormous datasets, the DOM itself can become the bottleneck:

```text
100,000 nodes
1,000,000 nodes
```

and `content-visibility` doesn't magically make the DOM disappear.

---

# 49. `content-visibility` doesn't mean "nothing exists"

This distinction matters:

```text
DOM exists
CSS exists
JS exists
semantic content exists
```

but:

```text
layout/paint work can be skipped
```

So you should not expect:

```css
content-visibility: auto;
```

to solve:

```text
huge DOM memory usage
huge HTML download
huge JS initialization
huge network transfer
```

It primarily attacks **rendering work**.

---

# 50. Don't confuse render skipping with resource loading

For genuinely lazy-loading resources, use the appropriate resource-level mechanism.

For example:

```html
<img
    src="..."
    loading="lazy"
    width="800"
    height="500"
    alt="..."
>
```

`content-visibility` is not your substitute for all network/resource loading strategies.

Web performance guidance treats lazy loading of images, iframes and other resources as a separate concern. ([MDN Web Docs][17])

---

# 51. `aspect-ratio` is a performance-adjacent property

Suppose:

```html
<img src="hero.jpg">
```

doesn't have predictable geometry.

The browser may initially lay out around incomplete dimensions, then adjust when the image becomes known.

Use:

```css
img {
    aspect-ratio: 16 / 9;
    width: 100%;
    height: auto;
}
```

or, even better, provide intrinsic dimensions in HTML when appropriate:

```html
<img
    src="hero.jpg"
    width="1600"
    height="900"
    alt="..."
>
```

This isn't primarily "render less," but it is critical for stable layout and therefore perceived performance and Core Web Vitals.

---

# 52. Be careful with expensive paint properties

Not every expensive CSS property triggers layout.

For example:

```css
box-shadow
filter
backdrop-filter
background effects
mix-blend-mode
large gradients
clip-path
```

can increase **paint/compositing cost**.

A page can therefore avoid layout perfectly and still be slow because paint is expensive.

web.dev specifically notes that blur-like effects can be considerably more expensive to paint, and `backdrop-filter` can harm performance. ([web.dev][12])

---

# 53. `box-shadow`

This:

```css
box-shadow:
    0 20px 60px rgb(0 0 0 / 20%);
```

can be substantially more expensive than:

```css
box-shadow:
    0 1px 2px rgb(0 0 0 / 10%);
```

especially when:

```text
large blur radius
large area
many elements
animation
continuous updates
```

are involved.

One large static shadow is not inherently a problem.

What is expensive is doing this:

```text
1000 cards
+
large blurry shadows
+
continuous animation
```

Performance must be evaluated in context.

---

# 54. `filter: blur()`

Blur is particularly interesting.

Conceptually:

```css
filter: blur(30px);
```

requires processing surrounding pixels.

As blur radius increases, the amount of pixel work can become substantial. web.dev's filter analysis specifically identifies blur and drop-shadow as among the more expensive filter effects. ([web.dev][18])

Therefore:

```css
filter: blur(4px);
```

and:

```css
filter: blur(80px);
```

should not be considered equivalent from a rendering-cost perspective.

---

# 55. `backdrop-filter`

This is often much more expensive than people realize:

```css
.glass {
    backdrop-filter: blur(20px);
}
```

The browser effectively has to process background content behind the translucent element.

It can be gorgeous.

But don't create:

```text
50 overlapping backdrop-filter cards
```

and then blame `will-change` when the page stutters.

web.dev explicitly warns that `backdrop-filter` may harm performance and recommends testing it before deployment. ([web.dev][19])

---

# 56. `mix-blend-mode`

```css
.hero {
    mix-blend-mode: screen;
}
```

creates a stacking context and blends with the backdrop. ([MDN Web Docs][20])

This can complicate compositing.

Use it because the visual effect requires it—not because it is supposedly a performance optimization.

---

# 57. `isolation`

```css
.component {
    isolation: isolate;
}
```

forces a new stacking context.

It is particularly useful when working with:

```css
mix-blend-mode;
z-index;
```

and compositing isolation. ([MDN Web Docs][21])

But:

```css
isolation: isolate;
```

is not a magic performance accelerator.

Its main purpose is **stacking/compositing isolation**.

Sometimes that isolation helps the browser or simplifies rendering dependencies, but you shouldn't add it indiscriminately.

---

# 58. `overflow: clip`

Modern CSS has:

```css
overflow: clip;
```

It clips overflow without turning the element into a scroll container. `overflow: hidden`, on the other hand, creates a scroll container even though scrollbars aren't displayed. ([MDN Web Docs][22])

So when you genuinely mean:

> "Clip this content. It must not be scrollable."

then:

```css
overflow: clip;
```

can more precisely express that intent.

Do not use it merely because the word "clip" sounds faster.

---

# 59. `contain: paint` vs `overflow: clip`

They're related, but not the same.

```css
overflow: clip;
```

means:

```text
clip overflow
```

while:

```css
contain: paint;
```

means:

```text
establish paint containment
```

Paint containment brings additional containment semantics and affects descendants/stacking/containing behavior.

So choose based on the behavior you require, not performance folklore.

---

# 60. Animation properties: what to prefer

A useful practical hierarchy is:

### Usually good choices

```css
transform
translate
scale
rotate
opacity
```

### Frequently more expensive when animated

```css
width
height
top
left
right
bottom
margin
padding
border-width
font-size
```

### Potentially expensive paint effects

```css
box-shadow
filter
backdrop-filter
large gradients
blend modes
```

MDN and web.dev both recommend favoring transform/opacity for animations where possible. ([MDN Web Docs][13])

---

# 61. Don't blindly avoid layout

This is another performance myth.

This:

```css
width: 200px;
```

is not "bad CSS."

The problem is:

```text
changing width every frame
on a large layout
during an interaction
```

If a property changes once:

```text
button clicked
→ panel expands
```

and the resulting layout takes 2 ms, there is no problem.

Performance advice should therefore be:

> Avoid unnecessary expensive work, particularly in high-frequency update paths.

Not:

> Never use layout properties.

web.dev explicitly emphasizes measurement rather than blindly optimizing every CSS rule. ([MDN Web Docs][23])

---

# 62. Animation frequency matters

Consider:

```css
width: 500px;
```

changed once.

Versus:

```css
width: calc(500px + var(--x));
```

where `--x` changes:

```text
60 times per second
```

The second is dramatically more important to optimize.

Performance problems often come from:

```text
scroll handlers
dragging
pointer movement
continuous animations
canvas-like UI
interactive dashboards
```

not from static CSS.

---

# 63. CSS containment can limit the blast radius

Suppose:

```text
page
 ├── header
 ├── sidebar
 ├── content
 │    ├── widget A
 │    ├── widget B
 │    └── widget C
 └── footer
```

If widget B changes layout repeatedly, containment can let you communicate:

```css
.widget-b {
    contain: layout;
}
```

Conceptually:

```text
widget B changes
        ↓
contained layout scope
        ↓
less outside invalidation
```

This is the architectural advantage of containment. ([MDN Web Docs][10])

---

# 64. Component architecture and containment

A useful modern design philosophy is:

```text
Page
 ├── Navigation
 ├── Hero
 ├── Features
 │    ├── Feature card
 │    ├── Feature card
 │    └── Feature card
 ├── Testimonials
 │    ├── Testimonial
 │    └── Testimonial
 └── Footer
```

instead of one giant render-sensitive subtree.

Then individual independent sections can have:

```css
.section {
    content-visibility: auto;
    contain-intrinsic-block-size: auto 30rem;
}
```

and truly isolated interactive widgets can have:

```css
.widget {
    contain: content;
}
```

This is much more meaningful than sprinkling `will-change` on everything.

---

# 65. CSS itself is render-blocking

This is another major optimization category.

CSS generally blocks rendering because the browser needs the CSSOM before it can reliably construct the final styled render tree. ([MDN Web Docs][24])

Therefore:

```text
huge CSS file
       ↓
download
       ↓
parse
       ↓
CSSOM
       ↓
rendering can continue
```

This makes **CSS delivery** just as important as individual property choices.

---

# 66. Remove unused CSS

Unused CSS contributes to:

```text
download
parsing
CSSOM/style processing
maintenance
```

Chrome DevTools Coverage can identify unused CSS. web.dev recommends using it to identify large portions of CSS that aren't needed for a given page. ([web.dev][25])

Instead of:

```css
/* 300 KB giant framework */
```

consider:

```text
critical CSS
page CSS
component CSS
optional/deferred CSS
```

where architecture allows it.

---

# 67. Minify and compress CSS

Production CSS should normally be:

```text
minified
compressed
cached
```

Typical production pipeline:

```text
source CSS
    ↓
PostCSS / bundler
    ↓
minification
    ↓
Brotli / gzip
    ↓
CDN/cache
```

MDN explicitly recommends minification and compression as part of CSS performance optimization. ([MDN Web Docs][23])

---

# 68. Split CSS based on actual usage

For example:

```html
<link rel="stylesheet" href="/core.css">

<link
    rel="stylesheet"
    href="/print.css"
    media="print">

<link
    rel="stylesheet"
    href="/mobile.css"
    media="screen and (width <= 480px)">
```

A stylesheet whose media condition doesn't currently match does not block rendering in the same way as matching critical CSS, although the browser may still download it at low priority. ([MDN Web Docs][23])

This is useful for:

```text
print styles
special modes
conditional layouts
optional feature-specific CSS
```

---

# 69. But don't create 100 CSS files

Splitting CSS is not automatically good.

You have tradeoffs:

```text
too much monolithic CSS
        ↓
large critical path
```

versus:

```text
hundreds of tiny CSS files
        ↓
requests / coordination / complexity
```

The right answer is generally:

```text
critical CSS
+
appropriately chunked non-critical CSS
```

based on actual application architecture.

---

# 70. Inline critical CSS carefully

For very small above-the-fold styles:

```html
<style>
    /* critical styles */
</style>
```

can eliminate an additional request.

But large inline CSS has downsides because the HTML itself becomes larger and the CSS cannot be reused/cached as an external resource in the same way. web.dev explicitly cautions against blindly inlining large stylesheets. ([web.dev][26])

---

# 71. Selector complexity: optimize, but don't obsess

Example:

```css
body main article .post h2.title {}
```

versus:

```css
.title {}
```

The simpler selector can be cheaper and is easier to maintain.

MDN and web.dev recommend avoiding unnecessarily complex selectors and limiting overly broad selectors. ([MDN Web Docs][23])

But this deserves an important caveat:

> Selector micro-optimization is usually much less important than reducing DOM size, expensive rendering, forced layout, and unused CSS.

MDN explicitly notes that selector optimization is generally a microsecond-level concern compared with bigger optimization opportunities. ([MDN Web Docs][24])

---

# 72. Avoid unnecessarily broad selectors

For example:

```css
body * {
    ...
}
```

can match an enormous number of elements.

Prefer a scoped component:

```css
.article {
    ...
}

.article > p {
    ...
}
```

where it makes architectural sense.

MDN specifically warns about applying styles to unnecessarily large portions of the tree. ([MDN Web Docs][23])

---

# 73. `:has()` deserves caution

Modern:

```css
.card:has(img)
```

is extremely powerful.

It is not inherently "slow."

But complex structural matching—especially large, dynamic `:has()` patterns—can increase style recalculation work.

MDN explicitly includes `:has()` as an area where performance considerations deserve attention. ([MDN Web Docs][23])

Use it because it expresses your UI logic clearly, not because you assume either:

```text
`:has()` = slow
```

or:

```text
`:has()` = free
```

Measure complicated cases.

---

# 74. `@scope` / cascade layers / specificity

Modern CSS architecture should also minimize unnecessary cascade complexity.

Useful tools include:

```css
@layer base;
@layer components;
@layer utilities;
```

and:

```css
@scope (.component) {
    ...
}
```

These are primarily architecture/maintenance features, but good CSS organization can reduce accidental style interactions and make performance debugging much easier.

MDN notes that cascade layers can reduce the need for escalating specificity and simplify large CSS systems. ([MDN Web Docs][27])

Do not claim that `@layer` magically makes CSS faster—it primarily improves cascade organization.

---

# 75. Container queries and performance

Modern container queries use:

```css
.container {
    container-type: inline-size;
}
```

or:

```css
.container {
    container-type: size;
}
```

This establishes containment needed for size querying. ([MDN Web Docs][28])

For example:

```css
.card-grid {
    container-type: inline-size;
}

@container (width > 700px) {
    .card-grid {
        grid-template-columns: repeat(3, 1fr);
    }
}
```

This is useful because the component reacts to **its own available space**, rather than requiring global viewport assumptions.

Don't use container queries solely because you think they are inherently faster; their principal benefit is component-level responsive architecture.

---

# 76. Font rendering is another major CSS-adjacent performance area

```css
@font-face {
    font-family: "MyFont";
    src: url("/fonts/myfont.woff2") format("woff2");
    font-display: swap;
}
```

`font-display` determines how text behaves while the font is loading.

Available modes include:

```text
auto
block
swap
fallback
optional
```

Different modes trade off:

```text
text visibility
font correctness
layout shifting
loading behavior
```

web.dev notes that `font-display` can materially affect FCP, LCP, and layout stability. ([web.dev][29])

---

# 77. `font-display: optional`

For body text where performance is prioritized:

```css
@font-face {
    font-display: optional;
}
```

This gives the browser permission to keep the fallback font if the webfont doesn't arrive quickly enough. web.dev describes this as the strongest performance-oriented strategy but with the tradeoff that the custom font may not be used. ([web.dev][29])

---

# 78. `font-display: swap`

Common:

```css
@font-face {
    font-display: swap;
}
```

This allows fallback text to appear and then swaps to the webfont when available.

The downside can be:

```text
fallback font
     ↓
custom font loads
     ↓
text metrics change
     ↓
layout changes
```

So use font metric adjustment techniques where needed.

---

# 79. `size-adjust`, `ascent-override`, `descent-override`, `line-gap-override`

Modern font control provides:

```css
@font-face {
    font-family: "Fallback Adjusted";
    src: local("Arial");
    size-adjust: 95%;
    ascent-override: 90%;
    descent-override: 22%;
    line-gap-override: 0%;
}
```

These can make the fallback metrics more closely match the eventual webfont, reducing layout differences when fonts swap.

This isn't the same category as `content-visibility`, but it belongs in any serious CSS performance handbook because fonts can affect layout, paint and Core Web Vitals.

---

# 80. A critical misconception: "GPU = performance"

You should think:

```text
CPU
GPU
main thread
compositor
rasterization
```

as implementation details.

The real goal is:

```text
less work
+
smaller invalidation scope
+
less layout
+
less paint
+
efficient compositing
```

A GPU can also become a bottleneck.

You can have:

```text
too many composited layers
+
huge textures
+
large blur surfaces
+
high-resolution device
```

and be slower than a simpler non-composited implementation.

This is why the CSSWG cautions that too many `will-change` declarations can exhaust resources. ([CSS Drafts][3])

---

# 81. Layers are not free

A composited layer consumes resources.

Think:

```text
DOM element
    ↓
surface / texture
    ↓
memory
    ↓
compositing
```

One large animated hero may benefit from compositing.

10,000 tiny cards each promoted into their own layer may be disastrous.

Therefore:

```css
will-change: transform;
```

should not be interpreted as:

```text
"create a free performance layer"
```

---

# 82. Sticky/fixed elements need special care

Large:

```css
position: fixed;
```

or:

```css
position: sticky;
```

elements that constantly repaint can become expensive.

MDN notes that scrolling with fixed/sticky content can cause repaint cost and discusses `will-change: transform` as a possible technique when repaint performance is actually a problem. ([MDN Web Docs][30])

But again:

```css
header {
    will-change: transform;
}
```

is not automatically necessary.

Measure first.

---

# 83. `backface-visibility`

You may see:

```css
.card {
    backface-visibility: hidden;
}
```

This is mostly a **3D transformation visual behavior** property.

It controls whether the backside of a transformed element is visible. It has no effect on ordinary 2D transforms. ([MDN Web Docs][31])

So don't add:

```css
* {
    backface-visibility: hidden;
}
```

as a performance reset.

That's cargo cult CSS.

---

# 84. The famous "GPU hacks" you should avoid as defaults

Avoid global patterns like:

```css
* {
    transform: translateZ(0);
}
```

or:

```css
* {
    will-change: transform;
}
```

or:

```css
* {
    backface-visibility: hidden;
}
```

or:

```css
* {
    contain: strict;
}
```

These are all examples of using a specialized mechanism without knowing whether the application's rendering architecture actually needs it.

---

# 85. `content-visibility` + `contain-intrinsic-size`: the best general long-page recipe

For a blog/article/documentation page:

```css
.section {
    content-visibility: auto;
    contain-intrinsic-block-size: auto 32rem;
}
```

HTML:

```html
<article>
    <section class="section">
        ...
    </section>

    <section class="section">
        ...
    </section>

    <section class="section">
        ...
    </section>

    <section class="section">
        ...
    </section>
</article>
```

This communicates:

```text
each section is independently renderable
↓
off-screen sections can be skipped
↓
browser has a reasonable estimated height
↓
once rendered, browser can remember actual size
```

This is probably the single most useful pattern from this entire topic.

---

# 86. Better than blindly applying it to every element

Do **not** do:

```css
* {
    content-visibility: auto;
}
```

Why?

Because you're not creating meaningful rendering chunks.

You can introduce:

```text
too many containment boundaries
unexpected layout behavior
unnecessary browser bookkeeping
harder debugging
```

and many elements will be visible anyway.

Use meaningful chunks:

```text
article section
card group
feed item
dashboard widget
large component
```

# 87. SPA/tab-panel recipe

Suppose:

```html
<div class="tab-panel is-active">...</div>
<div class="tab-panel">...</div>
<div class="tab-panel">...</div>
```

For inactive views:

```css
.tab-panel {
    content-visibility: hidden;
}

.tab-panel.is-active {
    content-visibility: visible;
}
```

This can keep the inactive subtree in the DOM while avoiding rendering its contents.

The tradeoff is accessibility/user-agent behavior: hidden content is skipped for user-agent features, so make sure your tab semantics and ARIA state reflect the UI state. ([MDN Web Docs][4])

---

# 88. Animated hidden panels with modern CSS

Modern CSS can transition discrete properties.

For example, `content-visibility` can participate in discrete transitions, and supporting browsers have special behavior to keep content visible for the duration of an entry/exit animation. CSS transitions can use:

```css
transition-behavior: allow-discrete;
```

for this class of transition. ([MDN Web Docs][4])

Example concept:

```css
.panel {
    transition:
        opacity 200ms ease,
        content-visibility 0s;
    transition-behavior: allow-discrete;

    content-visibility: hidden;
    opacity: 0;
}

.panel.is-open {
    content-visibility: visible;
    opacity: 1;
}
```

The exact transition architecture should be tested because `content-visibility` is discrete rather than a continuously interpolated visual quantity. ([MDN Web Docs][4])

---

# 89. Canvas-heavy components are a special case

Suppose:

```html
<canvas class="chart"></canvas>
```

inside:

```css
.chart-container {
    content-visibility: auto;
}
```

When off-screen, rendering work may be skipped.

Modern browsers expose:

```text
contentvisibilityautostatechange
```

which fires when the browser starts/stops skipping the rendering of an `auto` element. MDN specifically highlights this for cases such as controlling canvas rendering work. ([MDN Web Docs][4])

Conceptually:

```js
element.addEventListener(
    "contentvisibilityautostatechange",
    event => {
        // pause/resume expensive rendering
    }
);
```

This is a powerful bridge between CSS rendering optimization and JS-driven rendering.

---

# 90. Avoid forced layout when using content visibility

This is a subtle but very important point.

Suppose you create:

```css
.large-section {
    content-visibility: auto;
}
```

but your JavaScript constantly executes APIs that require layout information for the skipped subtree.

You may force the browser to do work you were trying to avoid.

web.dev specifically warns that DOM APIs which force rendering/layout can defeat `content-visibility`'s benefits, and Chromium can surface diagnostics for some of these cases. ([web.dev][5])

---

# 91. Classic layout thrashing

Bad:

```js
for (const item of items) {
    item.style.width = `${container.offsetWidth}px`;
}
```

because it mixes:

```text
write
read
write
read
...
```

and can repeatedly force layout.

Better:

```js
const width = container.offsetWidth;

for (const item of items) {
    item.style.width = `${width}px`;
}
```

This is called avoiding **forced synchronous layout/layout thrashing**.

web.dev's current guidance strongly recommends grouping reads and writes where possible. ([web.dev][32])

---

# 92. CSS containment can help JS-driven interfaces too

Imagine a dashboard:

```text
Dashboard
 ├── chart
 ├── table
 ├── activity feed
 ├── notifications
 └── analytics panel
```

If the analytics panel is highly dynamic:

```css
.analytics-panel {
    contain: layout paint;
}
```

can reduce how far its internal changes propagate.

If it's also frequently off-screen:

```css
.analytics-panel {
    content-visibility: auto;
    contain-intrinsic-block-size: auto 40rem;
}
```

may be more appropriate.

# 93. `contain` + `content-visibility`: don't stack blindly

Do not automatically write:

```css
.widget {
    contain: strict;
    content-visibility: auto;
}
```

because you're "doubling performance."

`content-visibility:auto` already supplies important containment semantics.

You should add extra containment only when it serves a specific need and remains correct.

# 94. A useful conceptual hierarchy

When optimizing a slow page, try this order:

```text
1. Remove unnecessary DOM/content
        ↓
2. Remove unnecessary CSS
        ↓
3. Prevent unnecessary rendering
        ↓
4. Contain expensive independent regions
        ↓
5. Use compositor-friendly animations
        ↓
6. Reduce expensive paint effects
        ↓
7. Use will-change only when measured evidence justifies it
```

This ordering matches the broad principles in current web performance guidance: measure first, reduce rendering work, isolate expensive subtrees, avoid expensive layout/paint paths, and use `will-change` cautiously. ([MDN Web Docs][23])

# 95. What you should NOT optimize prematurely

Don't waste hours worrying about:

```text
.btn vs button
0.1 ms selector differences
whether flex is "slow"
whether grid is "slow"
whether border-radius is "slow"
whether one shadow exists
whether a class has one extra character
```

before you investigate:

```text

unused CSS
forced synchronous layout
layout thrashing
large paint areas
huge blur effects
backdrop-filter
hundreds of animated nodes
large images
webfont loading
JS main-thread work
long tasks
```

Those tend to be the actual high-value problems.

MDN specifically emphasizes measuring before optimizing CSS because many micro-optimizations have negligible impact compared with larger architectural issues. ([MDN Web Docs][23])

Also test:


At:

# 103. Performance + accessibility must be considered together

Don't optimize a tab by doing:

```css
display: none;
```

simply because it "renders less."

That might be correct—but only if the content is actually intended to be unavailable.

Likewise:

```css
opacity: 0;
```

may preserve content but accidentally leave controls interactive. ([MDN Web Docs][15])

And:

```css
content-visibility: hidden;
```

removes it from find-in-page/tab/focus behavior. ([MDN Web Docs][4])

Performance behavior is inseparable from UI semantics.

---

# 104. `aria-hidden` is NOT a rendering optimization

This:

```html
<div aria-hidden="true">
```

doesn't itself make CSS render less.

It changes accessibility exposure.

Similarly:

```css
display: none;
```

does affect both layout/rendering and accessibility.

Don't mix these concepts.

MDN explicitly cautions that `aria-hidden` does not itself visually hide an element. ([MDN Web Docs][33])

---

# 105. `display: contents` is not a performance trick

You may see:

```css
.wrapper {
    display: contents;
}
```

and think:

```text
remove wrapper box = faster DOM
```

That is not a sound optimization strategy.

`display: contents` changes box generation rather than removing the DOM element, and current browser accessibility behavior has historical/implementation caveats. ([MDN Web Docs][15])

Use it when its **layout semantics** are appropriate, not to chase theoretical performance.

# 107. A "do not use" table

| Pattern                                        | Why not                                       |
| ---------------------------------------------- | --------------------------------------------- |
| `* { will-change: transform }`                 | Massive unnecessary resource use              |
| `body { will-change: transform }`              | Huge subtree / unnecessary optimization       |
| `will-change` everywhere                       | Browser already optimizes many cases          |
| `translateZ(0)` everywhere                     | Old compositing hack / layer bloat            |
| `contain: strict` everywhere                   | Can break sizing/layout/positioning           |
| `contain: paint` around dropdowns              | Can clip escaping UI                          |
| `contain: size` on content-sized boxes         | Can collapse sizing                           |
| `content-visibility: auto` on entire page      | Usually too coarse                            |
| `content-visibility: auto` on every tiny node  | Poor granularity                              |
| `opacity: 0` as semantic hiding                | Element remains interactive                   |
| giant animated `box-shadow`                    | Expensive paint                               |
| many large `backdrop-filter`s                  | Potentially expensive compositing/filter work |
| optimizing selector microseconds first         | Usually insignificant                         |
| adding CSS performance hacks without measuring | Can make the page worse                       |

# 108. The most important "when to use" matrix

| Feature                        | Use it when                                     | Avoid it when                                       |
| ------------------------------ | ----------------------------------------------- | --------------------------------------------------- |
| `content-visibility:auto`      | Large offscreen independent content             | Element is almost always visible                    |
| `content-visibility:hidden`    | Inactive expensive UI that stays in DOM         | Content must remain searchable/focusable            |
| `contain-intrinsic-block-size` | Using size containment for vertical content     | No size containment involved                        |
| `contain:size`                 | Component size is externally determined         | Children define natural size                        |
| `contain:inline-size`          | Inline dimension can be isolated                | Width naturally depends on descendants              |
| `contain:layout`               | Component layout is independent                 | Internal layout must affect outside                 |
| `contain:paint`                | Visual bounds are truly self-contained          | Tooltips/dropdowns escape                           |
| `contain:content`              | Reusable isolated widget                        | Component depends on external containment semantics |
| `contain:strict`               | Fully self-contained fixed/controlled component | General-purpose UI                                  |
| `will-change`                  | Imminent, known, measured expensive change      | Everything "just in case"                           |
| `transform`                    | Movement/scale/rotation animation               | You need actual document reflow                     |
| `opacity`                      | Fading                                          | You need interaction to disappear too               |
| `overflow:clip`                | Strict clipping, no scrolling semantics         | You need scrolling                                  |
| `filter:blur()`                | Required visual effect                          | Huge areas/high-frequency animation                 |
| `backdrop-filter`              | Required glass/translucency effect              | Large numbers of dynamic surfaces                   |

# 109. The strongest modern rule set

For a modern production site, my baseline would be roughly:

```text
┌────────────────────────────────────────────┐
│ 1. Keep DOM reasonably small              │
│ 2. Remove unused CSS                      │
│ 3. Keep critical CSS small                │
│ 4. Use semantic independent sections      │
│ 5. content-visibility:auto for long pages │
│ 6. Provide intrinsic block-size estimates │
│ 7. contain truly independent widgets      │
│ 8. animate transform/opacity when suitable │
│ 9. minimize expensive paint effects       │
│10. use will-change only when justified    │
│11. measure with DevTools                  │
│12. verify mobile performance              │
└────────────────────────────────────────────┘
```

This is much more robust than a "GPU acceleration checklist."

# 110. My recommended CSS architecture for your kind of modern portfolio

For a developer portfolio / long scrolling site, something like this is a particularly sensible architecture:

```css
/* Long, independent page sections */
.page-section {
    content-visibility: auto;
    contain-intrinsic-block-size: auto 32rem;
}

/* Independent complex components */
.component {
    contain: content;
}

/* Only components whose inline sizing is independently determined */
.responsive-component {
    container-type: inline-size;
}

/* Animation */
.animated {
    transition:
        transform 200ms ease,
        opacity 200ms ease;
}

/* Actual movement */
.animated.is-active {
    transform: translateY(0);
    opacity: 1;
}
```

And then:

```css
/* Do NOT automatically add this */
* {
    will-change: transform;
}
```

Instead, selectively introduce:

```css
.special-interaction {
    will-change: transform;
}
```

only where profiling shows that it helps.

```text

      ↓

      ↓

      ↓
Calculate layout
      ↓

      ↓
```

```text
      ↓

      ↓
```

```text
      ↓

```

```text
Animation
      ↓
Avoid changing document geometry
```

## With `will-change`

```text
Known imminent animation
      ↓
"Prepare for this"
```

That is the clean conceptual model.

# 112. The "golden rules"

### Rule 1

```css
content-visibility: auto;
```

is primarily a **render-skipping tool**, not a generic visibility property.

### Rule 2

Pair skipped content with an appropriate intrinsic size:

```css
contain-intrinsic-block-size: auto 30rem;
```

when the layout needs a reliable placeholder size. ([MDN Web Docs][6])

### Rule 3

Use `contain` when you know a subtree is independently laid out/painted.

### Rule 4

Don't use `contain: strict` casually.

### Rule 5

Use `transform` and `opacity` for high-frequency animations when their semantics fit.

### Rule 6

`will-change` is a **hint**, not a command. ([CSS Drafts][3])

### Rule 7

Never add `will-change` everywhere.

### Rule 8

Never assume "GPU" means "faster."

### Rule 9

Large blur, shadows and backdrop filtering can dominate paint cost.

### Rule 10

Measure first.

MDN's CSS performance guidance explicitly starts with determining what actually needs optimization rather than indiscriminately applying every technique. ([MDN Web Docs][23])

## One particularly important current-browser note

`content-visibility` is now broadly available in modern browser engines; MDN lists it as Baseline 2024, and web.dev has reported it as available across the three major browser engines. Older browsers can simply ignore the property, so the primary concern is validating the fallback behavior rather than avoiding the feature entirely. ([MDN Web Docs][4])
