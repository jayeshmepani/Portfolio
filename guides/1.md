# The Engineering Handbook to Web Performance: CSS Rendering, JavaScript Scheduling, and Thread Orchestration

A technical reference for browser internals, rendering mechanics, main-thread scheduling, and asset delivery. This guide covers how to isolate layout, skip rendering, schedule work on the event loop, move computation off the main thread, and optimize the critical rendering path.

---

# Part 1: The Unified Engine Model & Frame Budgets

The browser platform coordinates multiple threads, memory spaces, and queues to transform code into pixels. Understanding this architecture is essential for diagnosing bottlenecks and choosing the right optimization primitives.

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                       BROWSER PROCESS                                            │
│  Network Stack ──► IPC ──► Resource Cache                                                        │
└────────────────────────────────────────────────┬─────────────────────────────────────────────────┘
                                                 │ IPC
┌────────────────────────────────────────────────▼─────────────────────────────────────────────────┐
│                                      RENDERER PROCESS                                            │
│                                                                                                  │
│  ┌────────────────────────────────────────────────────────────────────────────────────────────┐  │
│  │ MAIN THREAD                                                                                │  │
│  │  Tasks & Microtasks ──► Observers ──► rAF ──► Style Recalc ──► Layout ──► Pre-Paint ──► ... │  │
│  └─────────────────────────────────────────────┬──────────────────────────────────────────────┘  │
│                                                │ Commit Layer Tree                               │
│  ┌─────────────────────────────────────────────▼──────────────────────────────────────────────┐  │
│  │ COMPOSITOR THREAD                                                                          │  │

```

### 1.1 The Full Rendering Pipeline

When execution occurs on the main thread, changes cascade sequentially through the rendering pipeline:

```text
JavaScript / Tasks
       ↓
Microtasks Execution (Promises, MutationObserver)
       ↓
requestAnimationFrame (rAF) Callbacks
       ↓
Style Calculation (Recalculate Style) ── Computes cascade, specificity, and CSSOM
       ↓
Layout (Reflow)                      ── Computes geometric boundaries, dimensions, and page flow
       ↓
Pre-Paint (Property Trees)           ── Builds transform, clip, effect, and scroll trees
       ↓
Paint (Rasterization Records)        ── Generates draw calls (fills, borders, text, vector paths)
       ↓
Commit                               ── Transfers layer tree & property trees to Compositor Thread
       ↓
Tiling & GPU Rasterization           ── GPU worker threads execute draw records to generate bitmaps
       ↓
Draw Layers & Compositing            ── Merges GPU quads into the final frame buffer
```

#### Pipeline Invalidation Types
- **Layout Invalidation**: Modifying geometry properties (`width`, `height`, `margin`, `top`, `left`, `font-size`) forces the pipeline to run **Layout $\rightarrow$ Pre-Paint $\rightarrow$ Paint $\rightarrow$ Commit $\rightarrow$ Composite**. If uncontained, this recalculation walks up to the document root and down to all siblings and descendants.
- **Paint Invalidation**: Modifying visual properties without geometric changes (`background-color`, `box-shadow`, `color`) skips Layout, running **Paint $\rightarrow$ Commit $\rightarrow$ Composite**.
- **Compositor Invalidation**: Modifying compositor-friendly properties (`transform`, `opacity`) skips Style recalculation on the main thread entirely once promoted to a dedicated layer, running purely on the **Compositor Thread $\rightarrow$ GPU Process**.

---

### 1.2 Hardware Refresh Rates and Frame Budgets

The physical display refresh rate defines the hard ceiling for frame execution. Exceeding this budget causes the compositor to miss the v-sync deadline, resulting in visual jank (dropped frames).

$$\text{Frame Budget Total} = \frac{1000\text{ ms}}{\text{Refresh Rate (Hz)}}$$

Because the browser requires $\approx 4\text{ to }6\text{ ms}$ for internal overhead (input event processing, IPC serialization, compositor commits, and GPU driver handoffs), the actual budget available for main-thread code execution is strictly bounded:

| Refresh Rate | Frame Budget Total | Safe Main-Thread Budget | Target Performance Profile |
| :--- | :--- | :--- | :--- |
| **60 Hz** | $16.67\text{ ms}$ | $\le 10.0\text{ ms}$ | Standard Desktop / Legacy Mobile |
| **90 Hz** | $11.11\text{ ms}$ | $\le 6.5\text{ ms}$ | Modern Mid-Tier Mobile Displays |
| **120 Hz** | $8.33\text{ ms}$ | $\le 4.0\text{ ms}$ | High-End Mobile / Pro Desktops |
| **144 Hz** | $6.94\text{ ms}$ | $\le 3.0\text{ ms}$ | High-Refresh Gaming Displays |

---

### 1.3 The 50ms Long Task Boundary & Core Web Vitals

A **Long Task** is defined as any continuous main-thread script execution exceeding **$50\text{ ms}$**. 

```text
User Event (Click/Tap)
       │
       ▼
┌────────────────────────────────────────────────────────┐
│ Main Thread: Busy with 120ms Long Task                 │ ── User input is queued; cannot be processed
└────────────────────────────────────────────────────────┘
       │
       ▼ (120ms Delay)
┌───────────────────────────────────────────┐
│ Input Handler Dispatched (8ms)            │
├───────────────────────────────────────────┤
│ Style Recalc + Layout + Paint (18ms)      │
└───────────────────────────────────────────┘
       │
       ▼
Next Frame Presented ── Total INP = 120ms + 8ms + 18ms = 146ms (Poor Responsiveness)
```

The $50\text{ ms}$ threshold is derived from the **RAIL model**:
1. User input feels instant if a visual response is committed within **$100\text{ ms}$**.
2. Processing the input, updating DOM state, and rendering the next frame requires up to **$50\text{ ms}$**.
3. Therefore, background script execution cannot exceed $50\text{ ms}$ without delaying queued input events beyond the $100\text{ ms}$ latency threshold.

#### The Performance Metrics
- **Interaction to Next Paint (INP)**: The primary Core Web Vital for responsiveness. INP measures the longest latency between a user interaction (tap, click, keydown) and the presentation of the next visual frame. Mitigating INP requires breaking up long tasks and avoiding forced reflows in input handlers.
- **Largest Contentful Paint (LCP)**: Measures render speed for the largest visible element (typically hero images, text blocks, or banners). Driven by network discovery, resource priorities, and render-blocking CSS/JS.
- **Cumulative Layout Shift (CLS)**: Measures visual stability. Caused by unsized media, dynamic injections, and layout collapsing from improper render-skipping configurations.

---

### 1.4 The Four Performance Pillars

All web performance optimizations fall into one of four categories:

1. **Do Less Work**: Eliminate rendering and computation for offscreen or irrelevant content (`content-visibility`, `IntersectionObserver`, bundle-splitting).
2. **Limit/Restrict Work**: Isolate the impact of changes so they don't trigger global recalculations across the DOM tree (`contain`, isolated components).
3. **Change Cheaply**: Route updates through compositor-only pipelines instead of the layout and paint engines (`transform`, `opacity`, CSS transitions).
4. **Schedule & Offload Surgically**: Move heavy computations off the main thread entirely, or slice tasks so they yield to incoming input events (`Web Workers`, `OffscreenCanvas`, `scheduler.yield()`, `scheduler.postTask()`).

# Part 2: CSS Rendering Optimization & Containment Engine

CSS containment gives the browser mathematical proof that an element's subtree is isolated from the rest of the page, allowing the engine to optimize layout and paint calculations.

```css
contain: none | strict | content | [ size || inline-size || layout || style || paint ]
```

---

### 2.1 The Containment Primitives

#### `contain: layout`
Asserts that the element’s internal layout is isolated from the rest of the document:
- Descendants cannot cause reflows that affect external ancestors or siblings.
- Margin collapsing stops at the boundary of the contained element.
- Establishes a **new containing block** for both `position: absolute` and `position: fixed` descendants.
- Establishes an independent stacking context.
- **When to use**: Independent UI components, cards, widgets, and dynamic panels subject to frequent internal DOM mutations.

#### `contain: paint`
Asserts that no descendant will ever paint outside the element’s bounding box:
- Descendants are clipped strictly to the element’s padding box.
- If the element is entirely offscreen, the browser can skip rasterizing and painting its descendants.
- Establishes a **new containing block** for `position: absolute` and `position: fixed` descendants.
- Establishes an independent stacking context.
- **Gotchas**: Clips overflowing UI such as tooltips, context menus, and exterior box-shadows.

#### `contain: size`
Asserts that the element’s size can be determined without inspecting any of its descendants:
- The element lays out **as if its content were completely empty**.
- Child nodes do not contribute to parent width or height calculations.
- **Critical Risk**: Unless explicit dimensional rules (`width`, `height`, `inline-size`, `block-size`) or `contain-intrinsic-size` are set, an element with `contain: size` will **collapse to 0 height/width**.
- **When to use**: Static-dimension banners, ad slots, and canvas/chart wrappers.

#### `contain: inline-size`
One-dimensional size containment:
- The *inline* size (width in horizontal writing modes) is computed independently of descendants, but the *block* size (height) continues to be derived from children.
- This serves as the foundation for Container Queries (`container-type: inline-size`).

#### `contain: style`
Scopes the reach of counters and quotes:
- CSS counters (`counter-increment`, `counter-reset`) and typographical quotes are scoped strictly to the element's subtree.
- **Common Misconception**: `contain: style` **does not** scope CSS rules, classes, or selectors. It does not provide scoped styling like Shadow DOM or `@scope`.

---

### 2.2 Shorthand Containment Values

#### `contain: content`
Shorthand for:
```css
contain: layout paint style;
```
- The safest general-purpose isolation declaration.
- Omits `size` containment, allowing the element to scale naturally based on its children's height.
- Clips visual overflow (`paint`) and creates an absolute/fixed containing block.

#### `contain: strict`
Shorthand for:
```css
contain: size layout paint style;
```
- Maximum possible isolation.
- Demands explicit dimensions or `contain-intrinsic-size`; otherwise, the container will collapse to zero dimensions.

```css
/* Repeating card: safe, isolated, auto-expanding height */
.card-item {
  contain: content;
}

/* Explicit embed slot: maximum performance, strictly sized */
.ad-slot-300x250 {
  contain: strict;
  width: 300px;
  height: 250px;
}
```

---

### 2.3 Containment Gotchas & Edge Cases

1. **Trapped Overlays**: Because `layout`, `paint`, `content`, and `strict` establish a new containing block for `position: fixed` elements, any descendant modal, tooltip, or flyout will anchor to the *contained element* rather than the viewport.
2. **Clipped Dropdowns**: Applying `contain: paint` or `contain: content` to a card that houses a custom `<select>` dropdown will clip the dropdown menu at the card boundary. Use `contain: layout style` when overflow must remain visible.

---

### 2.4 Render-Skipping: `content-visibility`

`content-visibility` allows user agents to skip layout and painting for elements that are not currently relevant to the user, providing significant performance gains on long, content-heavy pages.

```css
content-visibility: visible | hidden | auto;
```

```text
                  content-visibility: auto
                             │
            ┌────────────────┴────────────────┐
            ▼                                 ▼
      [ Offscreen ]                     [ In Viewport ]
  (Subtree rendering skipped)         (Subtree rendered)
  - Layout: Skipped                   - Layout: Evaluated
  - Paint: Skipped                    - Paint: Evaluated
  - Containment: Active               - Containment: Active
    (layout, paint, style, size)        (layout, paint, style)
```

#### Values & Operational Mechanics
- `visible`: Normal rendering. Subtree is styled, laid out, and painted without containment modifications.
- `hidden`: Complete rendering skip. Descendant layout, paint, and rasterization are skipped. The element retains internal state (scroll position, input values, focus history), but is removed from accessibility trees and Find-in-Page search.
- `auto`: Dynamic skipping based on viewport proximity.
  - **When Offscreen**: Applies layout, paint, style, and **size containment**. Descendant layout and paint are skipped.
  - **When Near Viewport**: Drops size containment and runs layout and paint operations before the user scrolls the element into view.
  - **Intersection Margin**: Engines determine relevance using a viewport margin. The suggested default is **50% of the viewport dimension**, but this threshold is adaptive. Do not assume intersection triggers at the exact pixel edge of the screen.
  - **Accessibility & Search**: Unlike `hidden`, elements marked `auto` **remain in the accessibility tree** and remain searchable via browser Find-in-Page (Ctrl+F). When a search match occurs, the browser auto-renders the section and scrolls it into view.

---

### 2.5 Sizing Placeholders: `contain-intrinsic-size`

When `content-visibility: auto` skips an element's rendering offscreen, size containment is applied. Without an intrinsic size, the element treats its content as empty and **collapses to zero height**. As the user scrolls down:

1. Offscreen elements sit with `height: 0px`.
2. As an element enters the viewport margin, layout runs and the element expands to its real height (e.g., `740px`).
3. This dynamic height expansion shifts subsequent content down, causing scrollbar instability and high Cumulative Layout Shift (CLS).

`contain-intrinsic-size` provides a placeholder dimension that the browser uses while the element's subtree is skipped.

```css
/* Shorthand: sets both axes to 600px */
contain-intrinsic-size: 600px;

/* Explicit width (1000px) and height (600px) */
contain-intrinsic-size: 1000px 600px;

/* Logical property: Block axis placeholder (height in horizontal writing modes) */
contain-intrinsic-block-size: 700px;

/* Dynamic caching pattern: Auto-remembers actual rendered size */
contain-intrinsic-block-size: auto 700px;

/* The 'auto none' pattern for Grid/Multicol items */
contain-intrinsic-size: auto none;
```

#### The `auto <length>` Sizing Lifecycle
1. **First Render**: The browser uses the provided length (`700px`) as a placeholder while the element is offscreen.
2. **First Intersection**: The element enters the viewport margin, size containment drops, and full layout runs (e.g., calculating an actual height of `732px`).
3. **Subsequent Scrolls**: When the element scrolls far offscreen again, the browser **remembers the measured `732px`** and uses it as the placeholder instead of the original `700px` fallback.

#### The `auto none` Sizing Variant
If declared as `auto none`, the element has no initial intrinsic size (collapsing to `0px` if empty), but caches its rendered size after its first layout pass. This is useful in multi-column and grid layouts where arbitrary initial placeholder sizes might otherwise distort column balancing.

### 2.6 The `contentvisibilityautostatechange` Event

When an element with `content-visibility: auto` transitions between being skipped and being rendered, the engine fires a `contentvisibilityautostatechange` event. This provides a clean way to start and stop resource-intensive JavaScript loops without manual scroll tracking:

```js
const chartElement = document.querySelector('.webgl-chart');

chartElement.addEventListener('contentvisibilityautostatechange', (event) => {
  if (event.skipped) {
    // Subtree is now skipped: pause animation and processing loops
    pauseWebGLWorker();
  } else {
    // Subtree is active: resume animation and rendering
    resumeWebGLWorker();
  }
});
```

---

### 2.7 Discrete Animations with `@starting-style`

Because `content-visibility` is a discrete property, animating it historically required coordinating CSS transitions with JavaScript timeouts. Modern browsers support discrete property transitions using `transition-behavior: allow-discrete` paired with `@starting-style`:

```css
.flyout-panel {
  content-visibility: hidden;
  opacity: 0;
  transform: translateY(20px);
  transition: 
    opacity 300ms ease,
    transform 300ms ease,
    content-visibility 300ms;
  transition-behavior: allow-discrete;
}

.flyout-panel.is-active {
  content-visibility: visible;
  opacity: 1;
  transform: translateY(0);
}

/* Defines entry styles for elements entering the DOM or changing display/visibility */
@starting-style {
  .flyout-panel.is-active {
    opacity: 0;
    transform: translateY(20px);
  }
}
```

When transitioning to `content-visibility: hidden`, the engine holds the element in the `visible` state until the `opacity` and `transform` transitions finish, then applies `content-visibility: hidden`.

### 2.8 Accessible Deferral: `hidden="until-found"`

To keep collapsed content hidden by default while preserving accessibility for Find-in-Page searches and fragment links, use the HTML `hidden="until-found"` attribute instead of manual CSS hiding:

```html
<section class="accordion">
  <button id="accordion-trigger" aria-expanded="false" onclick="toggle()">Read More</button>
  <div id="accordion-content" hidden="until-found">
    Searchable content that remains unrendered until matched via Ctrl+F.
  </div>
</section>
```

#### Mechanics and the `beforematch` Event
Under the hood, `hidden="until-found"` applies `content-visibility: hidden` with special matching rules. When a user runs a page search or navigates to an anchor linking inside the element:
1. The engine locates the search match within the skipped DOM tree.
2. The engine fires the `beforematch` event on the target element.
3. The engine automatically removes the `hidden="until-found"` attribute, setting `content-visibility: visible`.
4. The browser scrolls to and highlights the matched phrase.

```js
const content = document.querySelector('#accordion-content');
const trigger = document.querySelector('#accordion-trigger');

content.addEventListener('beforematch', () => {
  // Synchronize UI state when the browser auto-reveals the content
  trigger.setAttribute('aria-expanded', 'true');
});
```

*Note: Once revealed via `beforematch`, the element remains visible even if the user clears their search query.*

### 2.9 Compositor Optimization: `will-change`

`will-change` serves as a hint to notify the browser of upcoming property changes, allowing it to prepare optimizations (such as layer promotion) before an animation begins.

```css
will-change: auto | scroll-position | contents | <custom-ident>;
```

#### Critical Specification Rules
1. **It is a Hint, Not a Command**: Engines can and will ignore `will-change` under memory pressure.
2. **No Guaranteed GPU Promotion**: The specification gives engines flexibility in how they handle hints; layer promotion is an implementation detail, not a requirement.
3. **Semantic Side-Effects**:
   - `will-change: transform` and `will-change: opacity` create a **new stacking context**.
   - `will-change: transform` turns the element into a **containing block** for all descendants, including `position: fixed` elements.

#### The VRAM Consumption Model
Every composited layer consumes dedicated physical GPU memory (VRAM):

$$\text{Layer VRAM} \approx \text{Width} \times \text{Height} \times 4\text{ bytes (RGBA)} \times (\text{Device Pixel Ratio})^2$$

*Example*: Promoting a $1200 \times 800$ card on a modern mobile device with a $3\times$ DPR:
$$\text{VRAM} = 1200 \times 800 \times 4 \times 3^2 = 34,560,000\text{ bytes} \approx 34.56\text{ MB}$$

Adding `will-change: transform` to 20 cards on that page allocates nearly **$700\text{ MB}$ of VRAM**, often triggering layer-tree thrashing, blurry text rendering, and browser tab crashes on lower-end devices.

#### The Surgical Lifecycle Rule
Do not declare `will-change` permanently in stylesheets. Apply it right before the interaction, and remove it as soon as the animation completes:

```js
const sheet = document.querySelector('.bottom-sheet');

function openSheet() {
  // 1. Alert the compositor ahead of the transition
  sheet.style.willChange = 'transform, opacity';

  // 2. Wait two frames to give the engine time to construct and upload the layer
  requestAnimationFrame(() => {
    requestAnimationFrame(() => {
      sheet.classList.add('is-visible');
    });
  });
}

// 3. Drop the layer when the animation completes to free VRAM
sheet.addEventListener('transitionend', (e) => {
  if (e.target === sheet) {
    sheet.style.willChange = 'auto';
  }
}, { once: true });
```

#### Predictive Lead-Time via Hover
Declaring `will-change` in the exact same frame as the animation starts provides zero setup time for the compositor. If JavaScript orchestration is unfeasible, use predictive CSS targeting:

```css
/* Warm up the child layer when hovering the parent card */
.card-container:hover .action-drawer {
  will-change: transform;
}

.action-drawer:active {
  transform: translateY(0);
}
```

### 2.10 Compositing & Legacy Hacks

#### `translateZ(0)` vs `will-change: transform`
- `transform: translateZ(0)` / `translate3d(0,0,0)`: A legacy hack used to force layer promotion. It permanently allocates GPU memory and cannot be dropped dynamically under memory pressure.
- `will-change: transform`: The standardized hint. It allows browsers to allocate resources adaptively and reclaim memory when needed.
- **Modern Rule**: Avoid using `translateZ(0)`. Modern engines automatically promote elements during active CSS transitions and keyframe animations on `transform` and `opacity`. Reserve manual layer promotion for resolving verified, engine-specific rendering bugs (such as fixed headers flickering during rapid trackpad scrolling in WebKit).

#### Stacking and Clipping Primitives
- `backface-visibility: hidden`: Controls visibility during 3D rotations. It has no effect on 2D surfaces and should not be used as a general performance optimization.
- `isolation: isolate`: Creates a new stacking context to scope `mix-blend-mode` effects without triggering GPU layer promotion.
- `overflow: clip`: Clips content without creating a scroll container. This avoids the memory overhead of tracking scroll offsets required by `overflow: hidden`.

# Part 3: JavaScript Observers & Event Decoupling

Observer APIs move DOM measurements and visibility tracking off the main thread, replacing expensive polling and scroll listeners with asynchronous, browser-scheduled callbacks.

---

### 3.1 `IntersectionObserver`: Visibility Tracking

Reports changes in the intersection of a target element with an ancestor container or the top-level viewport.

```js
const observer = new IntersectionObserver(
  (entries, obs) => {
    for (const entry of entries) {
      if (!entry.isIntersecting) continue;
      
      const target = entry.target;
      target.src = target.dataset.src;
      obs.unobserve(target); // Stop tracking once loaded
    }
  },
  {
    root: null, // Uses the browser viewport
    rootMargin: '200px 0px', // Lookahead margin to trigger loading before visible
    threshold: 0.01 // Triggers as soon as a single pixel intersects
  }
);
```

#### Core Options
- `root`: The ancestor element used as the bounding box for intersection checks. Defaults to the browser viewport if set to `null`.
- `rootMargin`: Offsets applied to the root's bounding box. A positive value (e.g., `'300px'`) acts as a lookahead margin, firing callbacks *before* elements scroll into view.
- `threshold`: A single number or array of numbers between `0.0` and `1.0`, defining the percentage of target visibility required to trigger the callback (e.g., `[0, 0.5, 1.0]`).
- `trackVisibility`: A specialized flag (requiring a `delay` parameter) that verifies the target isn't obscured by other elements, filters, or transforms. Useful for ad-viewability tracking, but adds measurement overhead.

#### Use Cases
- Lazy-loading non-critical resources, video posters, and third-party widgets.
- Triggering infinite scroll boundaries using a sentinel element at the bottom of the list.
- Pausing canvas and WebGL render loops when components are scrolled offscreen.
- Tracking analytics impressions and scroll-synced navigation highlights.

#### Operational Rules
- Call `unobserve(target)` immediately after one-time actions (like lazy-loading) to prevent the callback from running on subsequent scroll events.
- For standard images and iframes, prefer native `loading="lazy"` over custom observers. Use `IntersectionObserver` when you need to run custom logic, like initializing complex components or loading multi-part assets.

---

### 3.2 `ResizeObserver`: Content-Rect Tracking

Monitors element size changes driven by CSS Grid, Flexbox, font loading, or window resizing.

```js
const ro = new ResizeObserver((entries) => {
  for (const entry of entries) {
    // Read the inline-size from the contentBoxSize array
    const inlineSize = entry.contentBoxSize[0]?.inlineSize 
      ?? entry.contentRect.width;
      
    updateResponsiveVisualizations(entry.target, inlineSize);
  }
});

ro.observe(document.querySelector('.chart-viewport'));
```

#### The Feedback Loop Error
A common error with `ResizeObserver` is:
`ResizeObserver loop completed with undelivered notifications.`

This happens when a `ResizeObserver` callback alters the size of an observed element, triggering another resize notification in the same frame. The engine breaks the cycle to prevent an infinite loop, throwing a warning.

```js
// ❌ DANGEROUS: Direct style mutation inside callback can trigger a loop error
const ro = new ResizeObserver((entries) => {
  for (const entry of entries) {
    if (entry.contentRect.width < 500) {
      entry.target.classList.add('compact'); // Modifies layout immediately
    }
  }
});

// ✅ STABLE: Defers layout-altering mutations to the next frame
const ro = new ResizeObserver((entries) => {
  requestAnimationFrame(() => {
    for (const entry of entries) {
      if (entry.contentRect.width < 500) {
        entry.target.classList.add('compact');
      }
    }
  });
});
```

---

### 3.3 `MutationObserver`: Structural DOM Tracking

Batches and monitors mutations made to the DOM tree (node insertions, deletions, attribute changes).

```js
const mo = new MutationObserver((mutationsList, observer) => {
  for (const mutation of mutationsList) {
    if (mutation.type === 'childList') {
      mutation.addedNodes.forEach((node) => {
        if (node.nodeType === Node.ELEMENT_NODE && node.matches('.third-party-ad')) {
          sanitizeExternalWidget(node);
        }
      });
    }
  }
});

mo.observe(document.getElementById('injected-content-container'), {
  childList: true,
  subtree: true,
  attributes: false,
  characterData: false
});
```

#### Rules of Use
1. **Never Track Sizes via Attributes**: Do not watch `class` or `style` mutations to detect element resizing. Use `ResizeObserver` instead.
2. **Limit Observation Scope**: Avoid attaching observers with `subtree: true` to `document.body`. This adds overhead during large DOM updates. Scope observations to the specific container element being modified.
3. **Always Disconnect**: Call `observer.disconnect()` when unmounting components to avoid retaining memory references to detached DOM nodes.

### 3.4 `PerformanceObserver`: Frame & Task Telemetry

Subscribes directly to browser performance metrics, providing access to telemetry on Long Tasks, Core Web Vitals, and frame timings.

// Listen for Long Tasks (>= 50ms)
const longTaskObserver = new PerformanceObserver((list) => {

# Part 4: Task Scheduling & Event Loop Orchestration

Managing main-thread work requires scheduling scripts across appropriate queues to prevent blocking input handling and visual frame updates.

```text
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                        MACROTASKS (Task Queue / Timer Queue)                          │
│  setTimeout  •  setInterval  •  postMessage  •  Network I/O Callback                   │
└───────────────────────────────────────────┬────────────────────────────────────────────┘
                                            │ Pops 1 Task
                                            ▼
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                        MICROTASK QUEUE (Runs to completion)                            │
│  Promises (.then/catch/finally)  •  queueMicrotask  •  MutationObserver                │
└───────────────────────────────────────────┬────────────────────────────────────────────┘
                                            │ Drains completely
                                            ▼
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                     ANIMATION FRAME QUEUE (Runs prior to Paint)                        │
│  requestAnimationFrame callbacks                                                       │
└───────────────────────────────────────────┬────────────────────────────────────────────┘
                                            │ Runs
                                            ▼
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                      RENDERING ENGINE (Style Recalc ──► Layout ──► Paint)             │
└───────────────────────────────────────────┬────────────────────────────────────────────┘
                                            │ Idle?
                                            ▼
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                        IDLE QUEUE (Runs only if time remains)                          │
│  requestIdleCallback                                                                   │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

---

### 4.1 Scheduling APIs Compared

| API | Execution Window | Best Use Case | Primary Hazard |
| :--- | :--- | :--- | :--- |
| `requestAnimationFrame` | Right before Style/Layout/Paint | Visual animations, coordinating DOM reads/writes | Runs on every frame; can cause jank if work takes too long |
| `requestIdleCallback` | During unallocated time between frames | Non-critical logging, pre-fetching, telemetry | Can be delayed indefinitely under sustained load; never mutate DOM |
| `scheduler.postTask()` | Prioritized queue (`user-blocking`, `user-visible`, `background`) | Priority-based task scheduling | Needs polyfills or feature detection in older browsers |
| `scheduler.yield()` | Yields to main thread, resumes as high-priority task | Slicing synchronous loops to keep the main thread responsive | Requires feature detection |
| `queueMicrotask` | Immediately after the current script run, before any rendering | Coordinating internal async state | Drains continuously; can block rendering and cause UI freezes |

---

### 4.2 Slicing Long Loops: `scheduler.yield()`

Long synchronous loops block the main thread, delaying input processing and dropping frame rates. Use `scheduler.yield()` to break loops into smaller chunks that yield back to the browser between iterations:

```js
async function processLargeDataset(items) {
  for (let i = 0; i < items.length; i++) {
    processIndividualItem(items[i]);

    // Yield control periodically to allow input handling and rendering
    if (i % 50 === 0) {
      if ('scheduler' in window && 'yield' in scheduler) {
        await scheduler.yield(); // Modern: resumes at top of priority queue
      } else {
        // Fallback: yields via macrotask queue
        await new Promise((resolve) => setTimeout(resolve, 0));
      }
    }
  }
}
```

---

### 4.3 Explicit Priority: `scheduler.postTask()`

Modern engines provide unified priority queues via the `postTask` API, replacing combinations of `setTimeout`, `postMessage`, and `requestIdleCallback`:

```js
if ('scheduler' in window && 'postTask' in scheduler) {
  // 1. High-priority task needed for direct user response
  scheduler.postTask(() => renderDirectFeedback(), { priority: 'user-blocking' });

  // 2. Default task for standard UI updates
  scheduler.postTask(() => updateSecondaryMetrics(), { priority: 'user-visible' });

  // 3. Low-priority task that yields to all other work
  const abortController = new AbortController();
  scheduler.postTask(() => sendTelemetryData(), {
    priority: 'background',
    delay: 2000,
    signal: abortController.signal
  });
}
```

---

### 4.4 `requestIdleCallback`: Rules for Background Tasks

`requestIdleCallback` runs tasks only when the engine has spare time within a frame period, making it ideal for non-critical work:

```js
function processBackgroundAnalytics(dataQueue) {
  requestIdleCallback((deadline) => {
    // Process items while time remains in the frame
    while ((deadline.timeRemaining() > 1 || deadline.didTimeout) && dataQueue.length > 0) {
      sendTelemetryChunk(dataQueue.shift());
    }

    if (dataQueue.length > 0) {
      // Re-queue remaining items if work is still pending
      processBackgroundAnalytics(dataQueue);
    }
  }, { timeout: 2000 }); // Hard timeout to force execution if the thread is busy
}
```

#### Critical Rules
1. **Never Mutate the DOM**: Calling DOM mutations inside an idle callback can trigger unscheduled style recalculations and reflow passes right at the end of the frame lifecycle. Use idle time to compute data, then apply DOM changes inside `requestAnimationFrame`.
2. **Do Not Rely on It for Critical Logic**: If the page is experiencing sustained interaction load, idle callbacks can be postponed indefinitely. Do not place application state updates or critical user logic inside `requestIdleCallback`.

---

### 4.5 The rAF $\rightarrow$ `setTimeout` Pattern for Low INP

When an interaction needs to trigger heavy computations, running that work synchronously inside the event listener will freeze the main thread and delay the initial feedback frame. Wrapping the heavy work in `requestAnimationFrame` followed by `setTimeout` allows the browser to paint an interim loading or active state first:

```js
button.addEventListener('click', () => {
  // 1. Update UI immediately to show active state
  button.classList.add('is-processing');

  // 2. Queue the heavy work after the browser presents the updated frame
  requestAnimationFrame(() => {
    // Paints the visual update first...
    setTimeout(() => {
      // ...then executes the heavy work in the subsequent task
      runHeavyProcessingAlgorithm();
      button.classList.remove('is-processing');
    }, 0);
  });
});
```

---

### 4.6 Passive Listeners & Event Hygiene

#### Passive Event Listeners
Browsers must wait for `touchstart`, `touchmove`, and `wheel` listeners to finish running to check if `event.preventDefault()` is called. This adds latency and can cause visible scroll jank.

```js
// ❌ ADDS SCROLL DELAY: Browser must wait for execution to check preventDefault
window.addEventListener('touchmove', handleTouch);

// ✅ FAST SCROLLING: Informs the compositor that the scroll will not be canceled
window.addEventListener('touchmove', handleTouch, { passive: true });
```
*Note: Modern browsers default root-level (`window`, `document`, `document.body`) touch and wheel listeners to `passive: true`. However, listeners added to custom scroll containers must still be configured explicitly.*

#### Debouncing vs. Throttling
- **Debounce**: Delays execution until events have stopped firing for a specified wait time. Best for discrete actions like search-as-you-type inputs or handling the end of a window resize.
- **Throttle**: Enforces a maximum execution rate, running once every $N$ milliseconds. Best for continuous interactions like scroll progress tracking or drag interactions.

```js
// rAF-coupled throttle: Syncs updates with the display refresh rate
function throttleToFrame(fn) {
  let isTicking = false;
  return (...args) => {
    if (isTicking) return;
    isTicking = true;
    requestAnimationFrame(() => {
      fn(...args);
      isTicking = false;
    });
  };
}

window.addEventListener('scroll', throttleToFrame(() => {
  updateScrollProgressBar();
}), { passive: true });
```

# Part 5: Multi-Threading: Web Workers & OffscreenCanvas

Moving heavy computation off the main thread is the most effective way to protect frame rates and keep input latency low.

```text
┌────────────────────────────────────────────────┐  postMessage (Copy / Structured Clone)  ┌────────────────────────────────────────────────┐
│ MAIN THREAD                                    │ ──────────────────────────────────────► │ DEDICATED WEB WORKER                           │
│  • Input Dispatch                              │                                         │  • Heavy Math / Parsing / Filtering            │
│  • DOM Tree & Styling                          │ ◄────────────────────────────────────── │  • Zero Access to DOM Tree                     │
│  • Style / Layout / Paint                      │  postMessage (Data Payload)             │  • Cannot touch window / document              │
└────────────────────────────────────────────────┘                                         └────────────────────────────────────────────────┘
                         │
                         │ transferControlToOffscreen() (Zero-Copy Transfer)
                         ▼
┌───────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┐
│ OFFSCREENCANVAS PIPELINE                                                                                                                  │
│  Worker drives 2D / WebGL contexts directly ──► Renders at 60/120 FPS even when Main Thread is completely locked                          │
└───────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┘
```

---

### 5.1 Dedicated Web Workers

Web Workers execute in an isolated background thread without access to the DOM, `window`, or document APIs.

```js
// main.js
const worker = new Worker(new URL('./parser.worker.js', import.meta.url), { type: 'module' });

// Transfer large binary data using Transferable Objects (zero-copy memory handoff)
const largeBuffer = new ArrayBuffer(1024 * 1024 * 64); // 64MB buffer
worker.postMessage({ buffer: largeBuffer }, [largeBuffer]);

console.log(largeBuffer.byteLength); // 0 (Memory was transferred to worker)

worker.onmessage = (event) => {
  console.log('Processed metrics:', event.data.result);
};
```

```js
// parser.worker.js
self.onmessage = (event) => {
  const incomingBuffer = event.data.buffer;
  // Execute heavy CPU-bound parsing off the main thread
  const processedMetrics = executeDataCrunching(incomingBuffer);

  self.postMessage({ result: processedMetrics });
};
```

#### Transferable Objects
Passing data via `postMessage` creates a structured clone by default, which can introduce serialization overhead for large datasets. To avoid this, pass **Transferable Objects** (`ArrayBuffer`, `ImageBitmap`, `MessagePort`). Transferring moves the underlying memory pointer to the receiving thread, emptying the buffer on the original thread and avoiding memory duplication.

---

### 5.2 OffscreenCanvas: Thread-Independent Graphics

`OffscreenCanvas` decouples rendering from the DOM, allowing WebGL, WebGPU, and 2D canvas drawing routines to run on a background worker thread.

```js
// main.js - Canvas setup
const canvas = document.querySelector('#performance-chart');
// Transfer canvas rendering control to the worker
const offscreen = canvas.transferControlToOffscreen();

const renderWorker = new Worker(new URL('./chart.worker.js', import.meta.url), { type: 'module' });
renderWorker.postMessage({ canvasInstance: offscreen }, [offscreen]);
```

```js
// chart.worker.js - Render loop runs on background thread
self.onmessage = (event) => {
  const canvas = event.data.canvasInstance;
  const ctx = canvas.getContext('2d');

  function render(time) {
    ctx.clearRect(0, 0, canvas.width, canvas.height);
    drawVisualizations(ctx, time);

    // Workers support requestAnimationFrame for smooth frame delivery
    requestAnimationFrame(render);
  }
  requestAnimationFrame(render);
};
```

Because rendering runs entirely inside the worker, the canvas continues rendering at 60/120 FPS even if the main thread is blocked by heavy script execution elsewhere on the page.

### 6.3 Web Font Performance

Fonts can introduce layout shifts (CLS) and block text rendering (FOUT/FOIT). Use modern font loading controls to manage these trade-offs:

```css

  font-family: 'Inter Web';
  src: url('/fonts/inter-latin.woff2') format('woff2');

@font-face {

  src: local('Arial');
  size-adjust: 107%;
  ascent-override: 90%;
  descent-override: 22.5%;
  line-gap-override: 0%;
}

body {
  font-family: 'Inter Web', 'Inter Fallback', sans-serif;
}
```

### 8.1 Detecting Layout Thrashing
Layout thrashing (Forced Synchronous Layout) occurs when JavaScript reads geometric properties after writing DOM styles, forcing the browser to run layout synchronously during script execution.

```js
// ❌ FORCES REFLOW: Interleaved style reads and writes
cards.forEach(card => {
  const currentHeight = card.offsetHeight; // READ (Forces immediate synchronous layout)
  card.style.height = `${currentHeight + 10}px`; // WRITE (Invalidates current layout)
});

// ✅ BATCHED READS AND WRITES: Single layout pass
const heights = cards.map(card => card.offsetHeight); // Batch all READS
cards.forEach((card, index) => {
  card.style.height = `${heights[index] + 10}px`; // Batch all WRITES
});
```

In the **Performance Panel**, this appears as a series of purple layout blocks tagged with red warning flags: **`Forced Reflow`**.

#### Blueprint C: Yield-Slicing a CPU-Bound Process with Responsive Fallback

Breaks up intensive background tasks using cooperative multitasking, keeping the main thread responsive to user input:

```js
async function runYieldAwareCompute(dataItems, processCallback) {
  const total = dataItems.length;
  let lastYieldTime = performance.now();

  for (let i = 0; i < total; i++) {
    // Run the compute work
    processCallback(dataItems[i], i);

    // Check if we've worked for >16ms (exceeded safe budget)
    if (performance.now() - lastYieldTime > 16) {
      if ('scheduler' in window && 'yield' in scheduler) {
        // Modern: yields and resumes at top of priority queue
        await scheduler.yield();
      } else {
        // Fallback: yields via the task queue
        await new Promise(resolve => setTimeout(resolve, 0));
      }
      lastYieldTime = performance.now();
    }
  }
}
```
