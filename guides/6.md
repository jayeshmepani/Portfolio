# 1. Core Mental Model: How CSS Affects Performance

Browsers generally render a page using a pipeline similar to this:

```text
HTML/CSS/JS
  ↓
DOM + CSSOM
  ↓
Style calculation
  ↓
Layout
  ↓
Paint
  ↓
Compositing
  ↓
Pixels on screen
```

Different CSS properties affect different stages.

## Cheap operations

Usually cheaper, often compositor-friendly:

```css
transform: translate(10px, 10px);
transform: scale(1.1);
transform: rotate(5deg);
opacity: 0.5;
```

These can often be animated without triggering layout or paint every frame.

## Expensive operations

Usually more expensive because they can trigger layout and/or paint:

```css
width: 200px;
height: 300px;
top: 20px;
left: 40px;
margin: 16px;
padding: 24px;
font-size: 18px;
border-width: 2px;
box-shadow: 0 10px 30px rgba(0, 0, 0, 0.3);
background-position: center;
```

Animating these can cause jank, especially on mobile.

## Main performance goals

Good CSS optimization usually targets one or more of these:

1. Reduce downloaded CSS bytes.
2. Reduce render-blocking CSS.
3. Reduce style recalculation work.
4. Reduce layout/reflow work.
5. Reduce paint work.
6. Move work to the compositor.
7. Avoid layout shift.
8. Avoid excessive GPU memory usage.
9. Keep accessibility and SEO intact.

# 2. Quick Rules of Thumb

If you remember only these rules:

## `content-visibility`

Use:

```css
content-visibility: auto;
contain-intrinsic-size: auto 600px;
```

For large below-the-fold sections that are expensive to render.

Avoid:

```css
content-visibility: hidden;
```

unless you understand the accessibility, focus, SEO, and layout consequences.

## `will-change`

Use:

```css
will-change: transform;
```

only shortly before an animation starts, and remove it after the animation ends.

Avoid:

```css
* {
  will-change: transform;
}
```

This can destroy performance.

## `contain`

Use:

```css
contain: content;
```

or more specific containment for independent UI components.

Avoid:

```css
contain: size;
```

on elements whose height depends on children unless you explicitly set a size.

## Animations

Prefer:

```css
transform: translateX(20px);
opacity: 0;
```

Avoid animating:

```css
top;
left;
width;
height;
margin;
padding;
```

unless you have a specific reason and have measured it.

# 3. `content-visibility`

## 3.1 What `content-visibility` does

`content-visibility` lets you tell the browser that an element’s content can be skipped under certain conditions.

The main values are:

```css
content-visibility: visible;
content-visibility: hidden;
content-visibility: auto;
```

### `visible`

Default behavior. The element renders normally.

```css
.section {
  content-visibility: visible;
}
```

Use when you want normal rendering.

---

### `hidden`

The element’s content is skipped. It is somewhat similar in spirit to `display: none`, but not identical.

```css
.section {
  content-visibility: hidden;
}
```

Important differences:

- The element’s box can still exist.
- The content inside may not contribute to sizing unless you provide explicit size or `contain-intrinsic-size`.
- It is not the same as `visibility: hidden`.
- It is not the same as `display: none`.
- It can be useful when you want to keep an element in the layout tree but skip rendering its contents.

Use `content-visibility: hidden` carefully. For most hide/show UI, `display: none`, the `hidden` attribute, or `inert` are often safer and more predictable.

---

### `auto`

This is the most performance-useful value.

```css
.section {
  content-visibility: auto;
}
```

When the element is offscreen, the browser can skip rendering its contents. When it becomes visible, the browser renders it.

This is especially useful for long pages with many below-the-fold sections.

---

## 3.2 Why `content-visibility: auto` helps

For a long page, the browser normally has to do work for the entire DOM, even content far below the viewport.

With `content-visibility: auto`, the browser can skip:

- style work for skipped content,
- layout work for skipped content,
- paint work for skipped content,
- some subresource work depending on the content.

This can improve:

- initial page load,
- first paint,
- scroll performance,
- memory usage,
- long-task duration.

But it must be used carefully because skipped content can affect sizing, scrollbars, accessibility, search behavior, and anchor navigation.

---

## 3.3 The biggest problem: layout shift and scrollbar jumps

When offscreen content is skipped, the browser still needs to know how much space to reserve.

If you do not provide a size, the element may collapse or reserve an incorrect amount of space.

That can cause:

- layout shift,
- scrollbar jumps,
- broken anchor scrolling,
- poor user experience.

To fix this, use `contain-intrinsic-size`.

---

# 4. `contain-intrinsic-size`

## 4.1 What it does

`contain-intrinsic-size` provides a placeholder size for an element whose content is being skipped.

Example:

```css
.article-section {
  content-visibility: auto;
  contain-intrinsic-size: auto 600px;
}
```

This tells the browser:

> “If you skip this section, reserve approximately 600px of height.”

The `auto` keyword is useful because it lets the browser remember the last rendered size if available.

---

## 4.2 Syntax patterns

Simple:

```css
.card-list {
  content-visibility: auto;
  contain-intrinsic-size: auto 400px;
}
```

Width and height:

```css
.hero-panel {
  content-visibility: auto;
  contain-intrinsic-size: auto 800px auto 500px;
}
```

Logical properties:

```css
.comment-group {
  content-visibility: auto;
  contain-intrinsic-block-size: auto 500px;
}
```

Use logical properties when you want better writing-mode compatibility.

---

## 4.3 Choosing a good placeholder size

Use a size close to the real rendered size.

Good:

```css
.comments {
  content-visibility: auto;
  contain-intrinsic-size: auto 800px;
}
```

Bad if actual comments are 3000px tall:

```css
.comments {
  content-visibility: auto;
  contain-intrinsic-size: auto 100px;
}
```

If the placeholder is too small, the scrollbar may jump when the user scrolls.

If the content height varies heavily, consider:

- grouping content into more predictable chunks,
- using skeleton sizes,
- using virtualization for huge lists,
- setting explicit heights where appropriate.

# 5. Where to Use `content-visibility: auto`

## 5.1 Good use cases

### 1. Long article sections

```css
.article > section:not(.hero) {
  content-visibility: auto;
  contain-intrinsic-size: auto 700px;
}
```

Good for:

- long blog posts,
- documentation pages,
- terms and conditions,
- product descriptions,
- FAQ pages.

---

### 2. Comment sections

```css
.comments {
  content-visibility: auto;
  contain-intrinsic-size: auto 1200px;
}
```

Comments are often below the fold and can be DOM-heavy.

---

### 3. Related content

```css
.related-posts {
  content-visibility: auto;
  contain-intrinsic-size: auto 600px;
}
```

---

### 4. Large feeds with moderate item count

```css
.feed-group {
  content-visibility: auto;
  contain-intrinsic-size: auto 1000px;
}
```

For huge feeds, virtualization is usually better.

---

### 5. Heavy charts or SVG sections

```css
.chart-section {
  content-visibility: auto;
  contain-intrinsic-size: auto 480px;
}
```

This is useful when charts are expensive to paint but are below the fold.

You can combine this with lazy initialization:

```js
const chartSection = document.querySelector(".chart-section");

chartSection.addEventListener("contentvisibilityautostatechange", (event) => {
  if (!event.skipped && !chartSection.dataset.initialized) {
    initChart(chartSection);
    chartSection.dataset.initialized = "true";
  }
});
```

---

### 6. Heavy media galleries

```css
.gallery {
  content-visibility: auto;
  contain-intrinsic-size: auto 900px;
}
```

Still use:

```html
<img loading="lazy" decoding="async" width="800" height="450" alt="...">
```

`content-visibility` does not replace responsive images or lazy loading.

---

### 7. Below-the-fold e-commerce sections

Examples:

- reviews,
- specifications,
- Q&A,
- shipping details,
- recommended products.

```css
.product-reviews {
  content-visibility: auto;
  contain-intrinsic-size: auto 900px;
}
```

Do not apply it blindly to the main product gallery or buy box if those are above the fold and critical.

---

## 5.2 Safe progressive enhancement pattern

```css
@supports (content-visibility: auto) {
  .below-fold-section {
    content-visibility: auto;
    contain-intrinsic-size: auto 600px;
  }
}
```

If unsupported, the property is ignored.

# 6. When Not to Use `content-visibility`

## 6.1 Do not use on critical above-the-fold content

Avoid:

```css
.hero {
  content-visibility: auto;
}
```

if the hero contains:

- LCP image,
- main headline,
- primary CTA,
- important navigation.

Why?

It can delay rendering or introduce unnecessary complexity for content the user needs immediately.

---

## 6.2 Do not use without size placeholders

Bad:

```css
.section {
  content-visibility: auto;
}
```

Better:

```css
.section {
  content-visibility: auto;
  contain-intrinsic-size: auto 600px;
}
```

Without placeholders, you may get layout shift and scrollbar instability.

---

## 6.3 Do not use for tiny components

Bad:

```css
.button {
  content-visibility: auto;
}
```

The overhead is usually not worth it. `content-visibility` helps most on large containers with expensive content.

---

## 6.4 Do not use as a replacement for virtualization

For huge lists, virtualization is usually better.

Example:

```text
10,000 list items in DOM
```

`content-visibility: auto` can reduce rendering work, but the DOM still exists. That can still hurt:

- memory,
- style calculation,
- accessibility tree size,
- JavaScript queries,
- serialization,
- framework diffing.

For very large lists, use:

- virtual scrolling,
- pagination,
- incremental loading.

`content-visibility` can complement these, but it is not always a replacement.

---

## 6.5 Be careful with sticky and fixed elements

Avoid applying `content-visibility: auto` to:

```css
.sticky-header,
.fixed-sidebar,
.floating-widget
```

unless you test carefully.

Sticky and fixed positioning depend on continuous layout and intersection behavior. Skipping content can produce unexpected behavior.

Also be careful when sticky elements are inside skipped ancestors.

---

## 6.6 Be careful with focusable content

If skipped content contains focusable elements, do not assume keyboard behavior will always be perfect.

Use robust hiding techniques when needed:

```html
<div hidden>
  ...
</div>
```

or:

```html
<div inert>
  ...
</div>
```

or:

```css
.is-hidden {
  display: none;
}
```

If you use `content-visibility: hidden`, also consider accessibility implications.

---

## 6.7 Be careful with SEO-critical content

Content hidden with `content-visibility: hidden` may not be treated like normal visible content by all consumers.

For SEO-critical text, prefer visible rendering or standard accessible hiding patterns.

`content-visibility: auto` on below-the-fold supplemental content is generally safer, but test your specific requirements.

---

## 6.8 Be careful with printing

`content-visibility: auto` or `hidden` may affect printing because offscreen or hidden content may not render as expected.

Reset for print:

```css
@media print {
  * {
    content-visibility: visible !important;
  }
}
```

Or more targeted:

```css
@media print {
  .article-section {
    content-visibility: visible !important;
    contain-intrinsic-size: auto;
  }
}
```

# 7. `contentvisibilityautostatechange`

Elements with `content-visibility: auto` can fire an event when their skipped state changes.

```js
const section = document.querySelector(".lazy-section");

section.addEventListener("contentvisibilityautostatechange", (event) => {
  if (event.skipped) {
    console.log("Content is currently skipped/offscreen.");
  } else {
    console.log("Content is now relevant/rendered.");
  }
});
```

Useful for:

- lazy initialization,
- starting animations only when visible,
- loading heavy widgets,
- initializing charts,
- enabling observers.

Example:

```js
document.querySelectorAll("[data-lazy-widget]").forEach((widget) => {
  widget.addEventListener("contentvisibilityautostatechange", (event) => {
    if (!event.skipped && !widget.dataset.loaded) {
      loadWidget(widget);
      widget.dataset.loaded = "true";
    }
  });
});
```

Support varies, so use feature detection or treat this as progressive enhancement.

# 9. `will-change`

## 9.1 What `will-change` does

`will-change` tells the browser that an element is likely to change in a specific way soon.

```css
.modal {
  will-change: transform, opacity;
}
```

This gives the browser a hint to prepare resources before the change happens.

The browser may:

- promote the element to its own compositor layer,
- pre-allocate textures,
- prepare transform/opacity animation resources,
- reduce animation startup jank.

But it also costs:

- GPU memory,
- CPU memory,
- layer management,
- possible text blurring,
- possible stacking context changes,
- possible fixed-positioning issues.

---

## 9.2 Common values

```css
will-change: transform;
will-change: opacity;
will-change: transform, opacity;
will-change: scroll-position;
will-change: filter;
```

Most common in UI work:

```css
will-change: transform;
will-change: opacity;
will-change: transform, opacity;
```

---

## 9.3 Correct usage pattern

The correct lifecycle is:

```text
Add will-change shortly before animation
  ↓
Run animation
  ↓
Remove will-change after animation
```

Do not leave it on permanently unless you have measured and justified it.

---

## 9.4 Good use cases

### 1. Modal or dialog opening

```css
.modal.will-animate {
  will-change: transform, opacity;
}

.modal.is-open {
  transform: translateY(0);
  opacity: 1;
}
```

JavaScript:

```js
const modal = document.querySelector(".modal");

function openModal() {
  modal.classList.add("will-animate");

  requestAnimationFrame(() => {
    requestAnimationFrame(() => {
      modal.classList.add("is-open");
    });
  });
}

modal.addEventListener("transitionend", (event) => {
  if (event.target === modal) {
    modal.classList.remove("will-animate");
  }
});
```

---

### 2. Drawer or sidebar

```css
.drawer.will-move {
  will-change: transform;
}

.drawer.is-open {
  transform: translateX(0);
}
```

---

### 3. Dropdown or tooltip

```css
.menu.will-fade {
  will-change: opacity, transform;
}
```

But only if the menu is actually about to open.

---

### 4. Carousel slides

Use only for active or near-active slides:

```css
.carousel-slide.is-active,
.carousel-slide.is-next {
  will-change: transform;
}
```

Do not apply to all slides:

```css
.carousel-slide {
  will-change: transform;
}
```

That can waste memory.

---

### 5. Drag interactions

```css
.draggable.is-dragging {
  will-change: transform;
}
```

---

### 6. Hover effects where animation is predictable

CSS-only example:

```css
.card-media {
  transition: transform 200ms ease;
}

.card:hover .card-media {
  will-change: transform;
  transform: scale(1.05);
}
```

This is acceptable for simple effects, but for critical animations, adding `will-change` slightly earlier with JavaScript can be more reliable.

---

## 9.5 When to use `will-change`

Use it when all of these are true:

1. The element actually animates soon.
2. The animation is causing measurable jank or startup stutter.
3. The animated properties are compositor-friendly, such as `transform` or `opacity`.
4. The number of elements with `will-change` is limited.
5. You remove it when no longer needed.

---

## 9.6 When not to use `will-change`

### Do not use globally

Bad:

```css
* {
  will-change: transform;
}
```

This can massively increase memory usage and reduce performance.

---

### Do not use on static elements

Bad:

```css
.header {
  will-change: transform;
}
```

If the header does not animate soon, this is wasted work.

---

### Do not use on hundreds of list items

Bad:

```css
.list-item {
  will-change: transform;
}
```

If you have 500 list items, you may create hundreds of layers.

Better:

```css
.list-item.is-animating {
  will-change: transform;
}
```

---

### Do not use it to animate layout properties

Bad:

```css
.bad {
  will-change: top, left;
  transition: top 300ms, left 300ms;
}
```

Better:

```css
.good {
  will-change: transform;
  transition: transform 300ms;
  transform: translate(20px, 40px);
}
```

Animating `top` and `left` can trigger layout. `transform` can often be composited.

---

### Do not use it as a magic fix

If an animation janks because it animates `width`, `height`, `box-shadow`, or `background-position`, `will-change` may not solve the root problem.

Fix the property first:

```css
/* Bad */
.element {
  transition: width 300ms, height 300ms;
  will-change: width, height;
}

/* Better */
.element {
  transition: transform 300ms;
  transform: scale(1.2);
}
```

---

### Do not use `will-change: scroll-position` everywhere

```css
.scroller {
  will-change: scroll-position;
}
```

This can sometimes help scrolling performance, but it can also increase memory usage. Use only when measured and needed.

For long lists, prefer:

- virtualization,
- `content-visibility`,
- `contain`,
- simpler DOM.

---

## 9.7 Side effects of `will-change`

### 1. New stacking context

Some `will-change` values can create stacking contexts or affect stacking behavior.

This can change how `z-index` behaves.

Example issue:

```css
.parent {
  will-change: transform;
}
```

A child with `position: fixed` may no longer behave as expected relative to the viewport.

Test carefully.

---

### 2. Fixed positioning can break

A transformed ancestor can become the containing block for fixed-positioned descendants.

`will-change: transform` may produce similar behavior in some cases.

Avoid applying `will-change: transform` to ancestors of fixed elements unless tested.

---

### 3. Blurry text

Layer promotion can cause text to look blurry during transforms, especially when scaling.

If you see blurry text:

- avoid scaling text heavily,
- use SVG where appropriate,
- avoid unnecessary layer promotion,
- test on high-DPI and low-DPI screens.

---

### 4. Increased memory usage

Each promoted layer uses memory.

Too many layers can cause:

- memory pressure,
- crashes on low-end devices,
- slower compositing,
- battery drain.

---

## 9.8 Practical `will-change` removal pattern

```js
function animateElement(el, className) {
  el.classList.add("will-animate");

  requestAnimationFrame(() => {
    requestAnimationFrame(() => {
      el.classList.add(className);
    });
  });

  el.addEventListener(
    "transitionend",
    (event) => {
      if (event.target !== el) return;
      el.classList.remove("will-animate");
    },
    { once: true }
  );
}
```

CSS:

```css
.panel {
  transform: translateY(20px);
  opacity: 0;
  transition:
    transform 300ms ease,
    opacity 300ms ease;
}

.panel.is-open {
  transform: translateY(0);
  opacity: 1;
}

.panel.will-animate {
  will-change: transform, opacity;
}
```

---

## 9.9 `will-change` decision table

| Situation | Recommendation |
|---|---|
| Modal opening | Add `will-change: transform, opacity` before opening, remove after |
| Drawer sliding | Add `will-change: transform` before slide, remove after |
| Hover zoom | Can use on hover for simple effects |
| Infinite list items | Avoid on all items |
| Static header | Avoid |
| Global reset | Never |
| Animating `top/left` | Replace with `transform` first |
| Scroll performance | Try other fixes first; use `scroll-position` only if measured |
| Carousel with 100 slides | Apply only to active/near-visible slides |

# 10. CSS Containment: `contain`

CSS containment tells the browser that an element’s internals are isolated from the rest of the page.

This can reduce layout, style, and paint work.

---

## 10.1 Basic syntax

```css
.card {
  contain: layout paint style;
}
```

Or use shorthands:

```css
.card {
  contain: content;
}
```

```css
.banner {
  contain: strict;
}
```

---

## 10.2 Values

### `layout`

```css
contain: layout;
```

Isolates internal layout.

Useful when an element’s internal layout should not affect outside elements.

---

### `paint`

```css
contain: paint;
```

Prevents descendants from painting outside the element’s bounds.

Useful for cards, clips, bounded widgets.

Be careful: it can clip overflowing UI such as dropdowns, tooltips, popovers, and context menus.

---

### `style`

```css
contain: style;
```

Scopes certain style features such as counters.

Less commonly needed, but useful in component systems.

---

### `size`

```css
contain: size;
```

The element’s size can be calculated without considering descendants.

Dangerous if the element’s height depends on its children.

Use only when the element has an explicit size or you know what you are doing.

Good:

```css
.ad-slot {
  width: 300px;
  height: 250px;
  contain: size;
}
```

Bad:

```css
.auto-height-card {
  contain: size;
}
```

The card may collapse.

---

### `content`

```css
contain: content;
```

Equivalent to:

```css
contain: layout paint style;
```

This is often the safest useful containment value for components.

---

### `strict`

```css
contain: strict;
```

Equivalent to:

```css
contain: size layout paint style;
```

Use only for elements with known sizes.

---

## 10.3 Where to use `contain`

### Cards

```css
.card {
  contain: layout paint style;
}
```

Good if the card does not have overflowing dropdowns or tooltips.

---

### List items

```css
.feed-item {
  contain: layout style;
}
```

Use `paint` only if clipping is safe.

---

### Ad slots

```css
.ad-slot {
  width: 300px;
  height: 250px;
  contain: strict;
}
```

Excellent for preventing layout shift.

---

### Independent widgets

```css
.widget {
  contain: content;
}
```

Good for:

- calendars,
- forms,
- sidebars,
- comments,
- embedded modules.

---

### Dynamic components

If JavaScript frequently updates a widget, containment can reduce invalidation scope.

```css
.live-score-widget {
  contain: layout paint style;
}
```

---

## 10.4 When not to use `contain`

### Do not use `paint` on dropdown containers

Bad:

```css
.dropdown {
  contain: paint;
}
```

If the dropdown menu needs to overflow, it may be clipped.

Better:

```css
.dropdown {
  contain: layout style;
}
```

---

### Do not use `size` on auto-height elements

Bad:

```css
.comment {
  contain: size;
}
```

Better:

```css
.comment {
  contain: layout paint style;
}
```

Or:

```css
.comment {
  contain: content;
}
```

---

### Do not use `strict` unless size is known

Bad:

```css
.dynamic-panel {
  contain: strict;
}
```

Good:

```css
.fixed-banner {
  width: 320px;
  height: 100px;
  contain: strict;
}
```

# 11. `content-visibility` vs `contain`

They are related but different.

| Feature | Purpose |
|---|---|
| `content-visibility` | Skip rendering of content when not relevant |
| `contain` | Limit layout/style/paint invalidation scope |
| `contain-intrinsic-size` | Reserve size for skipped content |
| `will-change` | Prepare for upcoming changes/animations |

You can combine them, but do not overdo it.

Example:

```css
.article-section {
  content-visibility: auto;
  contain-intrinsic-size: auto 700px;
}

.article-section .card {
  contain: layout paint style;
}
```

Usually you do not need to add extra containment to an element that already has `content-visibility: auto`, because `content-visibility` implies strong containment behavior.

# 12. Animation Optimization

## 12.1 Prefer compositor-friendly properties

Best:

```css
.element {
  transition:
    transform 300ms ease,
    opacity 300ms ease;
}
```

Avoid:

```css
.element {
  transition:
    width 300ms ease,
    height 300ms ease,
    top 300ms ease,
    left 300ms ease;
}
```

---

## 12.2 Use `transform` instead of geometry

Move:

```css
/* Bad */
.box {
  top: 100px;
  left: 100px;
}
```

Better:

```css
.box {
  transform: translate(100px, 100px);
}
```

Scale:

```css
/* Bad */
.box {
  width: 200px;
  height: 200px;
}
```

Better:

```css
.box {
  transform: scale(1.2);
}
```

Rotate:

```css
.box {
  transform: rotate(45deg);
}
```

---

## 12.3 Use modern transform properties when useful

Modern CSS allows:

```css
.element {
  translate: 0 20px;
  scale: 1.05;
  rotate: 2deg;
}
```

These are often easier to compose and animate.

---

## 12.4 Avoid animating `box-shadow` directly

Animating `box-shadow` can be expensive because it often causes paint.

Bad:

```css
.card {
  transition: box-shadow 300ms ease;
}

.card:hover {
  box-shadow: 0 20px 60px rgba(0, 0, 0, 0.25);
}
```

Better pattern:

```css
.card {
  position: relative;
}

.card::after {
  content: "";
  position: absolute;
  inset: 0;
  border-radius: inherit;
  box-shadow: 0 20px 60px rgba(0, 0, 0, 0.25);
  opacity: 0;
  transition: opacity 300ms ease;
  pointer-events: none;
}

.card:hover::after {
  opacity: 1;
}
```

This animates opacity instead of shadow.

---

## 12.5 Avoid animating `background-position`

Bad:

```css
.hero {
  transition: background-position 1s ease;
}
```

Better approaches:

- use `transform` on a layered element,
- use two backgrounds and crossfade opacity,
- use SVG/CSS gradients carefully.

---

## 12.6 Avoid animating `filter` heavily

```css
.element {
  filter: blur(20px);
}
```

Filters can be GPU-accelerated but are still expensive, especially:

- blur,
- drop-shadow,
- large areas,
- mobile devices.

If you must animate filter:

- keep area small,
- test on low-end devices,
- consider pseudo-element opacity crossfade instead.

---

## 12.7 Avoid `backdrop-filter` on large areas

```css
.overlay {
  backdrop-filter: blur(20px);
}
```

This is expensive because it samples and processes what is behind the element.

Use alternatives:

```css
.overlay {
  background: rgba(20, 20, 20, 0.6);
}
```

If blur is required:

- use a small blur radius,
- limit the area,
- avoid animating it,
- test on mobile.

---

## 12.8 Avoid `mix-blend-mode` unless necessary

```css
.blend {
  mix-blend-mode: multiply;
}
```

Blend modes can force expensive compositing and paint work.

Use sparingly.

---

## 12.9 Avoid `background-attachment: fixed`

```css
body {
  background-image: url("bg.jpg");
  background-attachment: fixed;
}
```

This can cause serious scroll jank, especially on mobile.

Better:

- use a fixed-position decorative element,
- use `transform`-based parallax carefully,
- avoid parallax on low-end devices,
- respect `prefers-reduced-motion`.

---

## 12.10 Respect reduced motion

```css
@media (prefers-reduced-motion: reduce) {
  *,
  *::before,
  *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}
```

This is both an accessibility and performance improvement.

---

# 13. Avoiding Layout Thrash and Forced Reflow

This is partly JavaScript, but CSS choices influence it heavily.

## 13.1 Do not animate layout properties if you can avoid it

Expensive:

```css
width;
height;
top;
right;
bottom;
left;
margin;
padding;
border-width;
font-size;
flex-basis;
grid-template-columns;
```

Sometimes unavoidable, but measure.

---

## 13.2 Use `aspect-ratio` to prevent layout shift

```css
img,
video {
  max-width: 100%;
  height: auto;
}

.media-frame {
  aspect-ratio: 16 / 9;
}
```

For images:

```html
<img
  src="photo.avif"
  width="1200"
  height="675"
  alt="Example"
  loading="lazy"
  decoding="async"
>
```

CSS:

```css
img {
  max-width: 100%;
  height: auto;
}
```

---

## 13.3 Reserve space for dynamic content

Bad:

```css
.notification {
  /* no min-height */
}
```

Better:

```css
.notification-slot {
  min-height: 56px;
}
```

Or use `contain-intrinsic-size` for skipped content.

---

## 13.4 Use `scrollbar-gutter` to avoid scrollbar shift

```css
html {
  scrollbar-gutter: stable;
}
```

This prevents layout shift when scrollbars appear/disappear.

# 14. CSS Delivery Optimization

CSS properties are only one part of performance. Delivery matters a lot.

---

## 14.1 Inline critical CSS

Inline the CSS required for above-the-fold content.

Example:

```html
<head>
  <style>
    /* critical CSS */
  </style>
</head>
```

Keep it small.

---

## 14.2 Defer non-critical CSS

Pattern:

```html
<link
  rel="preload"
  href="non-critical.css"
  as="style"
  onload="this.onload=null;this.rel='stylesheet'"
>
<noscript>
  <link rel="stylesheet" href="non-critical.css">
</noscript>
```

Or use build tools that handle this for you.

---

## 14.3 Avoid CSS `@import`

Bad:

```css
@import url("theme.css");
```

Better:

```html
<link rel="stylesheet" href="theme.css">
```

`@import` can delay CSS loading because it creates extra requests after CSS parsing.

---

## 14.4 Minify CSS

Use tools such as:

- Lightning CSS,
- cssnano,
- esbuild,
- PostCSS,
- Vite,
- webpack,
- Parcel.

Example:

```bash
npx lightningcss --minify input.css -o output.css
```

Exact CLI depends on tool/version.

---

## 14.5 Compress with Brotli or gzip

Server should compress text assets:

- CSS,
- HTML,
- JavaScript,
- SVG.

Brotli is usually better for static assets.

---

## 14.6 Remove unused CSS

Use:

- PurgeCSS,
- Lightning CSS,
- PostCSS plugins,
- framework tree-shaking,
- CSS coverage tools.

Be careful with dynamically added classes.

Safe-list example for PurgeCSS-style tools:

```js
safelist: [
  "is-open",
  "is-active",
  "modal--visible",
  /^carousel-/,
];
```

---

## 14.7 Split CSS by route

For large apps, load only what the current route needs.

Example:

```text
home.css
product.css
checkout.css
```

Do not ship one huge global stylesheet if most pages use a small part of it.

---

## 14.8 Avoid runtime CSS-in-JS when possible

Runtime CSS-in-JS can add overhead:

- style injection,
- serialization,
- recalculation,
- hydration cost.

Prefer:

- static CSS extraction,
- CSS Modules,
- build-time atomic CSS,
- plain CSS,
- vanilla-extract,
- Panda,
- or other zero-runtime approaches where appropriate.

---

# 15. Font Optimization

Fonts affect both load performance and layout shift.

---

## 15.1 Use `font-display`

```css
@font-face {
  font-family: "Brand";
  src: url("/fonts/brand.woff2") format("woff2");
  font-display: swap;
}
```

Options:

| Value | Use case |
|---|---|
| `swap` | Show fallback quickly, swap when ready |
| `optional` | Avoid layout shift if font is slow |
| `fallback` | Short block period, then fallback |
| `block` | Avoid unless necessary |

For performance-critical pages, `optional` can be excellent because it prevents layout shift and slow text.

---

## 15.2 Preload only critical fonts

```html
<link
  rel="preload"
  href="/fonts/brand-regular.woff2"
  as="font"
  type="font/woff2"
  crossorigin
>
```

Do not preload every font weight.

---

## 15.3 Subset fonts

Use `unicode-range`:

```css
@font-face {
  font-family: "Brand";
  src: url("/fonts/brand-latin.woff2") format("woff2");
  unicode-range: U+0000-00FF;
  font-display: swap;
}
```

---

## 15.4 Match fallback metrics to reduce CLS

Use font metric overrides:

```css
@font-face {
  font-family: "Brand Fallback";
  src: local("Arial");
  size-adjust: 105%;
  ascent-override: 90%;
  descent-override: 20%;
  line-gap-override: 0%;
}
```

This helps reduce layout shift when web fonts load.

---

# 16. Image Optimization from CSS and HTML

CSS cannot fully fix bad images, but it can help.

---

## 16.1 Use `aspect-ratio`

```css
.product-image {
  aspect-ratio: 4 / 3;
  width: 100%;
  object-fit: cover;
}
```

---

## 16.2 Use `loading="lazy"` for below-the-fold images

```html
<img
  src="photo.avif"
  width="800"
  height="600"
  alt="Example"
  loading="lazy"
  decoding="async"
>
```

Do not lazy-load the LCP image.

For LCP image:

```html
<img
  src="hero.avif"
  width="1600"
  height="900"
  alt="Hero"
  fetchpriority="high"
>
```

---

## 16.3 Use responsive images

```html
<img
  src="photo-800.avif"
  srcset="
    photo-400.avif 400w,
    photo-800.avif 800w,
    photo-1200.avif 1200w
  "
  sizes="(min-width: 800px) 800px, 100vw"
  width="800"
  height="600"
  alt="Example"
  loading="lazy"
  decoding="async"
>
```

---

## 16.4 Be careful with CSS background images for LCP

Background images can load later than `<img>` elements.

If the hero is an image, prefer:

```html
<img fetchpriority="high" src="hero.avif" alt="...">
```

or preload the background image if absolutely necessary.

# 17. Selectors and Style Recalculation

Modern browsers are fast, but huge DOM plus complex selectors can still hurt.

---

## 17.1 Prefer classes for large dynamic lists

Less ideal:

```css
.list ul li div p span {
  color: #333;
}
```

Better:

```css
.list-item-text {
  color: #333;
}
```

This is mostly about maintainability, but it can also reduce selector matching work in huge DOM trees.

---

## 17.2 Avoid excessive universal selectors

Usually fine in small pages:

```css
* {
  box-sizing: border-box;
}
```

But avoid heavy universal rules in huge documents if not needed.

---

## 17.3 Be careful with `:has()`

`:has()` is powerful but can be expensive in huge DOMs if used broadly.

Potentially expensive:

```css
form:has(input:invalid) {
  border-color: red;
}
```

Usually fine, but measure on large pages.

---

## 17.4 Avoid huge invalidation from `:hover`

Bad for large documents:

```css
body:hover .something {
  ...
}
```

Or:

```css
.page:hover .card {
  ...
}
```

This can cause broad style invalidation.

Prefer local hover:

```css
.card:hover .card-image {
  transform: scale(1.05);
}
```

---

# 18. Heavy CSS Effects to Use Carefully

These are not forbidden, but they need measurement.

## Expensive CSS features

```css
filter: blur();
filter: drop-shadow();
backdrop-filter: blur();
mix-blend-mode;
clip-path with complex paths;
mask-image;
border-image;
complex SVG filters;
text-shadow on large text blocks;
background-attachment: fixed;
large border-radius with overflow hidden;
complex gradients animated with background-position;
```

---

## Safer alternatives

| Expensive | Safer alternative |
|---|---|
| `backdrop-filter: blur()` | semi-transparent background |
| animated `box-shadow` | pseudo-element opacity |
| animated `background-position` | layered transform/opacity |
| full-page `filter` | localized effect |
| `background-attachment: fixed` | fixed decorative layer or no parallax |
| heavy `mix-blend-mode` | precomposed image effect |

---

# 19. Use `pointer-events: none` for Decorative Elements

If an element is purely decorative, disable pointer events:

```css
.decorative-overlay {
  pointer-events: none;
}
```

Benefits:

- reduces hit-testing work slightly,
- avoids accidental interactions,
- helps text selection and touch behavior.

Especially useful for:

- overlays,
- pseudo-elements,
- gradients,
- noise textures,
- decorative shapes.

---

# 20. Use `inert` for Hidden Interactive Content

If content is hidden but remains in the DOM, make sure it cannot be focused or activated.

```html
<div inert>
  <button>Should not be focusable</button>
</div>
```

CSS:

```css
[inert] {
  pointer-events: none;
  user-select: none;
}
```

This is better than relying only on visual hiding.

Use for:

- inactive modals,
- hidden drawers,
- off-canvas menus,
- background content when a dialog is open.

---

# 21. Visibility Patterns: `display`, `visibility`, `opacity`, `content-visibility`

These are often confused.

## `display: none`

```css
.hidden {
  display: none;
}
```

- Removed from layout.
- No paint.
- Usually hidden from accessibility tree.
- Can cause reflow when shown.
- Good default for hidden panels.

---

## `visibility: hidden`

```css
.hidden {
  visibility: hidden;
}
```

- Still occupies layout space.
- Not painted.
- Can transition visibility.
- Children can override with `visibility: visible`.
- More expensive than `display: none` because layout still exists.

---

## `opacity: 0`

```css
.hidden {
  opacity: 0;
}
```

- Still occupies layout.
- Still painted.
- Still interactive unless `pointer-events: none`.
- Still accessible unless additionally hidden.
- Useful for animations.

---

## `content-visibility: hidden`

```css
.hidden-content {
  content-visibility: hidden;
}
```

- Skips rendering of content.
- Element box may still exist.
- Can reserve size with `contain-intrinsic-size`.
- More specialized.
- Use carefully.

---

## Recommended defaults

| Need | Use |
|---|---|
| Hide completely | `display: none` or `hidden` |
| Hide but keep space | `visibility: hidden` or sized wrapper |
| Hide for animation | `opacity: 0` plus visibility management |
| Hide offscreen content for performance | `content-visibility: auto` |
| Hide but keep in DOM for state | Usually `display: none`, sometimes `content-visibility: hidden` |
| Prevent interaction | `inert`, `pointer-events: none`, or proper hiding |

---

# 22. Practical Patterns and Recipes

## Recipe 1: Long article with below-the-fold sections

```css
.article-section {
  content-visibility: auto;
  contain-intrinsic-size: auto 700px;
}

.article-section .card {
  contain: layout paint style;
}

@media print {
  .article-section {
    content-visibility: visible !important;
    contain-intrinsic-size: auto;
  }
}
```

---

## Recipe 2: Comments section

```css
.comments {
  content-visibility: auto;
  contain-intrinsic-size: auto 1200px;
}

.comment {
  contain: layout style;
}
```

If comments have avatars/images:

```html
<img loading="lazy" decoding="async" width="48" height="48" alt="Avatar">
```

---

## Recipe 3: Modal with clean `will-change`

CSS:

```css
.modal {
  position: fixed;
  inset: 0;
  transform: translateY(24px);
  opacity: 0;
  transition:
    transform 250ms ease,
    opacity 250ms ease;
}

.modal.is-open {
  transform: translateY(0);
  opacity: 1;
}

.modal.will-animate {
  will-change: transform, opacity;
}
```

JavaScript:

```js
function openModal(modal) {
  modal.classList.add("will-animate");

  requestAnimationFrame(() => {
    requestAnimationFrame(() => {
      modal.classList.add("is-open");
    });
  });

  modal.addEventListener(
    "transitionend",
    (event) => {
      if (event.target === modal) {
        modal.classList.remove("will-animate");
      }
    },
    { once: true }
  );
}
```

---

## Recipe 4: Card hover zoom without layout animation

```css
.card {
  overflow: hidden;
  contain: layout paint style;
}

.card-image {
  transition: transform 250ms ease;
}

.card:hover .card-image {
  transform: scale(1.05);
}

@media (hover: hover) and (pointer: fine) {
  .card:hover .card-image {
    will-change: transform;
  }
}
```

---

## Recipe 5: Accordion without animating `height`

Avoid animating `height: auto`.

Better CSS grid pattern:

```css
.accordion-panel {
  display: grid;
  grid-template-rows: 0fr;
  transition: grid-template-rows 300ms ease;
}

.accordion-panel.is-open {
  grid-template-rows: 1fr;
}

.accordion-panel > .accordion-inner {
  overflow: hidden;
  min-height: 0;
}
```

This still causes layout, but it avoids JavaScript height measurement and is often smooth enough when contained.

If you need maximum performance, animate transform/opacity instead, or use measured height carefully.

---

## Recipe 6: Fixed-size ad or embed slot

```css
.ad-slot {
  width: 300px;
  height: 250px;
  contain: strict;
  overflow: hidden;
}
```

This prevents layout shift.

---

## Recipe 7: Lazy heavy widget

CSS:

```css
.heavy-widget {
  content-visibility: auto;
  contain-intrinsic-size: auto 480px;
}
```

JavaScript:

```js
document.querySelectorAll(".heavy-widget").forEach((widget) => {
  widget.addEventListener("contentvisibilityautostatechange", (event) => {
    if (!event.skipped && !widget.dataset.loaded) {
      initHeavyWidget(widget);
      widget.dataset.loaded = "true";
    }
  });
});
```

---

## Recipe 8: Drawer with reduced motion support

```css
.drawer {
  transform: translateX(100%);
  transition: transform 300ms ease;
}

.drawer.is-open {
  transform: translateX(0);
}

.drawer.will-move {
  will-change: transform;
}

@media (prefers-reduced-motion: reduce) {
  .drawer {
    transition: none;
  }

  .drawer.will-move {
    will-change: auto;
  }
}
```

# 23. Anti-Patterns

## Anti-pattern 1: Global `will-change`

```css
* {
  will-change: transform;
}
```

Result:

- too many layers,
- high memory,
- worse performance.

---

## Anti-pattern 2: `content-visibility` without placeholder

```css
.section {
  content-visibility: auto;
}
```

Result:

- layout shift,
- scrollbar jumps.

Fix:

```css
.section {
  content-visibility: auto;
  contain-intrinsic-size: auto 600px;
}
```

---

## Anti-pattern 3: `contain: size` on dynamic containers

```css
.comment {
  contain: size;
}
```

Result:

- collapsed containers.

Fix:

```css
.comment {
  contain: layout paint style;
}
```

---

## Anti-pattern 4: Animating `top` and `left`

```css
.tooltip {
  transition: top 200ms, left 200ms;
}
```

Fix:

```css
.tooltip {
  transition: transform 200ms;
  transform: translate(20px, 40px);
}
```

---

## Anti-pattern 5: Using `will-change` instead of fixing property choice

```css
.bad {
  will-change: width, height;
  transition: width 300ms, height 300ms;
}
```

Fix:

```css
.good {
  transition: transform 300ms;
  transform: scale(1.1);
}
```

---

## Anti-pattern 6: Heavy blur on mobile

```css
.fullscreen-overlay {
  backdrop-filter: blur(30px);
}
```

Fix:

```css
.fullscreen-overlay {
  background: rgba(15, 15, 15, 0.65);
}
```

---

## Anti-pattern 7: Applying `content-visibility` to hero

```css
.hero {
  content-visibility: auto;
}
```

Usually avoid.

---

## Anti-pattern 8: Hiding focusable content without focus management

Bad:

```css
.hidden-menu {
  content-visibility: hidden;
}
```

If it contains links/buttons, use robust hiding:

```html
<div hidden>
  ...
</div>
```

or:

```html
<div inert>
  ...
</div>
```

# 25. Measuring CSS Performance

Do not optimize blindly.

---

## 25.1 Chrome DevTools Performance panel

Use this for:

- long tasks,
- layout work,
- style recalculation,
- paint,
- compositing.

Steps:

1. Open DevTools.
2. Go to Performance.
3. Enable CPU throttling, for example 4x.
4. Record page load.
5. Record the interaction that janks.
6. Look for:
   - purple layout events,
   - style recalculation,
   - paint events,
   - long tasks,
   - dropped frames.

---

## 25.2 Rendering tab

Enable:

- Paint flashing,
- Layer borders,
- FPS meter,
- Layout Shift Regions.

Use cases:

| Tool | What it shows |
|---|---|
| Paint flashing | What is being repainted |
| Layer borders | What has its own layer |
| FPS meter | Frame rate during interaction |
| Layout Shift Regions | What is shifting |

If you see many layers after adding `will-change`, that is a warning sign.

---

## 25.3 Coverage panel

Use Coverage to find unused CSS.

Steps:

1. DevTools.
2. Command menu.
3. Search “Coverage”.
4. Reload.
5. Inspect unused bytes.

Do not blindly remove unused CSS if classes are added dynamically.

---

## 25.4 Lighthouse

Use for:

- unused CSS,
- render-blocking CSS,
- CLS,
- LCP,
- TBT.

But do not rely only on Lighthouse score. Use real interaction profiling.

---

## 25.5 WebPageTest

Useful for:

- real network conditions,
- filmstrip,
- CPU timing,
- connection throttling,
- multi-step tests.

---

## 25.6 Test on real low-end devices

A desktop machine can hide performance problems.

Test on:

- low-end Android,
- mid-range phones,
- throttled CPU,
- throttled network.

# 26. Metrics and What CSS Affects

## LCP: Largest Contentful Paint

Affected by:

- render-blocking CSS,
- hero image loading,
- font loading,
- critical CSS size,
- server response time,
- resource priorities.

CSS fixes:

- inline critical CSS,
- defer non-critical CSS,
- preload LCP resources,
- avoid lazy-loading LCP,
- use `fetchpriority="high"` for LCP image.

---

## CLS: Cumulative Layout Shift

Affected by:

- images without dimensions,
- fonts,
- dynamic content,
- scrollbar appearance,
- skipped content without placeholders.

CSS fixes:

```css
aspect-ratio;
width/height;
min-height;
scrollbar-gutter: stable;
contain-intrinsic-size;
font-display: optional;
font metric overrides;
```

---

## INP: Interaction to Next Paint

Affected by:

- long style recalculation,
- long layout,
- heavy hover effects,
- huge DOM,
- expensive CSS selectors,
- heavy JavaScript.

CSS fixes:

- reduce invalidation scope with `contain`,
- avoid broad `:hover` invalidation,
- use compositor-friendly animations,
- reduce DOM size,
- use virtualization,
- avoid heavy effects during interaction.

---

# 27. Full Optimization Checklist

## Before adding any optimization

- [ ] Measure baseline.
- [ ] Identify the actual bottleneck.
- [ ] Confirm the issue is CSS-related.
- [ ] Test on low-end devices.
- [ ] Have a rollback plan.

---

## `content-visibility`

- [ ] Use `content-visibility: auto` mainly for large below-the-fold containers.
- [ ] Always provide `contain-intrinsic-size` if size is not fixed.
- [ ] Use approximate real sizes.
- [ ] Do not apply to hero or critical above-the-fold UI.
- [ ] Do not use on tiny components.
- [ ] Test scrolling for scrollbar jumps.
- [ ] Test keyboard focus.
- [ ] Test screen readers if relevant.
- [ ] Test print styles.
- [ ] Test anchor links and find-in-page behavior.
- [ ] Use virtualization for very large lists.

---

## `will-change`

- [ ] Use only before animation.
- [ ] Remove after animation.
- [ ] Limit number of elements.
- [ ] Prefer `transform` and `opacity`.
- [ ] Do not apply globally.
- [ ] Do not use for static elements.
- [ ] Check for new stacking contexts.
- [ ] Check fixed-position descendants.
- [ ] Check text blurriness.
- [ ] Check GPU memory with layer borders.

---

## `contain`

- [ ] Use `contain: content` for independent components.
- [ ] Use `contain: strict` only for fixed-size elements.
- [ ] Avoid `contain: paint` when dropdowns/tooltips overflow.
- [ ] Avoid `contain: size` on auto-height elements.
- [ ] Test visual overflow.
- [ ] Test positioned descendants.

---

## Animations

- [ ] Animate `transform` and `opacity`.
- [ ] Avoid animating `width`, `height`, `top`, `left`.
- [ ] Avoid animating `box-shadow` directly.
- [ ] Avoid animating `background-position`.
- [ ] Avoid heavy `filter` animations.
- [ ] Avoid large `backdrop-filter` blurs.
- [ ] Respect `prefers-reduced-motion`.

---

## CSS delivery

- [ ] Minify CSS.
- [ ] Compress with Brotli/gzip.
- [ ] Inline critical CSS.
- [ ] Defer non-critical CSS.
- [ ] Remove unused CSS safely.
- [ ] Avoid `@import`.
- [ ] Split CSS by route if large app.
- [ ] Cache CSS properly.

---

## Images and fonts

- [ ] Add `width` and `height` or `aspect-ratio`.
- [ ] Use `loading="lazy"` for below-the-fold images.
- [ ] Do not lazy-load LCP image.
- [ ] Use `fetchpriority="high"` for LCP image.
- [ ] Use responsive images.
- [ ] Use modern formats.
- [ ] Use `font-display: swap` or `optional`.
- [ ] Preload only critical fonts.
- [ ] Subset fonts.
- [ ] Match fallback metrics.

---

## Layout stability

- [ ] Use `scrollbar-gutter: stable`.
- [ ] Reserve space for dynamic widgets.
- [ ] Use `contain-intrinsic-size` for skipped content.
- [ ] Avoid layout shift from fonts.
- [ ] Avoid layout shift from ads/embeds.
- [ ] Use fixed-size containers where appropriate.

# 28. Final Decision Table

| Problem | Best CSS tool | Warning |
|---|---|---|
| Below-the-fold sections are heavy | `content-visibility: auto` | Use placeholder size |
| Huge list with thousands of items | Virtualization | `content-visibility` may not be enough |
| Animation stutters at start | `will-change` briefly | Remove after animation |
| Card content should not affect outside layout | `contain: content` | Check overflow clipping |
| Fixed-size ad slot | `contain: strict` | Must have explicit size |
| Modal/drawer animation | `will-change: transform, opacity` | Do not leave on permanently |
| Hover zoom | `transform: scale()` | Avoid width/height animation |
| Shadow animation | Pseudo-element opacity | Avoid animating `box-shadow` |
| Hidden tab panel | `display: none` or `hidden` | `content-visibility: hidden` only if needed |
| Offscreen chart | `content-visibility: auto` + lazy init | Test size and accessibility |
| Scrollbar shift | `scrollbar-gutter: stable` | Test layout |
| Image layout shift | `width/height` or `aspect-ratio` | Required for CLS |
| Font layout shift | `font-display: optional` + metric overrides | Test typography |
| Global CSS performance | Critical CSS, minify, remove unused | Do not rely on one trick |

# 29. Recommended Practical Strategy

Start in this order:

## Step 1: Fix delivery

- Reduce CSS bytes.
- Inline critical CSS.
- Defer non-critical CSS.
- Remove unused CSS.
- Avoid render-blocking CSS.

This usually gives the biggest wins.

---

## Step 2: Fix layout stability

- Add image dimensions.
- Use `aspect-ratio`.
- Reserve space for dynamic content.
- Use `scrollbar-gutter`.
- Fix font shift.

---

## Step 3: Fix animation properties

Use:

```css
transform;
opacity;
```

Avoid:

```css
width;
height;
top;
left;
box-shadow;
background-position;
```

---

## Step 4: Use containment

Apply:

```css
contain: content;
```

to independent components.

Apply:

```css
contain: strict;
```

to fixed-size widgets.

---

## Step 5: Use `content-visibility`

Apply:

```css
content-visibility: auto;
contain-intrinsic-size: auto 600px;
```

to large below-the-fold sections.

---

## Step 6: Use `will-change` surgically

Only after other fixes, and only if measured.

# 30. Short Cheat Sheet

```css
/* Good: below-the-fold section */
.section {
  content-visibility: auto;
  contain-intrinsic-size: auto 600px;
}

/* Good: independent component */
.card {
  contain: layout paint style;
}

/* Good: fixed-size slot */
.ad-slot {
  width: 300px;
  height: 250px;
  contain: strict;
}

/* Good: temporary animation hint */
.is-animating {
  will-change: transform, opacity;
}

/* Good: animation properties */
.modal {
  transition:
    transform 250ms ease,
    opacity 250ms ease;
}

/* Bad */
* {
  will-change: transform;
}

/* Bad */
.section {
  content-visibility: auto;
}

/* Bad */
.auto-height-card {
  contain: size;
}

/* Bad */
.tooltip {
  transition: top 200ms, left 200ms;
}
```

---

# 31. Final Guidance

The safest high-impact CSS performance stack is:

1. Ship less CSS.
2. Inline critical CSS.
3. Defer non-critical CSS.
4. Use stable layout sizes.
5. Animate `transform` and `opacity`.
6. Use `contain` for independent components.
7. Use `content-visibility: auto` with `contain-intrinsic-size` for large below-the-fold sections.
8. Use `will-change` only temporarily and only when measured.

The most dangerous mistakes are:

1. Applying `will-change` globally.
2. Using `content-visibility` without size placeholders.
3. Using `contain: size` on auto-height elements.
4. Animating layout properties unnecessarily.
5. Adding heavy blur/blend/shadow effects without testing on mobile.
