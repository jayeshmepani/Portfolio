Yes. On the JavaScript side, there is a much larger performance toolbox than just `IntersectionObserver`. The important part is understanding **which mechanism solves which bottleneck**.

I researched the current MDN, web.dev, Chrome/web-platform guidance, including newer APIs such as **`scheduler.postTask()` / `scheduler.yield()`**, **Long Animation Frames**, **Speculation Rules**, **`import defer`**, and current resource-priority guidance. One major theme is consistent: **optimize scheduling, loading, rendering, and lifetime separately instead of applying “lazy loading” or “async” everywhere.** ([MDN Web Docs][1])

# JavaScript Performance, Loading & Runtime Optimization — Comprehensive Guide

---

# 1. The mental model you should use

Most browser JavaScript that touches the UI runs on the **main thread**. That same thread also has to process events, style/layout work, rendering, and painting. A large JavaScript task can therefore delay both interaction and rendering. ([MDN Web Docs][2])

Think of your application as five separate performance problems:

```text
                    WEB APP PERFORMANCE
                           │
        ┌──────────────────┼──────────────────┐
        │                  │                  │
      LOADING           RUNTIME           RENDERING
        │                  │                  │
   What gets loaded?   How much work?    How often?
   When?               Where?            What gets recalculated?
   At what priority?   On which thread?
        │                  │                  │
        └──────────────────┼──────────────────┘
                           │
                     LIFECYCLE
                           │
             When can work stop / resume?
```

And there is a sixth concern:

```text
OBSERVABILITY
    ↓
How do you prove what is actually slow?
```

That leads to the following toolbox:

| Problem                          | Main tools                                     |
| -------------------------------- | ---------------------------------------------- |
| Detect viewport visibility       | `IntersectionObserver`                         |
| Detect element resizing          | `ResizeObserver`                               |
| Detect DOM mutations             | `MutationObserver`                             |
| Measure performance              | `PerformanceObserver`                          |
| Animate/sync visual updates      | `requestAnimationFrame()`                      |
| Run low-priority work            | `requestIdleCallback()`                        |
| Prioritize/yield tasks           | `scheduler.postTask()`, `scheduler.yield()`    |
| Cancel work                      | `AbortController` / `AbortSignal`              |
| Defer code                       | `async`, `defer`, modules, `import()`          |
| Defer module evaluation          | `import defer`                                 |
| Parallelize heavy CPU work       | Web Workers                                    |
| Lazy-load resources              | native `loading`, IO, dynamic import           |
| Speculate future navigations     | Speculation Rules                              |
| Pause hidden-page work           | Page Visibility                                |
| Preserve instant back navigation | bfcache-friendly lifecycle                     |
| Send analytics without blocking  | `sendBeacon()`, `fetch(..., {keepalive:true})` |
| Prevent scroll blocking          | passive listeners                              |
| Reduce DOM work                  | delegation, batching, smaller DOM              |
| Avoid stale async work           | cancellation / abort                           |
| Diagnose jank                    | Performance panel, LoAF, Event Timing          |

---

# 2. The biggest optimization principle

The strongest optimization usually isn't:

```js
makeThisFunctionFaster();
```

It is:

```text
Don't execute the function yet.
Don't execute it at all.
Execute less of it.
Execute it somewhere else.
Execute it in smaller pieces.
Cancel it if it is no longer needed.
```

For example:

```text
Bad:

Page loads
  ↓
Initialize 30 widgets
  ↓
Initialize 15 libraries
  ↓
Parse 500 KB JS
  ↓
Build everything
  ↓
User finally gets interaction
```

Better:

```text
Page loads
  ↓
Initialize only what is immediately needed
  ↓
Load feature when needed
  ↓
Load expensive feature when visible
  ↓
Move CPU-heavy processing to worker
  ↓
Cancel obsolete work
```

This principle is behind code splitting, lazy loading, observers, task scheduling, workers, and resource prioritization. ([MDN Web Docs][3])

---

# 3. `IntersectionObserver`

This is probably the most important observer for web-performance work.

## What it solves

It tells you when an element intersects a root, normally the viewport.

```js
const observer = new IntersectionObserver(entries => {
    for (const entry of entries) {
        if (entry.isIntersecting) {
            // Do something.
        }
    }
});

observer.observe(element);
```

The important benefit is that you don't have to continuously implement viewport detection yourself through scroll handlers and repeated geometry calculations. The browser manages intersection calculations and can optimize them. ([MDN Web Docs][4])

---

# 4. The old pattern you should usually avoid

This:

```js
window.addEventListener("scroll", () => {
    const rect = element.getBoundingClientRect();

    if (rect.top < window.innerHeight) {
        loadSomething();
    }
});
```

is not automatically catastrophic.

The problem is doing this for many elements, repeatedly, while the page is scrolling:

```text
scroll event
   ↓
query geometry
   ↓
calculate
   ↓
query geometry
   ↓
calculate
   ↓
100 elements
   ↓
repeat continuously
```

Intersection Observer exists precisely to remove much of this manual machinery. ([MDN Web Docs][4])

---

# 5. `root`

Default:

```js
const observer = new IntersectionObserver(callback);
```

means:

```text
root = viewport
```

You can observe relative to a scroll container:

```js
const observer = new IntersectionObserver(callback, {
    root: scrollContainer
});
```

This is useful for:

```text
horizontal carousels
chat panels
virtualized lists
scrollable dashboards
nested scrolling areas
```

The `root` defines the rectangle used for intersection testing. ([MDN Web Docs][5])

---

# 6. `rootMargin`

This is extremely useful for preloading.

Example:

```js
const observer = new IntersectionObserver(callback, {
    rootMargin: "400px 0px"
});
```

Conceptually:

```text
actual viewport
┌─────────────────────────┐
│                         │
│       viewport          │
│                         │
└─────────────────────────┘

intersection zone
┌─────────────────────────┐
│      + 400px            │
│ ┌─────────────────────┐ │
│ │      viewport       │ │
│ └─────────────────────┘ │
│      + 400px            │
└─────────────────────────┘
```

This allows you to start work **before** content becomes visible.

For an image:

```text
image is 300px away
        ↓
observer fires
        ↓
start fetch
        ↓
network finishes
        ↓
user reaches image
        ↓
already available
```

This is much better than waiting until the element is actually visible when latency matters.

---

# 7. `threshold`

You can say:

```js
threshold: 0
```

or:

```js
threshold: 0.5
```

or:

```js
threshold: [0, 0.25, 0.5, 0.75, 1]
```

A threshold determines at what intersection ratios callbacks should be generated. MDN documents the behavior and notes that multiple threshold crossings can be delivered in a single callback, so you should not assume exactly one entry per callback. ([MDN Web Docs][4])

For lazy loading:

```js
threshold: 0
```

is usually sufficient.

Don't use:

```js
threshold: Array.from({length: 101}, (_, i) => i / 100)
```

unless you genuinely need fine-grained visibility measurements.

That creates substantially more observation events.

---

# 8. `trackVisibility`

This is a specialized feature:

```js
const observer = new IntersectionObserver(callback, {
    trackVisibility: true,
    delay: 500
});
```

It asks the browser to determine whether something is actually visible rather than merely geometrically intersecting.

That means accounting for situations such as:

```text
covered by another element
opacity effects
filters
transforms
other visual compromise
```

But this calculation is computationally expensive. MDN explicitly recommends using it only when necessary and pairing it with a `delay`; when enabled, the minimum delay is 100 ms. ([MDN Web Docs][4])

Good use:

```text
ad / impression measurement
actual-viewability analytics
```

Bad use:

```text
every lazy-loaded image
every card
every animation
```

For normal lazy loading, you generally don't need it.

---

# 9. The correct lazy-component pattern

```js
const observer = new IntersectionObserver((entries, observer) => {
    for (const entry of entries) {
        if (!entry.isIntersecting) {
            continue;
        }

        const element = entry.target;

        loadComponent(element);

        observer.unobserve(element);
    }
}, {
    rootMargin: "300px 0px"
});

document
    .querySelectorAll("[data-lazy-component]")
    .forEach(element => observer.observe(element));
```

Notice this:

```js
observer.unobserve(element);
```

Once your one-time initialization has happened, continued observation is unnecessary.

---

# 10. One observer vs many observers

You usually don't need:

```js
elements.forEach(element => {
    const observer = new IntersectionObserver(...);
    observer.observe(element);
});
```

Instead:

```js
const observer = new IntersectionObserver(...);

elements.forEach(element => {
    observer.observe(element);
});
```

One observer can observe multiple targets.

This gives you a much cleaner architecture:

```text
ONE observer
 ├── image 1
 ├── image 2
 ├── image 3
 ├── card 1
 ├── card 2
 └── widget 1
```

rather than:

```text
observer 1
observer 2
observer 3
...
```

This is mostly an architecture/lifecycle advantage; don't interpret it as a universal benchmark that one observer is always faster.

---

# 11. Native lazy loading should come first

For ordinary images:

```html
<img
    src="/images/photo.webp"
    loading="lazy"
    width="800"
    height="600"
    alt="..."
>
```

you often don't need custom Intersection Observer code at all.

The browser has native lazy-loading behavior for images and iframes. MDN explicitly recommends lazy-loading non-critical resources using `loading="lazy"`. ([MDN Web Docs][6])

Use Intersection Observer when you need to control **what happens**, not merely whether a standard resource loads.

Examples:

```text
initialize chart
start animation
load JS chunk
attach map
start video
hydrate component
fetch data
begin expensive computation
```

---

# 12. Never lazy-load your LCP resource blindly

This is particularly important.

If your hero image is the Largest Contentful Paint element:

```html
<img
    src="/hero.webp"
    loading="lazy"
>
```

can delay its request.

web.dev explicitly says LCP images should not be lazy-loaded because that introduces unnecessary resource delay. ([web.dev][7])

For likely LCP images, a more appropriate pattern can be:

```html
<img
    src="/hero.webp"
    fetchpriority="high"
    width="1600"
    height="900"
    alt="..."
>
```

where testing shows it is actually the LCP resource. `fetchpriority` is a hint rather than an absolute priority command, so use it selectively. ([web.dev][7])

---

# 13. `ResizeObserver`

`ResizeObserver` is the correct tool when you want to react to **element size**, rather than viewport size.

```js
const observer = new ResizeObserver(entries => {
    for (const entry of entries) {
        const width = entry.contentRect.width;

        // Adapt component behavior.
    }
});

observer.observe(element);
```

It is widely available and was specifically designed as a performant alternative to hacks based on window resize plus repeated measurements. ([MDN Web Docs][8])

---

# 14. Don't use `window.resize` for element-level problems

Bad architecture:

```js
window.addEventListener("resize", updateEverything);
```

when what you actually mean is:

```text
"tell me when this component's width changes."
```

The window may not resize when:

```text
sidebar changes
grid changes
font changes
parent changes
container query changes
content changes
```

`ResizeObserver` handles element-size changes directly. ([MDN Web Docs][8])

---

# 15. `ResizeObserver` is extremely useful for reusable components

For example:

```js
const ro = new ResizeObserver(entries => {
    for (const entry of entries) {
        const width = entry.contentBoxSize?.[0]?.inlineSize
            ?? entry.contentRect.width;

        entry.target.classList.toggle(
            "compact",
            width < 500
        );
    }
});
```

This is useful for:

```text
charts
data tables
custom controls
cards
editor panes
sidebars
chat windows
widgets
```

Though for pure layout behavior, prefer **CSS container queries** where they solve the problem without JS.

---

# 16. Use CSS instead of JS when CSS can solve it

This:

```js
ResizeObserver → calculate breakpoint → add class
```

may be unnecessary if the real requirement is simply:

```text
"when this container becomes narrow, use compact layout."
```

CSS:

```css
.wrapper {
    container-type: inline-size;
}

@container (width < 500px) {
    .card {
        /* compact layout */
    }
}
```

is generally cleaner because the browser handles layout declaratively.

Use `ResizeObserver` when you need **logic**, not just styling.

---

# 17. The biggest `ResizeObserver` trap: feedback loops

This is bad:

```js
const ro = new ResizeObserver(entries => {
    for (const entry of entries) {
        entry.target.style.width =
            `${entry.contentRect.width + 10}px`;
    }
});
```

Why?

```text
resize
 ↓
observer
 ↓
change size
 ↓
resize
 ↓
observer
 ↓
change size
 ↓
...
```

Browsers protect against runaway processing, but the MDN guidance explicitly warns that this can generate recurring `"ResizeObserver loop completed with undelivered notifications"` behavior and visible broken-layout flashes. ([MDN Web Docs][9])

---

# 18. Batch ResizeObserver mutations

If resizing in response to observation is necessary, schedule the mutation:

```js
const ro = new ResizeObserver(entries => {
    requestAnimationFrame(() => {
        for (const entry of entries) {
            updateLayout(entry.target);
        }
    });
});
```

MDN specifically recommends deferring resizing code to `requestAnimationFrame()` in cases where the intended behavior would otherwise generate observer feedback. ([MDN Web Docs][9])

---

# 19. `MutationObserver`

This observes DOM mutations:

```js
const observer = new MutationObserver(mutations => {
    for (const mutation of mutations) {
        // React to DOM changes.
    }
});

observer.observe(container, {
    childList: true,
    subtree: true
});
```

It replaces the obsolete Mutation Events model. ([MDN Web Docs][10])

---

# 20. MutationObserver is powerful—and easy to abuse

Don't do:

```js
observer.observe(document.body, {
    childList: true,
    subtree: true,
    attributes: true,
    characterData: true
});
```

unless you genuinely need to observe almost the entire page.

You can create an enormous stream of mutations:

```text
framework updates
DOM changes
attribute changes
animation-related changes
third-party widgets
analytics widgets
```

and then your observer callback itself becomes a workload.

Use the narrowest possible configuration:

```js
observer.observe(container, {
    childList: true
});
```

if that's all you need.

---

# 21. MutationObserver callbacks are microtasks

This is an important scheduling distinction.

Mutation Observer callbacks use the microtask queue. Microtasks run after the current task but before the browser proceeds to its next rendering opportunity. ([MDN Web Docs][11])

That means:

```text
task
 ↓
DOM changes
 ↓
MutationObserver
 ↓
microtasks
 ↓
render opportunity
```

Therefore, a giant MutationObserver callback can itself delay rendering.

Observer APIs do not magically make callback work free.

---

# 22. The observer callback must remain lightweight

Bad:

```js
const observer = new MutationObserver(() => {
    // Search the whole DOM
    // Recalculate everything
    // Parse data
    // Render thousands of nodes
});
```

Better:

```text
Mutation
  ↓
record what changed
  ↓
schedule one batch
  ↓
process affected nodes only
```

For example:

```js
let scheduled = false;
const pending = new Set();

const observer = new MutationObserver(mutations => {
    for (const mutation of mutations) {
        if (mutation.target instanceof HTMLElement) {
            pending.add(mutation.target);
        }
    }

    if (scheduled) {
        return;
    }

    scheduled = true;

    requestAnimationFrame(() => {
        scheduled = false;

        for (const element of pending) {
            update(element);
        }

        pending.clear();
    });
});
```

The principle is:

> Observe rapidly; process in batches.

---

# 23. `PerformanceObserver`

This is the observer that is specifically about **measuring performance**.

```js
const observer = new PerformanceObserver(list => {
    for (const entry of list.getEntries()) {
        console.log(entry);
    }
});

observer.observe({
    type: "resource",
    buffered: true
});
```

`PerformanceObserver` is widely available and can observe performance timeline entries asynchronously. `buffered: true` allows the observer to receive matching entries recorded before the observer was created. ([MDN Web Docs][12])

---

# 24. Don't poll performance

Bad:

```js
setInterval(() => {
    performance.getEntries();
}, 1000);
```

Use:

```text
PerformanceObserver
```

instead.

The observer model is specifically intended for passively receiving new performance entries rather than repeatedly querying the growing performance timeline. MDN also notes that observer notifications are asynchronous and are generally less disruptive. ([MDN Web Docs][13])

# 25. Performance entry types you should know

Modern browsers can expose:

```text

event
first-input

long-animation-frame
mark
measure
element

```

Support varies by browser, so use:

```js
PerformanceObserver.supportedEntryTypes
```

to detect capabilities. ([MDN Web Docs][14])

# 26. Long Tasks

A Long Task is traditionally a task exceeding 50 ms.

You can observe them:

```js
const observer = new PerformanceObserver(list => {
    for (const entry of list.getEntries()) {
        console.log("Long task:", entry);
    }
});

observer.observe({
    type: "longtask",
    buffered: true
});
```

The Long Tasks API reports tasks over 50 ms, but current web.dev guidance notes that the newer **Long Animation Frames API** addresses limitations of Long Tasks and provides better attribution. ([web.dev][15])

---

# 27. Long Animation Frames — LoAF

This is one of the newer APIs you should know.

```js
const observer = new PerformanceObserver(list => {
    for (const entry of list.getEntries()) {
        console.log(entry);
    }
});

observer.observe({
    type: "long-animation-frame",
    buffered: true
});
```

A long animation frame is a rendering update delayed beyond 50 ms. The API can provide more detailed attribution than the older Long Tasks API. ([MDN Web Docs][16])

This is especially valuable for diagnosing:

```text
scroll jank
animation jank
slow interactions
rendering stalls
large DOM updates
framework rendering work
```

---

# 28. Why Long Animation Frames are better for modern UI diagnosis

Suppose:

```text
JavaScript task = 40ms
style/layout/paint = 30ms
```

Total frame problem:

```text
70ms
```

A Long Task-only view may underrepresent the whole rendering problem because the JavaScript itself did not exceed 50 ms.

LoAF can reveal the **long frame as a rendering-level problem**. web.dev explicitly describes this broader scope as an advantage over Long Tasks. ([web.dev][15])

---

# 29. Event Timing / interaction measurement

Modern interaction performance is centered around **INP**.

JavaScript can inspect event timing:

```js
const observer = new PerformanceObserver(list => {
    for (const entry of list.getEntries()) {
        console.log({
            name: entry.name,
            duration: entry.duration,
            processingStart: entry.processingStart,
            processingEnd: entry.processingEnd
        });
    }
});

observer.observe({
    type: "event",
    buffered: true,
    durationThreshold: 40
});
```

`PerformanceEventTiming` provides information about input delay and event processing, and is one of the underlying APIs used to measure INP. ([MDN Web Docs][17])

---

# 30. INP's current target

The current web.dev guidance uses:

```text
≤ 200 ms     good
200–500 ms   needs improvement
> 500 ms     poor
```

measured at the 75th percentile of page views, segmented by mobile and desktop. ([web.dev][18])

This is extremely relevant to JavaScript optimization because INP includes:

```text
input delay
+
event handler processing
+
presentation delay
```

not merely "how fast was my function." ([web.dev][19])

---

# 31. `requestAnimationFrame()`

Use this for work directly tied to visual updates.

```js
requestAnimationFrame(timestamp => {
    updateUI(timestamp);
});
```

The browser calls the callback before the next repaint, and the cadence generally follows the display's refresh rate. Modern screens can run at 60, 75, 120, 144 Hz and beyond. ([MDN Web Docs][20])

---

# 32. `requestAnimationFrame()` is one-shot

This:

```js
requestAnimationFrame(update);
```

does **not** create a permanent loop.

For animation:

```js
function animate(timestamp) {
    update(timestamp);

    requestAnimationFrame(animate);
}

requestAnimationFrame(animate);
```

MDN explicitly notes that the callback must schedule another frame to continue animation. ([MDN Web Docs][20])

---

# 33. Use the timestamp

Bad:

```js
function animate() {
    x += 5;

    requestAnimationFrame(animate);
}
```

This can behave differently across refresh rates.

Better:

```js
let previous;

function animate(timestamp) {
    if (previous === undefined) {
        previous = timestamp;
    }

    const delta = timestamp - previous;
    previous = timestamp;

    x += speed * delta;

    requestAnimationFrame(animate);
}

requestAnimationFrame(animate);
```

MDN specifically warns that animation progress should be based on the callback timestamp so animation doesn't run faster on high-refresh-rate displays. ([MDN Web Docs][20])

---

# 34. The right pattern for scroll-driven JavaScript

Do not do:

```js
window.addEventListener("scroll", () => {
    element.style.transform = ...;
});
```

when the handler performs expensive work on every event.

Use a scheduler/coalescing pattern:

```js
let ticking = false;

window.addEventListener("scroll", () => {
    if (ticking) {
        return;
    }

    ticking = true;

    requestAnimationFrame(() => {
        ticking = false;

        updateFromScroll();
    });
}, { passive: true });
```

The event can arrive many times, but you process at most once per animation frame.

---

# 35. Passive event listeners

For cancelable input events such as wheel/touch events:

```js
element.addEventListener("touchmove", onTouchMove, {
    passive: true
});
```

means:

> this handler will not call `preventDefault()`.

That allows the browser to proceed with the default action such as scrolling without waiting for the handler to prove it won't cancel the event. MDN explains that this can reduce scroll/input delay. ([MDN Web Docs][21])

---

# 36. Important nuance: `scroll` itself cannot be canceled

You do not need:

```js
window.addEventListener("scroll", onScroll, {
    passive: true
});
```

for the purpose of making the scroll itself cancel-safe, because `scroll` cannot be canceled.

MDN explicitly notes this distinction. ([MDN Web Docs][21])

But using passive consistently can still communicate intent when you have handlers on other input events.

---

# 37. Don't lie with `passive:true`

This is invalid as a logical design:

```js
element.addEventListener("touchmove", event => {
    event.preventDefault();
}, {
    passive: true
});
```

`preventDefault()` won't work in a passive listener and the browser may emit a warning. ([MDN Web Docs][21])

Use:

```js
passive: false
```

only where you genuinely need cancellation.

---

# 38. Event delegation

Instead of:

```js
document
    .querySelectorAll(".button")
    .forEach(button => {
        button.addEventListener("click", handleClick);
    });
```

you can use:

```js
container.addEventListener("click", event => {
    const button = event.target.closest(".button");

    if (!button) {
        return;
    }

    handleClick(button);
});
```

Benefits include:

```text
fewer listener registrations
works with dynamically inserted children
simpler lifecycle
less per-node setup
```

This can matter for very large dynamic lists.

Don't use delegation blindly when event semantics, isolation, or debugging become worse than the benefit.

---

# 39. `once`

When an event only matters once:

```js
element.addEventListener("load", initialize, {
    once: true
});
```

the browser automatically removes the listener after its first invocation. MDN documents `once` specifically for this purpose. ([MDN Web Docs][21])

---

# 40. `AbortSignal` for event lifecycle management

Modern `addEventListener()` supports:

```js
const controller = new AbortController();

element.addEventListener("mousemove", handler, {
    signal: controller.signal
});

// Later:
controller.abort();
```

This removes the listener when the signal is aborted. ([MDN Web Docs][21])

This is particularly useful for components:

```text
component mounted
    ↓
attach listeners
    ↓
component destroyed
    ↓
controller.abort()
    ↓
all associated listeners removed
```

---

# 41. `AbortController` is bigger than event listeners

You can use the same concept for Fetch:

```js
const controller = new AbortController();

const response = await fetch("/api/data", {
    signal: controller.signal
});

// Later:
controller.abort();
```

Aborting can cancel fetches, response-body consumption and streams. ([MDN Web Docs][22])

---

# 42. This matters enormously for live search

Bad:

```text
user types "j"
 → request A

user types "ja"
 → request B

user types "jay"
 → request C

user types "jaye"
 → request D

user types "jayesh"
 → request E
```

Now all five requests may be active.

Better:

```js
let controller;

async function search(query) {
    controller?.abort();

    controller = new AbortController();

    try {
        const response = await fetch(
            `/api/search?q=${encodeURIComponent(query)}`,
            {
                signal: controller.signal
            }
        );

        return await response.json();
    } catch (error) {
        if (error.name === "AbortError") {
            return;
        }

        throw error;
    }
}
```

Now obsolete work is explicitly canceled.

That is often much more valuable than trying to make each request "slightly faster."

---

# 43. Cancellation is an optimization

A useful general rule:

```text
old work that is no longer relevant = wasted work
```

Examples:

```text
cancel previous search
cancel stale route fetch
cancel invisible component fetch
cancel old animation
cancel unnecessary worker task
cancel expensive computation
cancel inactive observer
```

`AbortController` is one of the cleanest browser-native ways to represent this lifecycle. ([MDN Web Docs][22])

---

# 44. JavaScript loading: `async`

For classic scripts:

```html
<script
    src="/analytics.js"
    async
></script>
```

the script can be fetched in parallel with HTML parsing and evaluated as soon as available. ([MDN Web Docs][23])

Use `async` when:

```text
execution order does not matter
script doesn't depend on DOM parsing completion
script doesn't need to wait for other scripts
```

Good examples:

```text
independent analytics
independent third-party widgets
advertising integrations
some isolated telemetry
```

---

# 45. Don't use `async` for dependent scripts

Bad:

```html
<script async src="library.js"></script>
<script async src="app.js"></script>
```

if:

```text
app.js depends on library.js
```

They can execute in whichever order they become ready.

---

# 46. `defer`

For classic scripts:

```html
<script
    src="/app.js"
    defer
></script>
```

the browser can fetch while parsing, but executes the script after the document has been parsed and before `DOMContentLoaded`. ([MDN Web Docs][24])

This is often the right default for traditional classic application scripts.

---

# 47. Modules are deferred by default

```html
<script
    type="module"
    src="/app.js"
></script>
```

Module scripts are deferred automatically.

Therefore:

```html
<script type="module" defer src="/app.js"></script>
```

doesn't give you an additional normal `defer` behavior; `defer` has no effect on module scripts. ([MDN Web Docs][25])

---

# 48. `async` module scripts are different

You can have:

```html
<script
    type="module"
    async
    src="/analytics.js"
></script>
```

In this case the module and its dependencies are fetched in parallel and evaluated as soon as they're available. ([MDN Web Docs][23])

Use only when execution can happen independently.

---

# 49. Dynamic `import()`

For features that aren't needed at startup:

```js
const module = await import("./heavy-editor.js");

module.initializeEditor();
```

Dynamic import enables code splitting and on-demand loading. MDN recommends it when modules genuinely need to be loaded dynamically. web.dev notes that it can reduce startup contention by keeping non-critical code out of the initial JavaScript workload. ([MDN Web Docs][26])

---

# 50. Excellent dynamic-import candidates

```text
image editor
PDF viewer
charts
map
syntax highlighter
Markdown parser
code editor
admin-only tools
checkout-specific logic
rare modal
advanced search
WASM module
large library used by one route
```

Example:

```js
button.addEventListener("click", async () => {
    const { openEditor } = await import("./editor.js");

    openEditor();
});
```

The user never opens the editor:

```text
editor.js
↓
never needed
↓
never loaded
```

---

# 51. Dynamic import isn't automatically perfect

Suppose:

```js
await import("./huge-5MB-library.js");
```

right after a user's click.

You've improved startup.

But you may now create:

```text
user clicks
   ↓
network
   ↓
download
   ↓
parse
   ↓
compile
   ↓
evaluate
   ↓
finally show UI
```

If the imported module is huge, evaluation can itself create a long task. web.dev explicitly warns about this behavior. ([web.dev][27])

Therefore:

```text
code splitting ≠ no cost
```

It moves cost to a more appropriate time.

---

# 52. `import defer` — newer and different

Modern JavaScript now has:

```js
import defer * as feature from "./feature.js";
```

This is distinct from `import()`.

With `import defer`:

```text
fetch
↓
parse
↓
link
↓
DO NOT evaluate yet
↓
evaluate when namespace properties are accessed
```

MDN documents `import defer` as a newer mechanism for deferring **synchronous evaluation** while still linking the module graph up front. ([MDN Web Docs][28])

---

# 53. `import()` vs `import defer`

|                 | `import()`                 | `import defer`                         |
| --------------- | -------------------------- | -------------------------------------- |
| Fetch           | deferred                   | upfront                                |
| Link            | deferred                   | upfront                                |
| Evaluation      | when imported              | when namespace accessed                |
| Returns Promise | yes                        | no                                     |
| Async coloring  | yes                        | less                                   |
| Best for        | genuinely optional modules | known module whose evaluation can wait |

Example:

```js
import defer * as parser from "./parser.js";
```

then:

```js
function compile(input) {
    return parser.compile(input);
}
```

Accessing `parser.compile` triggers evaluation of the deferred module graph. ([MDN Web Docs][28])

Do **not** defer a module whose startup side effects are required—for example a polyfill that must install before later code executes. MDN explicitly warns about this. ([MDN Web Docs][28])

---

# 54. `modulepreload`

If a module is known to be needed soon:

```html
<link
    rel="modulepreload"
    href="/modules/editor.js"
>
```

the browser can preemptively fetch, parse and compile the module and place it in the module map for later execution. ([MDN Web Docs][29])

This is useful when:

```text
module is not executed immediately
but
you know it will be required soon
```

---

# 55. Don't `modulepreload` everything

Bad:

```html
<link rel="modulepreload" href="a.js">
<link rel="modulepreload" href="b.js">
<link rel="modulepreload" href="c.js">
<link rel="modulepreload" href="d.js">
<link rel="modulepreload" href="e.js">
...
```

Preloading too much competes for bandwidth and processing resources.

MDN explicitly warns that modulepreload must be balanced against other operations that could otherwise become starved. ([MDN Web Docs][29])

---

# 56. Preload vs modulepreload vs prefetch

These are very different:

```text
preload
    ↓
I need this for THIS page soon

modulepreload
    ↓
I need this JavaScript module prepared soon

prefetch
    ↓
I might need this later

prerender
    ↓
I probably navigate here soon; prepare whole page
```

---

# 57. Resource priority

The Fetch Priority API lets you communicate relative importance.

Examples:

```html
<img
    src="/hero.webp"
    fetchpriority="high"
>
```

or:

```html
<script
    src="/analytics.js"
    async
    fetchpriority="low"
></script>
```

The API is a **hint**, not a command. web.dev recommends using it to correct cases where browser heuristics don't match the intended priority. ([web.dev][30])

---

# 58. Prioritize only genuinely important things

Don't do:

```text
10 high-priority images
10 high-priority scripts
8 high-priority fetches
```

because then:

```text
everything = high priority
```

which defeats the purpose.

web.dev specifically warns that giving high priority to multiple images can make prioritization less useful. ([web.dev][7])

---

# 59. `fetch()` priority

Fetch Priority can also apply to JavaScript-created fetches:

```js
fetch("/next-data.json", {
    priority: "low"
});
```

where supported.

web.dev documents this as another use of the Fetch Priority API. ([web.dev][30])

Again:

```text
high / low = relative hint
```

not an absolute network scheduler.

---

# 60. `preconnect`

If your critical resource comes from:

```text
https://cdn.example.com
```

you can establish the connection early:

```html
<link
    rel="preconnect"
    href="https://cdn.example.com"
>
```

This can perform connection setup before the actual resource is discovered. ([web.dev][31])

Use it for a **small number of genuinely important cross-origin origins**.

Not:

```html
<link rel="preconnect" href="https://site1.com">
<link rel="preconnect" href="https://site2.com">
<link rel="preconnect" href="https://site3.com">
...
```

for every third party.

---

# 61. `prefetch`

For likely future navigation:

```html
<link
    rel="prefetch"
    href="/about.html"
>
```

Historically, this is a speculative low-priority fetch.

For **document navigation**, the modern preferred mechanism where supported is increasingly the **Speculation Rules API**. MDN explicitly recommends Speculation Rules for document prefetch instead of older mechanisms when supported. ([MDN Web Docs][32])

---

# 62. Speculation Rules

Modern browsers can receive rules like:

```html
<script type="speculationrules">
{
    "prefetch": [
        {
            "where": {
                "href_matches": "/docs/*"
            }
        }
    ]
}
</script>
```

This tells supporting browsers they can prefetch likely future document navigations.

The API can also prerender documents:

```text
request
 ↓
HTML
 ↓
CSS
 ↓
JS
 ↓
subresources
 ↓
rendering
 ↓
hidden ready-to-activate page
```

When the user actually navigates, activation can be near-instant. ([MDN Web Docs][33])

---

# 63. Prefetch vs prerender

### Prefetch

```text
download future page response
```

### Prerender

```text
download
+
render
+
execute
+
load subresources
+
prepare page
```

Prerender therefore consumes substantially more resources.

MDN's current guidance recommends broader use of prefetch where safe, while using prerender more selectively because of its larger cost and side-effect risks. ([MDN Web Docs][33])

---

# 64. Huge warning with prefetch/prerender

Never treat a GET URL as automatically safe for speculative navigation.

Potentially dangerous examples include URLs that:

```text
sign out
add to cart
change language
send SMS
consume usage quota
modify state
trigger tracking
```

Speculation Rules requests can happen before the user actually navigates. MDN explicitly lists these kinds of unsafe side effects. ([MDN Web Docs][33])

Use speculative loading only with **safe, idempotent navigation resources**.

---

# 65. Prerendered pages need lifecycle-aware JavaScript

A prerendered document can execute JavaScript before the user actually sees it.

You can detect:

```js
if (document.prerendering) {
    // Delay side effects.
}
```

When activated:

```js
document.addEventListener(
    "prerenderingchange",
    () => {
        initializeAnalytics();
    },
    { once: true }
);
```

The Speculation Rules API provides this specifically so page code can avoid doing inappropriate work during hidden prerendering. ([MDN Web Docs][33])

---

# 66. `requestIdleCallback()`

This is for low-priority work:

```js
requestIdleCallback(() => {
    runNonCriticalWork();
});
```

It's useful for work that can wait until the browser has spare time. ([MDN Web Docs][34])

Examples:

```text
analytics preparation
non-critical indexing
secondary precomputation
warming rarely used features
non-essential data processing
```

---

# 67. Always use a timeout for required idle work

Bad:

```js
requestIdleCallback(doSomethingImportant);
```

with no timeout when the work must eventually happen.

A busy page can postpone the callback for potentially a long time.

Better:

```js
requestIdleCallback(doSomethingImportant, {
    timeout: 2000
});
```

MDN strongly recommends a timeout for required work because otherwise callback execution can be delayed by seconds. ([MDN Web Docs][34])

---

# 68. `requestIdleCallback()` is not a universal API

It is still **not Baseline**, according to current MDN compatibility data. ([MDN Web Docs][34])

So don't build your entire scheduling architecture around it.

A fallback can be:

```js
const idle = window.requestIdleCallback
    ? callback => requestIdleCallback(callback)
    : callback => setTimeout(callback, 0);
```

Though the semantics are not identical.

---

# 69. `requestIdleCallback()` is not for animation

Don't do:

```js
requestIdleCallback(animate);
```

Use:

```js
requestAnimationFrame(animate);
```

Animation wants to align with rendering.

Idle work wants to run when the browser has spare time.

Different scheduling goals.

---

# 70. `scheduler.postTask()`

This is one of the most interesting newer APIs.

```js
scheduler.postTask(task, {
    priority: "background"
});
```

Supported priorities include:

```text
user-blocking
user-visible
background
```

The API also supports delay and abort signals. ([MDN Web Docs][1])

---

# 71. `scheduler.yield()`

For long functions:

```js
async function processLargeDataset(items) {
    processFirstHalf(items);

    await scheduler.yield();

    processSecondHalf(items);
}
```

This gives the browser an opportunity to run other work before continuing.

MDN specifically describes `scheduler.yield()` as a way to break up long tasks while preserving a logical async function structure. ([MDN Web Docs][1])

---

# 72. `scheduler.postTask()` priorities

You can conceptually classify work as:

```text
USER-BLOCKING
    ↓
input / essential interaction / immediate UI

USER-VISIBLE
    ↓
non-critical visible UI

BACKGROUND
    ↓
analytics / cleanup / indexing / secondary work
```

Example:

```js
scheduler.postTask(
    () => initializeVisibleWidget(),
    { priority: "user-visible" }
);

scheduler.postTask(
    () => buildSearchIndex(),
    { priority: "background" }
);
```

The API is designed around this kind of prioritization. ([MDN Web Docs][1])

---

# 73. But `scheduler.postTask()` is not yet universal

Current MDN marks it as **Limited availability / not Baseline**. ([MDN Web Docs][35])

Therefore:

```js
if ("scheduler" in globalThis) {
    await scheduler.yield();
} else {
    await new Promise(resolve => setTimeout(resolve, 0));
}
```

is a reasonable progressive-enhancement pattern.

---

# 74. `setTimeout(..., 0)` is still useful

This:

```js
setTimeout(work, 0);
```

doesn't mean:

```text
execute immediately
```

It queues a task for a future opportunity.

The currently running JavaScript has to finish first. ([MDN Web Docs][36])

It remains useful for:

```text
breaking work into tasks
yielding
compatibility fallback
deferring non-critical initialization
```

but more modern APIs can communicate intent more precisely.

---

# 75. `queueMicrotask()` is NOT yielding

This is a very important distinction.

```js
queueMicrotask(() => {
    doWork();
});
```

does not hand control back to the browser in the same way as:

```js
setTimeout(...)
```

or:

```js
scheduler.yield()
```

Microtasks are processed before the browser proceeds to the next task/rendering opportunity. Recursive microtask creation can even starve the event loop. ([MDN Web Docs][11])

So:

```text
queueMicrotask
    = ordering/deferred micro work

scheduler.yield
    = give browser a chance to proceed

requestAnimationFrame
    = coordinate with rendering

requestIdleCallback
    = use idle time
```

These are not interchangeable.

---

# 76. A scheduling matrix

| API                       | Best for                                      |
| ------------------------- | --------------------------------------------- |
| synchronous               | tiny immediate work                           |
| `queueMicrotask()`        | post-current-task micro-work/order guarantees |
| `requestAnimationFrame()` | visual updates                                |
| `setTimeout()`            | coarse task deferral / fallback               |
| `requestIdleCallback()`   | non-urgent idle work                          |
| `scheduler.postTask()`    | prioritized work                              |
| `scheduler.yield()`       | breaking long tasks                           |
| Worker                    | CPU-heavy independent work                    |

---

# 77. Web Workers

If you have:

```text
large computation
```

you can move it off the main thread:

```js
const worker = new Worker("/worker.js");

worker.postMessage(data);
```

Inside the worker:

```js
self.onmessage = event => {
    const result = expensiveCalculation(event.data);

    self.postMessage(result);
};
```

Workers don't have direct DOM access, but they can prevent expensive computation from monopolizing the UI thread. web.dev explicitly recommends workers when significant computation would otherwise overwhelm the main thread. ([web.dev][37])

---

# 78. Workers don't magically make computation faster

This distinction is crucial.

Without worker:

```text
CPU work = 500 ms
main thread blocked = 500 ms
```

With worker:

```text
CPU work ≈ 500 ms
main thread blocked by worker work ≈ much less
```

You didn't necessarily make the calculation itself faster.

You made the application **more responsive** by moving the work.

web.dev explicitly describes off-main-thread architecture as moving work rather than inherently reducing total work, with some communication overhead. ([web.dev][38])

---

# 79. Worker communication has a cost

This:

```js
worker.postMessage(hugeObject);
```

can involve structured cloning / transfer behavior and communication overhead.

For large binary data, transferable objects such as:

```text
ArrayBuffer
```

can be much more appropriate.

web.dev discusses communication overhead as an important tradeoff in off-main-thread architecture. ([web.dev][38])

---

# 80. Excellent worker use cases

```text
crypto
large JSON/data processing
compression
parsing
search indexing
image processing
audio analysis
astronomical calculations
syntax parsing
Markdown parsing
WASM
machine learning
large mathematical calculations
```

Given the kinds of computational packages you work with, an ephemeris/astronomical calculation engine is actually a very strong candidate for Worker execution when the result does not require synchronous DOM access.

---

# 81. Bad worker use cases

Don't use a worker for:

```text
simple click handler
class toggle
small DOM update
basic validation
single calculation that takes 0.1 ms
```

The communication and architecture overhead won't be justified.

---

# 82. Worker + dynamic import

You can also combine:

```text
IntersectionObserver
        ↓
user approaches chart
        ↓
dynamic import
        ↓
Worker creation
        ↓
heavy calculation off-main-thread
```

This is extremely powerful for expensive optional features.

Example architecture:

```text
Page startup
   ↓
no chart library loaded

Chart becomes near viewport
   ↓
import("./chart.js")

User activates chart
   ↓
Worker created

Dataset processing
   ↓
worker

DOM rendering
   ↓
main thread
```

Now you have optimized:

```text
startup download
+
startup evaluation
+
main-thread CPU
```

rather than trying to solve all three with `will-change`.

---

# 83. Page Visibility API

For background tabs:

```js
document.addEventListener("visibilitychange", () => {
    if (document.hidden) {
        pauseExpensiveWork();
    } else {
        resumeExpensiveWork();
    }
});
```

This is very useful for:

```text
animations
polling
timers
video
canvas
live charts
game loops
background computation
```

The Page Visibility API is widely available, and browsers already throttle many background operations such as timers and `requestAnimationFrame`; explicit pausing is still valuable when the work is under your control. ([MDN Web Docs][39])

---

# 84. Don't rely exclusively on browser throttling

You might think:

> Chrome will throttle background tabs anyway.

That is not the right strategy.

Browser policies differ and some activity remains exempt from some throttling. Explicit lifecycle control is still better:

```js
if (document.hidden) {
    stopPolling();
    stopAnimation();
    stopRenderingCharts();
}
```

The browser's own throttling exists as a safety mechanism; your application's lifecycle should still express its intent. ([MDN Web Docs][39])

---

# 85. Pause polling when hidden

Bad:

```js
setInterval(fetchData, 5000);
```

for an application that continues polling while completely hidden.

Better:

```js
let timer;

function startPolling() {
    timer = setInterval(fetchData, 5000);
}

function stopPolling() {
    clearInterval(timer);
    timer = undefined;
}

document.addEventListener("visibilitychange", () => {
    if (document.hidden) {
        stopPolling();
    } else {
        startPolling();
    }
});
```

This saves:

```text
CPU
network
battery
server load
```

---

# 86. `sendBeacon()`

Analytics should not block page dismissal.

Instead of synchronous/unload-style work:

```js
navigator.sendBeacon("/analytics", data);
```

The Beacon API is designed to send data asynchronously without blocking the page transition. web.dev recommends it for analytics-style delivery. ([web.dev][15])

---

# 87. Prefer `visibilitychange`

For analytics:

```js
document.addEventListener("visibilitychange", () => {
    if (document.visibilityState === "hidden") {
        navigator.sendBeacon("/analytics", payload);
    }
});
```

MDN recommends `visibilitychange` as the primary approach and `pagehide` as a fallback where needed. `unload` is problematic for bfcache and unreliable on some mobile scenarios. ([MDN Web Docs][40])

---

# 88. `fetch(..., {keepalive:true})`

A modern alternative is:

```js
fetch("/analytics", {
    method: "POST",
    body: JSON.stringify(data),
    keepalive: true
});
```

web.dev explicitly identifies `sendBeacon()` and `fetch(..., {keepalive:true})` as non-blocking ways to send data that can outlive the page session. ([web.dev][41])

---

# 89. Back/forward cache — bfcache

bfcache is not ordinary HTTP cache.

It can restore a previous page from memory, making back/forward navigation extremely fast. web.dev notes that `Cache-Control: no-store` can historically affect eligibility, whereas `no-cache` / `max-age=0` do not have that same bfcache restriction. ([web.dev][42])

This means your JavaScript lifecycle matters not just for CPU—but for navigation performance.

---

# 90. Avoid `unload`

`unload` is problematic.

MDN explains that it is incompatible with bfcache in important browser scenarios, and some browsers may not fire it reliably. `beforeunload` can also affect bfcache eligibility, particularly in Firefox. ([MDN Web Docs][40])

Prefer:

```text
visibilitychange
pagehide
pageshow
```

according to the lifecycle event you actually need.

---

# 91. `pageshow` is important for restored pages

A page restored from bfcache may appear instantly from memory rather than being reloaded normally.

If your application needs to refresh state after restoration:

```js
window.addEventListener("pageshow", event => {
    if (event.persisted) {
        refreshStaleState();
    }
});
```

This lets you preserve fast navigation while correcting genuinely stale dynamic data. web.dev explicitly discusses using `pageshow` when bfcache-restored content may need refreshing. ([web.dev][42])

---

# 92. Don't create huge DOM trees from JavaScript

This is one of the most important JS-side performance issues.

Suppose:

```js
for (const item of 10000Items) {
    container.append(createItem(item));
}
```

You can create a large client-side task that:

```text
builds nodes
+
parses HTML
+
updates DOM
+
triggers rendering work
```

web.dev explains that client-side HTML generation can create long tasks and that large DOMs increase rendering and interaction cost. ([web.dev][43])

---

# 93. Server-render HTML when practical

For initial content:

```text
server HTML
    ↓
browser incrementally parses
    ↓
render incrementally
```

can be more efficient than:

```text
empty HTML
    ↓
download JS
    ↓
execute JS
    ↓
generate HTML
    ↓
render everything
```

web.dev specifically notes that HTML delivered during navigation benefits from incremental parsing and automatic opportunities for yielding, while client-generated HTML can form long tasks. ([web.dev][43])

---

# 94. Don't hide important resources behind JavaScript

Bad:

```html
<div id="hero"></div>
```

then:

```js
hero.innerHTML = `
    <img src="/hero.webp">
`;
```

Now the browser cannot discover that image from the original HTML preload scanning path.

web.dev explicitly warns that dynamically inserted LCP resources can introduce avoidable discovery delay. ([web.dev][7])

Prefer:

```html
<img src="/hero.webp" ...>
```

in initial HTML for critical resources.

---

# 95. DOM updates should be batched

Instead of:

```js
for (const item of items) {
    container.appendChild(createItem(item));
}
```

in some scenarios, constructing a fragment first can reduce repeated attachment operations:

```js
const fragment = document.createDocumentFragment();

for (const item of items) {
    fragment.appendChild(createItem(item));
}

container.appendChild(fragment);
```

The deeper principle is:

```text
many tiny DOM writes
        ↓
batch them
        ↓
one larger update
```

The exact benefit depends on the surrounding layout/rendering context, so benchmark pathological cases rather than treating `DocumentFragment` as a magic requirement.

---

# 96. Avoid layout thrashing

This remains one of the most important JS/CSS interactions.

Bad:

```js
for (const element of elements) {
    element.style.width = "500px";

    console.log(element.offsetWidth);
}
```

That can create a repeated:

```text
write
↓
forced layout
↓
read
↓
write
↓
forced layout
↓
read
```

pattern.

A much better architecture is:

```text
READ
READ
READ

WRITE
WRITE
WRITE
```

web.dev specifically identifies forced synchronous layout and layout thrashing as major sources of responsiveness problems. ([web.dev][44])

---

# 97. The classic FastDOM-style mental model

Think:

```js
const measurements = elements.map(
    element => element.getBoundingClientRect()
);

// Now mutate.
for (const [index, element] of elements.entries()) {
    element.style.transform =
        `translateX(${measurements[index].width}px)`;
}
```

instead of interleaving geometry reads with writes.

Again, the key is not that `getBoundingClientRect()` itself is "bad."

It is:

```text
read after a write that invalidated geometry
```

that can force expensive synchronous work.

---

# 98. `getBoundingClientRect()` is not evil

This is another internet myth.

This is fine:

```js
const rect = element.getBoundingClientRect();
```

The problem is using it in a hot loop or after writes that invalidate layout.

Example:

```text
scroll event
 ↓
write style
 ↓
getBoundingClientRect()
 ↓
layout
 ↓
write style
 ↓
getBoundingClientRect()
 ↓
layout
```

That's the pathological pattern.

---

# 99. Use CSS for visual state whenever possible

Instead of:

```js
element.style.display = "none";
element.style.opacity = "0";
element.style.transform = "...";
```

for every frame/state, prefer:

```js
element.classList.toggle("is-open", open);
```

with CSS:

```css
.panel {
    opacity: 0;
    transform: translateY(8px);
}

.panel.is-open {
    opacity: 1;
    transform: translateY(0);
}
```

This isn't merely prettier.

It reduces imperative DOM manipulation and lets the browser handle the rendering model declaratively.

---

# 100. Don't continuously set styles from JavaScript

Bad:

```js
setInterval(() => {
    element.style.transform = ...
    element.style.opacity = ...
    element.style.left = ...
}, 16);
```

For animation:

```text
CSS transition/keyframes
```

or:

```text
requestAnimationFrame + transform
```

are generally more appropriate.

Use JS to determine state, not to constantly micromanage the style system when CSS can perform the animation.

---

# 101. Don't use JavaScript for pure responsiveness

Bad:

```js
window.addEventListener("resize", () => {
    if (window.innerWidth < 768) {
        ...
    }
});
```

for pure visual responsiveness.

Prefer:

```css
@media (...) { ... }
```

or:

```css
@container (...) { ... }
```

Then JS is reserved for behavior that genuinely depends on the condition.

---

# 102. Don't use MutationObserver when a direct hook exists

Bad:

```text
DOM changes
 ↓
MutationObserver notices
 ↓
discover newly-created buttons
 ↓
attach listeners
```

if your application already knows when the component is created.

Prefer:

```js
initializeComponent(element);
```

directly from the component lifecycle.

MutationObserver is best when you **do not control or cannot directly intercept the source of the mutation**.

---

# 103. Don't use ResizeObserver when container queries are enough

Likewise:

```text
element width changed
 ↓
ResizeObserver
 ↓
JS calculates CSS state
```

may be unnecessary when:

```css
@container (...) { ... }
```

can express the entire requirement.

---

# 104. Don't use IntersectionObserver when the browser already has native lazy loading

For:

```html
<img loading="lazy">
<iframe loading="lazy">
```

custom IO isn't necessarily needed just to recreate native browser behavior. ([MDN Web Docs][6])

Use IO for richer behavior.

---

# 105. Debouncing

For events where you care about the **final** state:

```js
let timeout;

input.addEventListener("input", () => {
    clearTimeout(timeout);

    timeout = setTimeout(() => {
        search(input.value);
    }, 250);
});
```

Good for:

```text
search
validation
filtering
autosave
resize-end behavior
analytics
```

---

# 106. Throttling

For events where you need periodic updates:

```js
function throttle(fn, interval) {
    let last = 0;

    return (...args) => {
        const now = performance.now();

        if (now - last >= interval) {
            last = now;
            fn(...args);
        }
    };
}
```

Good for:

```text
telemetry
non-visual scroll metrics
drag calculations
network updates
```

But for visual updates, `requestAnimationFrame()` is usually more appropriate than arbitrary millisecond throttling.

---

# 107. Better than a generic throttle for rendering

Instead of:

```js
throttle(updateUI, 16)
```

use:

```js
requestAnimationFrame(updateUI)
```

because the latter coordinates the update with the browser's rendering cadence. ([MDN Web Docs][20])

---

# 108. Cache DOM references

Bad:

```js
function update() {
    document.querySelector(".header .logo").textContent = title;
}
```

every time in a hot path.

Better:

```js
const logo = document.querySelector(".header .logo");

function update() {
    logo.textContent = title;
}
```

This is not usually your biggest optimization, but it helps reduce repeated DOM queries in hot code.

The larger benefit is architectural:

```text
find DOM once
        ↓
reuse reference
```

---

# 109. Avoid repeatedly traversing the DOM

Bad:

```js
document.querySelectorAll(".card").forEach(...)
```

inside a repeatedly firing event.

Better:

```js
const cards = document.querySelectorAll(".card");
```

once when practical.

Or use event delegation for highly dynamic structures.

---

# 110. Use `WeakMap`/`WeakSet` for associated component metadata

Example:

```js
const state = new WeakMap();

state.set(element, {
    initialized: true
});
```

This can be useful when associating metadata with DOM elements without maintaining a separate collection whose lifetime you have to manage manually.

It is especially useful for component infrastructure:

```text
DOM node
   ↓
state / controller / cleanup metadata
```

The important performance principle is lifecycle-aware data ownership rather than blindly preferring one collection type.

---

# 111. Clean up observers

When a component is destroyed:

```js
observer.disconnect();
```

or:

```js
observer.unobserve(element);
```

Otherwise you may keep unnecessary monitoring alive.

The same goes for:

```text
event listeners
intervals
timeouts
observers
workers
streams
WebSockets
AbortControllers
```

Every resource should have a lifecycle.

---

# 112. Component lifecycle pattern

A very strong architecture is:

```js
function mountComponent(element) {
    const controller = new AbortController();

    const observer = new ResizeObserver(...);
    observer.observe(element);

    element.addEventListener("click", handleClick, {
        signal: controller.signal
    });

    return () => {
        controller.abort();
        observer.disconnect();
    };
}
```

Now:

```text
mount
 ↓
resources allocated

unmount
 ↓
cleanup function
 ↓
resources released
```

This becomes particularly important in SPAs and dynamic interfaces.

---

# 113. Don't repeatedly create observers during rerenders

Bad:

```js
function render() {
    const observer = new IntersectionObserver(...);
    observer.observe(element);
}
```

if `render()` runs dozens of times.

You may accidentally create:

```text
observer 1
observer 2
observer 3
observer 4
...
```

Use stable lifecycle-managed instances.

---

# 114. Don't repeatedly create Workers

Similarly:

```js
function calculate() {
    const worker = new Worker("/worker.js");
    ...
}
```

for every tiny calculation can create unnecessary startup and communication overhead.

For repeated tasks:

```text
create worker
 ↓
send jobs
 ↓
reuse worker
 ↓
terminate when no longer needed
```

unless worker startup isolation itself is intentional.

---

# 115. Network concurrency isn't infinite

This pattern:

```js
await Promise.all(
    urls.map(url => fetch(url))
);
```

can launch a huge number of requests.

For 5 requests:

```text
reasonable
```

For 5000:

```text
possibly terrible
```

You can create:

```text
network contention
memory pressure
server pressure
CPU overhead
queueing
```

A concurrency limiter can be better.

---

# 116. Example bounded concurrency

Conceptually:

```js
const queue = [...urls];
const concurrency = 4;

async function worker() {
    while (queue.length) {
        const url = queue.shift();

        if (!url) {
            return;
        }

        await fetch(url);
    }
}

await Promise.all(
    Array.from({ length: concurrency }, worker)
);
```

The actual ideal concurrency should depend on the workload.

Don't assume:

```text
more parallelism = faster
```

---

# 117. Use streaming instead of waiting for everything

For large responses:

```js
const response = await fetch("/large-data");

const reader = response.body.getReader();

while (true) {
    const {done, value} = await reader.read();

    if (done) {
        break;
    }

    processChunk(value);
}
```

This can let you process large data incrementally rather than:

```text
download entire object
 ↓
parse entire object
 ↓
process entire object
```

which can produce a giant burst of main-thread work.

Streaming is especially useful for:

```text
large JSON-like protocols
files
AI output
logs
HTML
server-sent data
```

---

# 118. Don't `JSON.parse()` giant payloads on the main thread casually

This:

```js
const data = JSON.parse(hugeString);
```

can produce a substantial synchronous task.

For large data:

```text
streaming
worker
server-side shaping
pagination
incremental processing
```

may be more appropriate.

---

# 119. Minification matters

Production JS should normally be:

```text
minified
compressed
cacheable
code-split
```

Minification reduces transferred code size, and reducing JavaScript payload can also reduce subsequent parsing/compilation cost. MDN explicitly lists minification and deferred/non-critical loading as JavaScript performance techniques. ([web.dev][45])

---

# 120. Tree shaking

With ES modules:

```js
import { foo } from "./library.js";
```

build tools can potentially remove unused exports.

This is one of the reasons static imports are advantageous for initial dependencies: static structure gives tooling more opportunity for analysis and tree shaking. MDN explicitly contrasts static imports with dynamic imports in this respect. ([MDN Web Docs][26])

---

# 121. Avoid giant utility imports

Bad:

```js
import * as Utils from "./everything.js";
```

when you only need:

```js
formatDate
```

Prefer:

```js
import { formatDate } from "./date.js";
```

provided your build architecture supports effective tree shaking.

---

# 122. Third-party JavaScript is particularly expensive

A third-party script has multiple costs:

```text
DNS
connection
download
parse
compile
execute
DOM interaction
network requests
event listeners
```

web.dev explicitly calls out third-party scripts as a source of long tasks and main-thread contention. ([web.dev][46])

Audit:

```text
analytics
chat widgets
ads
A/B testing
social embeds
heatmaps
marketing pixels
```

and remove anything no longer necessary.

---

# 123. Don't load a library just because one function is useful

Bad:

```text
500 KB library
 ↓
need 3 KB of functionality
```

Possible alternatives:

```text
native browser API
smaller library
tree-shakable package
custom implementation
dynamic chunk
```

But don't reinvent complex functionality solely to save 2 KB when maintenance cost is much higher.

---

# 124. Startup JavaScript deserves special treatment

During startup, the user often wants:

```text
page visible
page interactive
```

not:

```text
all application features initialized
```

The optimization strategy should therefore be:

```text
startup
 ├── critical UI
 ├── essential interaction
 └── everything else deferred
```

web.dev's current guidance emphasizes reducing startup JavaScript because parsing, compilation, and execution all consume main-thread capacity. ([web.dev][27])

---

# 125. An excellent startup sequence

Conceptually:

```text
HTML arrives
    ↓
critical CSS
    ↓
critical JS
    ↓
first usable UI
    ↓
user can interact
    ↓
load secondary feature
    ↓
idle work
    ↓
background work
```

Not:

```text
HTML
 ↓
initialize entire application
 ↓
initialize every widget
 ↓
load everything
 ↓
do analytics
 ↓
build cache
 ↓
index everything
 ↓
finally become responsive
```

# 126. "DOMContentLoaded" is not a performance strategy

Some older applications do:

```js
document.addEventListener(
    "DOMContentLoaded",
    initializeEverything
);
```

This is better than executing against a DOM that doesn't exist, but if `initializeEverything()` takes 600 ms, you've simply created a giant startup task.

The event itself isn't the optimization.

**What happens inside the handler** matters.

---

# 127. Don't make one giant initialization function

Bad:

```js
function initializeEverything() {
    initNavigation();
    initSearch();
    initCharts();
    initGallery();
    initMaps();
    initAnimations();
    initAnalytics();
    initEditor();
    initComments();
    initEverythingElse();
}
```

Instead:

```text
critical initialization
↓
render
↓
secondary initialization
↓
idle/background
```

You can schedule different groups appropriately.

---

# 128. Priority-oriented initialization

For browsers supporting `scheduler`:

```js
scheduler.postTask(
    () => initCriticalInteraction(),
    { priority: "user-blocking" }
);

scheduler.postTask(
    () => initVisibleWidgets(),
    { priority: "user-visible" }
);

scheduler.postTask(
    () => initAnalytics(),
    { priority: "background" }
);
```

That expresses intent more clearly than a chain of arbitrary `setTimeout()` calls. ([MDN Web Docs][1])

---

# 129. Yield giant loops

Bad:

```js
for (const item of 1000000Items) {
    process(item);
}
```

Better conceptually:

```js
async function process(items) {
    for (let i = 0; i < items.length; i++) {
        process(items[i]);

        if (i % 500 === 0) {
            if ("scheduler" in globalThis) {
                await scheduler.yield();
            } else {
                await new Promise(resolve => setTimeout(resolve, 0));
            }
        }
    }
}
```

The exact chunk size should be measured.

The principle is:

```text
large synchronous task
        ↓
smaller tasks
        ↓
browser gets opportunities to handle input/rendering
```

web.dev explicitly recommends breaking long work into separate tasks. ([web.dev][19])

---

# 130. But don't over-yield

This can also be bad:

```js
for (...) {
    await scheduler.yield();
}
```

You may turn a fast calculation into enormous scheduling overhead.

The goal is:

```text
enough work per chunk
+
enough opportunities to yield
```

not:

```text
yield as often as physically possible
```

# 131. CSS + JS + Observer architecture

A modern component could look like:

```text
Component
│
├── CSS
│   ├── containment
│   ├── content-visibility
│   └── transitions
│
├── IntersectionObserver
│   └── lazy initialization

├── ResizeObserver
│   └── logic based on actual size

│   ├── events
│   └── fetch
│

│   └── visual updates
```

This is substantially more sophisticated than:

```text
component

```

# 132. Example: lazy chart component

Imagine:

```html
<section class="chart" data-chart="sales">
    ...
</section>
```

A strong architecture could be:

```js
const observer = new IntersectionObserver(async entries => {
    for (const entry of entries) {
        if (!entry.isIntersecting) {
            continue;
        }

        observer.unobserve(entry.target);

        const { initializeChart } =
            await import("./chart.js");

        initializeChart(entry.target);
    }
}, {
    rootMargin: "500px 0px"
});

document
    .querySelectorAll("[data-chart]")
    .forEach(element => observer.observe(element));
```

Now:

```text
startup
↓
no chart library

chart gets near viewport
↓
dynamic import

library loaded
↓
chart initialized
```

This reduces startup work and avoids downloading the feature if the user never reaches it. Dynamic imports are a standard code-splitting mechanism. ([web.dev][27])

# 133. Example: lazy image with native loading

Prefer:

```html
<img
    loading="lazy"
    src="/photo.webp"
    width="1200"
    height="800"
    alt="..."
>
```

over recreating the browser's functionality in JavaScript.

For custom image behavior:

```text
IntersectionObserver
    +
src/srcset assignment
```

can still be appropriate.

But don't use JavaScript to hide an important LCP resource from the preload scanner. ([web.dev][7])

# 134. Example: cancellable search

Combine:

```text
debounce
+
AbortController
+
small result rendering
```

```js
let timeout;
let controller;

input.addEventListener("input", () => {
    clearTimeout(timeout);

    timeout = setTimeout(async () => {
        controller?.abort();

        controller = new AbortController();

        try {
            const response = await fetch(
                `/api/search?q=${encodeURIComponent(input.value)}`,
                {
                    signal: controller.signal
                }
            );

            const results = await response.json();

            renderResults(results);
        } catch (error) {
            if (error.name !== "AbortError") {
                throw error;
            }
        }
    }, 200);
});
```

This prevents both:

```text
too many requests
```

and:

```text
stale requests finishing after newer requests
```

# 135. Example: visibility-aware animation

```js
let animationFrame;

function animate(timestamp) {
    render(timestamp);
    animationFrame = requestAnimationFrame(animate);
}

function start() {
    if (animationFrame == null) {
        animationFrame = requestAnimationFrame(animate);
    }
}

function stop() {
    if (animationFrame != null) {
        cancelAnimationFrame(animationFrame);
        animationFrame = null;
    }
}

document.addEventListener("visibilitychange", () => {
    if (document.hidden) {
        stop();
    } else {
        start();
    }
});
```

Browsers often pause `requestAnimationFrame` in background tabs anyway, but explicit lifecycle handling prevents your surrounding application logic from continuing unnecessarily. ([MDN Web Docs][39])

# 136. Example: PerformanceObserver-based field telemetry

```js
if (
    PerformanceObserver.supportedEntryTypes.includes(

    const observer = new PerformanceObserver(list => {
        for (const entry of list.getEntries()) {

                startTime: entry.startTime

    observer.observe({
        type: "long-animation-frame",

}
```

Then combine this with:

```text
page URL
device class
interaction
route
component
connection
```

to identify real-world performance problems.

Don't collect everything blindly; web.dev explicitly advises measuring only data that you actually intend to use, because telemetry itself consumes resources. ([web.dev][47])

# 137. `performance.mark()` and `performance.measure()`

```js
performance.mark("editor-start");

initializeEditor();

performance.mark("editor-end");

performance.measure(
    "editor-initialization",
    "editor-start",
    "editor-end"

```

Then observe:

```js
const observer = new PerformanceObserver(list => {

```

This lets you answer:

```text

How slow?
On which route?
Before or after interaction?
```

rather than guessing.

`PerformanceObserver` supports these performance entry mechanisms directly. ([MDN Web Docs][48])

# 140. Service Worker — powerful, but not automatically necessary

Service Workers can provide:

```text
offline behavior
runtime caching
pre-caching
stale-while-revalidate
network fallback
application-shell caching
```

The Cache Storage API gives you fine-grained control, but a service worker also adds complexity and lifecycle concerns. web.dev contrasts HTTP caching with service-worker strategies and notes that service workers are useful when you need custom cache control. ([web.dev][49])

Don't add one solely because:

> "service workers make websites faster."

They can also make cache invalidation harder.

# 141. Prefer HTTP caching before inventing a JS cache

For static assets:

```text
Cache-Control
ETag
immutable hashed filenames
CDN
Brotli
HTTP/2 / HTTP/3
```

are often a better foundation.

Then consider:

```text
Service Worker CacheStorage
```

when you require application-specific caching logic.

# 142. `stale-while-revalidate`

For content where slightly stale data is acceptable:

```http
Cache-Control: max-age=60, stale-while-revalidate=300
```

can allow cached content to be returned immediately while revalidation occurs in the background.

web.dev documents this specifically as a balance between freshness and responsiveness. ([web.dev][50])

Good candidates:

```text
news
weather
frequently refreshed content
non-critical APIs
```

Not:

```text
financial transaction state
security-sensitive authorization state
one-time actions
```

without careful semantics.

# 143. Storage APIs and performance

Avoid synchronous storage in hot paths:

```js
localStorage.getItem(...)
localStorage.setItem(...)
```

These APIs are synchronous.

web.dev notes that among common browser storage options, in-memory storage and `localStorage` are synchronous, while options such as IndexedDB are asynchronous. ([web.dev][51])

So don't do:

```js
window.addEventListener("scroll", () => {
    localStorage.setItem(...)
});
```

That is exactly the kind of unnecessary synchronous work you should avoid.

---

# 144. Use IndexedDB for larger async application data

For:

```text
large datasets
offline data
structured client-side storage
cacheable application state
```

IndexedDB is usually more suitable than repeatedly using synchronous Web Storage.

For tiny configuration:

```text
localStorage
```

can still be perfectly appropriate.

Again, the issue is not:

```text
localStorage bad
IndexedDB good
```

but:

```text
synchronous hot-path work
    = dangerous
```

# 145. Memory is performance

You should consider:

```text
DOM nodes
event listeners
closures
arrays
caches
observers
workers
decoded images
canvas buffers
WebGL resources
```

as runtime resources.

A page that slowly leaks memory may eventually become a performance problem even if the first 30 seconds look perfect.

# 146. Common memory-leak pattern

```js
const elements = [];

function mount() {
    const element = document.createElement("div");

    elements.push(element);
}
```

If those references remain indefinitely:

```text
removed from DOM
BUT
still referenced by array
        ↓
cannot be garbage collected
```

Lifecycle management matters.

# 147. Another common leak

```js
window.addEventListener("resize", handler);
```

for a component that is removed later—but the listener remains attached to `window`.

The component's closure may still retain:

```text
DOM
state
large objects
```

Use `AbortSignal` or explicit cleanup. ([MDN Web Docs][21])

# 148. Another leak: observers

```js
const observer = new MutationObserver(...);
observer.observe(element, ...);

// element removed...
```

If the observer itself remains active unnecessarily, you've kept infrastructure alive.

Clean up:

```js
observer.disconnect();
```

The same principle applies to all observers.

# 149. Loading strategy: a complete modern model

Think about every feature using this sequence:

```text
                  FEATURE
                     │
            Is it needed at startup?
                  /     \
                yes      no
                │         │
             load now   defer
                          │
                  Is user likely to use it?
                       /       \
                     yes        no
                     │           │
                  prepare     keep unloaded
                     │
              Is it near viewport?
                /          \
              yes           no
              │             │
           load now       wait
              │
       Is it CPU-heavy?
          /         \
        yes          no
        │             │
      Worker       main thread
```

This is much more useful than memorizing individual APIs.

# 150. Resource loading hierarchy

For an asset or feature:

```text
1. Is it unnecessary?
       ↓
   remove it

2. Is it needed eventually but not now?
       ↓
   lazy-load it

3. Is it needed soon?
       ↓
   preload / modulepreload / preconnect

4. Is it the most important resource?
       ↓
   consider fetchpriority

5. Is it for a likely future navigation?
       ↓
   prefetch / speculation rules

6. Is it almost certain to be the next navigation?
       ↓
   carefully consider prerender
```

Resource hints are intentionally advisory and should be used based on likely resource importance. ([web.dev][52])

---

# 151. The biggest loading mistake

This:

```text
"Load everything as early as possible."
```

is wrong.

Because:

```text
bandwidth is finite
CPU is finite
memory is finite
```

If you load ten "important" things simultaneously, they compete.

The correct philosophy is:

```text
Load the right thing
at the right time
with the right priority.
```

web.dev's resource-priority guidance explicitly emphasizes contention between resources. ([web.dev][7])

---

# 152. The biggest observer mistake

This:

```text
"Observers are performant, therefore observer callbacks can be heavy."
```

is wrong.

The observer gives you a better **triggering mechanism**.

It does not make this cheap:

```js
new IntersectionObserver(() => {
    process100000Nodes();
});
```

The callback still runs JavaScript.

Likewise:

```text
ResizeObserver
MutationObserver
PerformanceObserver
```

all require sensible callback design.

---

# 153. The biggest async mistake

This:

```text
"async = fast"
```

is wrong.

`async` changes scheduling/loading behavior.

It doesn't reduce the amount of work.

Likewise:

```text
dynamic import
worker
requestIdleCallback
setTimeout
```

can relocate work without eliminating it.

The fundamental question is:

```text
How much work?
When?
Where?
How often?
Can it be canceled?
```

---

# 154. The biggest Worker mistake

This:

```text
"Put everything in a worker."
```

is wrong.

Workers are excellent for:

```text
CPU-heavy independent computation
```

but inappropriate for:

```text
DOM manipulation
tiny operations
work requiring synchronous UI access
```

And communication has a cost. ([web.dev][38])

---

# 155. The biggest `requestIdleCallback` mistake

This:

```text
"Idle means immediately."
```

wrong.

Idle means:

```text
when the browser happens to have an opportunity
```

It can be delayed.

Therefore:

```js
requestIdleCallback(work, { timeout: 2000 });
```

is more appropriate for work that is non-urgent but eventually required. ([MDN Web Docs][34])

---

# 156. The biggest microtask mistake

This:

```js
queueMicrotask(heavyWork);
```

is not a performance optimization if:

```text
heavyWork
```

blocks the next rendering opportunity.

Microtasks run before the browser proceeds to normal rendering opportunities, and recursively creating microtasks can starve the event loop. ([MDN Web Docs][11])

---

# 157. The most useful combined architecture

For a complex modern application:

```text
                         HTML
                          │
                 Critical resources
                          │
                 Minimal startup JS
                          │
                Initial UI interactive
                          │
        ┌─────────────────┼─────────────────┐
        │                 │                 │
 IntersectionObserver  User action     Idle scheduler
        │                 │                 │
 lazy feature          dynamic import     background work
        │                 │                 │
        └──────────────┬──┴─────────────────┘
                       │
                 Expensive feature
                       │
                ┌──────┴──────┐
                │             │
             main thread    Worker
                │             │
              DOM/UI       CPU work
                │             │
                └──────┬──────┘
                       │
                PerformanceObserver
                       │
```

# 171. The ultimate decision framework

```text

remove dependency

```

### 2. Can I delay it?

```text

dynamic import
IntersectionObserver
idle scheduling
```

### 3. Can I avoid doing it repeatedly?

```text

caching
event delegation
observer reuse
batching
```

### 4. Can I make it smaller?

```text
smaller bundle
smaller DOM
smaller response
smaller image
```

### 5. Can I move it off the main thread?

```text
Worker
```

### 6. Can I yield between chunks?

```text
scheduler.yield
setTimeout fallback
```

### 7. Can I cancel it?

```text

cleanup
unobserve
```

### 8. Can CSS/HTML/browser do it instead?

```text

native lazy loading
container queries
resource hints
```

### 9. Did the optimization actually improve the measured problem?

```text
DevTools
field data
INP
LoAF
network waterfall
```

Only after that should you keep the optimization.

# 173. My recommended baseline for a modern site

For a modern developer portfolio or content-heavy site, I would generally start with:

```html
<!-- Critical JavaScript -->
<script
    type="module"
    src="/assets/app.js"
></script>

<!-- Critical LCP image -->
<img
    src="/assets/hero.webp"
    width="1600"
    height="900"
    fetchpriority="high"
    alt="..."
>

<!-- Non-critical images -->
<img
    src="/assets/project.webp"
    width="1200"
    height="800"
    loading="lazy"
    alt="..."
>
```

Then JavaScript:

```js
// Lazy expensive components.
const observer = new IntersectionObserver(
    async entries => {
        for (const entry of entries) {
            if (!entry.isIntersecting) {
                continue;
            }

            observer.unobserve(entry.target);

            const { init } = await import(
                "./components/heavy-widget.js"
            );

            init(entry.target);
        }
    },
    {
        rootMargin: "400px 0px"
    }
);
```

Then:

```js
// Pause non-essential work when hidden.
document.addEventListener("visibilitychange", () => {
    if (document.hidden) {
        stopNonEssentialWork();
    } else {
        resumeNonEssentialWork();
    }
});
```

And for expensive computation:

```text
main thread
    ↓
Worker
    ↓
result
    ↓
small DOM update
```

And for measurement:

```js
if (
    PerformanceObserver.supportedEntryTypes.includes(
        "long-animation-frame"
    )
) {
    new PerformanceObserver(list => {
        for (const entry of list.getEntries()) {
            reportLoAF(entry);
        }
    }).observe({
        type: "long-animation-frame",
        buffered: true
    });
}
```

# 175. The core rules I would actually memorize

```text
1. Ship less JavaScript.
2. Execute less JavaScript.
3. Execute non-critical JavaScript later.
4. Don't block the main thread.
5. Break long tasks into smaller tasks.
6. Use workers for genuinely CPU-heavy independent work.
7. Cancel obsolete asynchronous work.
8. Use IntersectionObserver for visibility-triggered behavior.
9. Use ResizeObserver for genuine element-size logic.
10. Use MutationObserver only when mutation observation is actually required.
11. Use requestAnimationFrame for visual updates.
12. Use idle scheduling only for work that can wait.
13. Use scheduler.postTask/yield where supported and useful.
14. Don't confuse microtasks with yielding.
15. Don't recreate browser-native lazy loading unnecessarily.
16. Don't hide important LCP resources behind JavaScript.
17. Don't preload everything.
18. Don't mark everything high priority.
19. Don't prerender everything.
20. Don't create giant client-side DOM trees unnecessarily.
21. Don't mix DOM reads and writes in hot paths.
22. Pause unnecessary work when the page is hidden.
23. Preserve bfcache eligibility.
24. Measure INP and long animation frames.
25. Optimize the bottleneck you measured—not the API you happen to know.
```

The particularly important conceptual chain is:

```text
                    PERFORMANCE
                         │
              ┌──────────┴──────────┐
              │                     │
           LOAD LESS             DO LESS
              │                     │
      code splitting         lazy loading
      dynamic import         visibility
      priority               cancellation
      prefetch               batching
              │                     │
              └──────────┬──────────┘
                         │
                     BLOCK LESS
                         │
              ┌──────────┼──────────┐
              │          │          │
            yield      worker      rAF
            tasks      thread      frames
              │          │          │
              └──────────┼──────────┘
                         │
                      MEASURE
                         │
               PerformanceObserver
                     INP / LoAF
```

That is the JavaScript equivalent of the CSS model from your previous question:

```text
CSS:
    content-visibility → skip work
    contain            → isolate work
    transform/opacity  → cheaper animation
    will-change        → prepare selectively

JS:
    observer           → trigger only when relevant
    dynamic import     → load only when needed
    scheduler          → run at appropriate priority
    worker             → move heavy computation
    AbortController    → cancel obsolete work
    rAF                → align visual updates
    visibility API     → stop unnecessary background work
    PerformanceObserver→ prove where the problem is
```

### The current APIs worth paying special attention to

Some of the most important modern additions that weren't part of the older "JavaScript performance tips" era are **Long Animation Frames**, **Prioritized Task Scheduling (`scheduler.postTask()` / `scheduler.yield()`)**, **Speculation Rules**, and **`import defer`**. Their support levels differ, so these should generally be treated as progressive enhancements rather than assumptions of universal browser support. ([web.dev][15])

And the most important practical rule remains: **don't add performance APIs because they sound advanced. Add them because you can identify a specific class of work they prevent, defer, isolate, move, or cancel—and then verify that the resulting page is actually better.** Current web performance guidance consistently emphasizes measurement, especially real-user responsiveness, rather than optimization by folklore.
