# JS-Side Performance: Observers, Scheduling, Workers, and Loading

The companion to the CSS rendering-performance guide. Where that guide covers *what the browser skips rendering*, this one covers *how your JavaScript detects, defers, schedules, and offloads work* so the main thread stays free to respond to the user. Same spirit: what each API does, exactly when to reach for it, and where it bites you.

---

## 1. The main thread is the bottleneck — orient around that

Almost everything below exists to answer one of three questions:

1. **"Do I need to know about this right now?"** → Observer APIs (Intersection/Resize/Mutation/Performance) replace polling loops and synchronous measurement with async, browser-scheduled notifications.
2. **"When should this code run?"** → Scheduling APIs (`requestAnimationFrame`, `requestIdleCallback`, `scheduler.postTask`/`scheduler.yield`) place work at the right point in the event loop instead of running it immediately and blocking.
3. **"Does this even need to run on the main thread?"** → Web Workers, `OffscreenCanvas`, and resource hints move work off the thread that handles input, layout, and paint entirely, or move it earlier/later in time.

A **long task** is any single uninterrupted chunk of main-thread work lasting 50ms or more. That threshold isn't arbitrary — it comes from the RAIL model's reasoning that a response feels instant within roughly 100ms, and the browser itself needs about half of that budget for input dispatch, style recalc, and paint, leaving roughly 50ms as the largest chunk of pure script work that won't register as a delay. Interaction to Next Paint (INP), the current Core Web Vital for responsiveness, is essentially a measure of how often your long tasks get in the way of user input.

## 2. Observer APIs — replacing polling with browser-native notifications

The pre-observer way of answering "has this element scrolled into view / changed size / had its DOM mutated" was to attach a `scroll`/`resize` listener and call `getBoundingClientRect()` or similar synchronously, over and over, on the main thread. Every one of the observers below exists to move that measurement off the hot path and into an async, browser-scheduled callback.

### 2.1 `IntersectionObserver` — visibility, without scroll listeners

**What it does:** asynchronously reports when a target element's visibility relative to a root (default: the viewport) crosses one or more thresholds, without any synchronous geometry queries in your code.

```js
const observer = new IntersectionObserver(
  (entries, obs) => {
    entries.forEach((entry) => {
      if (!entry.isIntersecting) return;
      const img = entry.target;
      img.src = img.dataset.src;
      obs.unobserve(img); // stop watching once handled
    });
  },
  {
    root: null,       // null = the viewport
    rootMargin: '200px', // start reacting 200px before it's actually visible
    threshold: 0,      // fire as soon as 1px is visible
  }
);

document.querySelectorAll('img[data-src]').forEach((img) => observer.observe(img));
```

**Options that matter:**
- `root` — the ancestor used as the viewport for intersection checks; `null` means the browser viewport, but you can pass a scrollable container for intersection within, say, a scrollable sidebar.
- `rootMargin` — grows or shrinks the root's bounding box before intersection is computed. A positive value (`"200px"`) triggers callbacks *before* the element is actually visible — this is how you get a head start on loading.
- `threshold` — a number (or array of numbers) between 0 and 1 representing what fraction of the target must be visible before firing. `[0, 0.5, 1]` fires at 0%, 50%, and 100% visible.
- `trackVisibility` (with a required `delay`) — additionally verifies the target isn't obscured or visually distorted by opacity/filters/transforms before counting it as visible. This is computationally expensive by design, so only use it when true "was it actually seen" accuracy matters (e.g., ad viewability).

**Use cases:**
- **Lazy-loading images/iframes/video posters below the fold**, with `rootMargin` providing a preload head start.
- **Infinite scroll** — observe a small sentinel element at the bottom of a list; when it intersects, fetch and append the next page. Far cleaner than scroll-position math.
- **Deferring expensive work** — pause/resume canvas animations, video playback, or WebGL loops based on actual visibility rather than a scroll listener's approximation.
- **Scroll-triggered animations** — toggle a CSS class when an element enters view (combine with `prefers-reduced-motion` checks).
- **Ad viewability / analytics** — measuring how long an element was actually on screen.
- **Scrollspy navigation** — tracking which section is currently in view to highlight the matching nav link.

**Gotchas:**
- Always call `unobserve()` (or `disconnect()` for the whole observer) once you no longer need updates for a target — an unbounded set of live observers is a real memory/CPU cost, and a common bug is forgetting to unobserve after a one-time lazy-load, which leaves the callback firing every time the element re-enters the viewport for no reason.
- For plain `<img>`/`<iframe>` lazy loading with no extra logic, prefer the native `loading="lazy"` attribute (see §6) over rolling your own observer — reach for `IntersectionObserver` when you need more control than the browser default gives you (loading a whole component, swapping a poster image, starting an expensive render).
- Intersection callbacks are themselves async and can be delayed under load — don't use this API for anything that needs guaranteed-immediate synchronous confirmation.

### 2.2 `ResizeObserver` — element size, without window-resize hacks

**What it does:** reports changes to an element's content-box, border-box, or (for SVG) bounding-box size — including size changes that have nothing to do with the viewport (a sidebar collapsing, a flex sibling growing, a font swap changing text metrics).

```js
const resizeObserver = new ResizeObserver((entries) => {
  for (const entry of entries) {
    const sidebar = entry.target;
    const width = entry.contentBoxSize[0].inlineSize;
    redrawChart(sidebar, width);
  }
});
resizeObserver.observe(document.querySelector('.chart-container'));
```

**Use cases:**
- Charts, `<canvas>` drawings, or maps that must redraw when their container resizes for any reason (not just window resize — a CSS Grid track changing, a flex item's siblings appearing/disappearing).
- Responsive components that need to make layout decisions based on their *own* rendered size rather than a media query on the viewport (this is the foundation container queries are conceptually built on, though CSS `@container` now covers a lot of the pure-styling version of this use case).
- Sticky panels or custom scroll areas that must reflow after their container's dimensions change.

**Gotchas:**
- A `ResizeObserver loop completed with undelivered notifications` warning/error happens when your callback itself changes the observed element's size, creating a feedback loop within the same frame. The browser detects this, warns, and settles it — but the fix is to defer the resizing logic inside your callback to *after* the next repaint, typically by wrapping it in `requestAnimationFrame`.
- Don't reach for it as a `window.resize` replacement when you only actually care about viewport size — a plain `resize` listener (ideally debounced) or a CSS media query is simpler and cheaper for that narrower case.

### 2.3 `MutationObserver` — DOM changes, without event-spam hacks

**What it does:** watches a subtree for additions/removals of nodes, attribute changes, or character-data changes, and reports them in a single batched callback rather than firing per-mutation.

```js
const observer = new MutationObserver((mutations) => {
  for (const mutation of mutations) {
    if (mutation.type === 'childList') {
      mutation.addedNodes.forEach((node) => {
        if (node.nodeType === Node.ELEMENT_NODE) handleNewComment(node);
      });
    }
  }
});
observer.observe(document.querySelector('#comments'), {
  childList: true,
  subtree: true,
  attributes: false,
});
```

**Use cases:**
- Reacting to DOM changes injected by third-party scripts or widgets you don't control (ad slots, chat widgets, CMS-injected content).
- Building framework-agnostic component libraries that need to detect when their host node's children change.
- Detecting content injected after a route change in non-SPA-aware analytics tooling.

**Gotchas:**
- **This is the wrong tool for size changes.** A common mistake is watching `style`/`class` attribute mutations to infer a size change — that only catches direct attribute edits, and misses the overwhelming majority of real resizes (caused by content reflow, sibling changes, font loading, etc.). Use `ResizeObserver` for size; use `MutationObserver` only for actual DOM structure/attribute/text changes.
- `subtree: true` on a large, frequently-changing tree (e.g., the `<body>` of a chat app) can itself become a performance liability — scope the observed node as narrowly as you can.
- Always `disconnect()` when the relevant component unmounts or the watch is no longer needed; a forgotten observer keeps its callback (and everything the closure references) alive.

### 2.4 `PerformanceObserver` — the browser's own timing data

**What it does:** subscribes to entries on the Performance Timeline — marks/measures you create yourself, but also browser-native entry types like `longtask`, `largest-contentful-paint`, `layout-shift`, `event` (for INP), `resource`, `paint`, and more.

```js
const observer = new PerformanceObserver((list) => {
  list.getEntries().forEach((entry) => {
    if (entry.duration > 50) {
      reportToRUM({ name: entry.name, duration: entry.duration, start: entry.startTime });
    }
  });
});
observer.observe({ type: 'longtask', buffered: true }); // buffered: true also gets entries recorded before this call
```

**Use cases:**
- **Long Tasks API (`entryType: "longtask"`)** — flags any main-thread block ≥50ms, the single most direct signal for diagnosing poor INP. The newer **Long Animation Frames (LoAF) API** (`entryType: "long-animation-frame"`) supersedes it for INP work specifically, since it additionally attributes blocking time to scripts and breaks a frame's work down by phase.
- Custom `mark`/`measure` instrumentation for your own app-specific timings (e.g., "time from click to data rendered").
- Feeding real-user-monitoring (RUM) pipelines with `largest-contentful-paint`, `layout-shift`, and `event` entries to compute Core Web Vitals from real traffic rather than lab conditions.

**Gotchas:**
- `longtask` entries currently attribute the *container* (top-level page vs. a specific iframe) responsible via `TaskAttributionTiming`, but pinpointing the exact script/function inside a long task is still coarse compared to a DevTools trace — treat it as a signal for *where to look*, not a full profiler replacement.
- Set `buffered: true` when you want entries that were recorded before your observer was registered (useful for catching long tasks that happened very early in page load, before your monitoring script had a chance to attach).

## 3. Scheduling APIs — choosing *when* code runs

Four different tools, four different timing guarantees. The mistake most people make is picking the one they've heard of (usually `setTimeout` or `requestAnimationFrame`) regardless of fit.

| API | Runs... | Best for | Key caveat |
|---|---|---|---|
| `requestAnimationFrame` | Right before the next repaint, synced to the display's refresh rate | Visual updates: animations, layout reads/writes you want batched with the browser's own paint cycle | Runs *every* frame while scheduled — don't use it for background work; it competes with actual rendering |
| `requestIdleCallback` | Only during genuinely idle time, after input handling and rendering are done | Strictly non-urgent background work: analytics batching, prefetching, speculative pre-rendering | May be delayed indefinitely under sustained load, and may never run before page unload — never put user-visible or correctness-critical work here; pass a `timeout` option if it must eventually run |
| `scheduler.postTask()` | User-specified priority (`user-blocking`, `user-visible`, `background`), scheduled accordingly | Explicit-priority task scheduling with cancellation/delay support — the modern, unified replacement for the ad hoc mix of `setTimeout`/`postMessage`/`requestIdleCallback` | Newer API; verify current browser support before depending on it as your only code path |
| `scheduler.yield()` | Yields control back to the browser mid-task, resumes as the next queued task | Breaking up a long synchronous loop so input/paint can interleave, while preserving your function's continuation (no manual state-passing needed) | Not supported in Safari as of recent checks — feature-detect and fall back |

```js
// requestAnimationFrame — for anything the user should see move smoothly
function animate(time) {
  el.style.transform = `translateX(${computeX(time)}px)`;
  requestAnimationFrame(animate);
}
requestAnimationFrame(animate);

// requestIdleCallback — for slicing non-urgent background work
requestIdleCallback((deadline) => {
  while (deadline.timeRemaining() > 1 && tasks.length) {
    processOneTask(tasks.shift());
  }
}, { timeout: 2000 });

// scheduler.yield — breaking a long loop into cooperative chunks (feature-detect first)
async function processLargeList(items) {
  for (const item of items) {
    processItem(item);
    if ('scheduler' in window && 'yield' in scheduler) {
      await scheduler.yield();
    }
  }
}
```

**The rAF → setTimeout pattern for INP:** when an interaction handler needs to do meaningful work, wrapping the heavy part in `requestAnimationFrame` followed by a `setTimeout(fn, 0)` guarantees the browser gets a chance to paint an interim frame between the input and the heavy logic — a well-known technique for keeping perceived responsiveness high even when the actual work is non-trivial.

**A rule that generalizes across all four:** never use `requestIdleCallback` (or any idle-time scheduling) to mutate the DOM directly — idle callbacks run at a point in the frame lifecycle where DOM writes can force an extra, unscheduled layout. Use `requestAnimationFrame` for the actual DOM write, and idle time for the computation that decides *what* to write.

**Don't use `setInterval` for animation.** It runs on a separate timer queue with no relationship to the display's actual refresh cycle, which causes double-scheduling and dropped frames compared to a self-scheduling `requestAnimationFrame` loop.

## 4. Web Workers and OffscreenCanvas — actually leaving the main thread

Scheduling APIs change *when* work runs on the main thread; Workers change *which thread* it runs on entirely. This is the only tool in this guide that gives you real parallelism rather than cooperative interleaving.

```js
// main.js
const worker = new Worker('worker.js');
worker.postMessage(largeDataset);
worker.addEventListener('message', (e) => renderResults(e.data));

// worker.js
self.addEventListener('message', (e) => {
  const result = expensiveComputation(e.data);
  self.postMessage(result);
});
```

**Use cases:**
- Parsing/transforming large JSON payloads or CSV data.
- Image or data processing (filters, compression, hashing) too heavy to do inline.
- Any CPU-bound computation whose duration would otherwise register as a long task and hurt INP.

**`OffscreenCanvas`** extends this specifically to `<canvas>` work: it decouples canvas rendering from the DOM so a worker (which has no DOM access at all) can still drive a `<canvas>` element's pixels via `transferControlToOffscreen()`.

```js
// main thread
const htmlCanvas = document.querySelector('canvas');
const offscreen = htmlCanvas.transferControlToOffscreen();
const worker = new Worker('render-worker.js');
worker.postMessage({ canvas: offscreen }, [offscreen]); // transfer, not copy

// render-worker.js
self.onmessage = (evt) => {
  const ctx = evt.data.canvas.getContext('2d');
  function draw(t) {
    ctx.clearRect(0, 0, evt.data.canvas.width, evt.data.canvas.height);
    // ...drawing logic...
    requestAnimationFrame(draw); // requestAnimationFrame works inside workers too
  }
  requestAnimationFrame(draw);
};
```

Because the canvas object is *transferred* (not copied), the main thread loses direct access to it once handed off — this is a deliberate thread-safety guarantee, not a bug. Animation logic running in the worker keeps running smoothly even if the main thread is completely blocked by other JavaScript, which is the whole point: a chart, particle system, or shimmer/loading animation on `OffscreenCanvas` won't visibly stutter even during a heavy main-thread operation elsewhere on the page.

**When *not* to reach for a Worker:**
- For anything that needs synchronous DOM access — workers have none. If you genuinely need to touch the DOM mid-computation, this isn't your tool (or you need to restructure so the DOM write happens back on the main thread after the worker responds).
- For small, cheap computations — spinning up a worker and serializing data across the `postMessage` boundary has its own overhead; it only pays off once the computation itself is meaningfully expensive.
- As a substitute for actually fixing an O(n²) algorithm — moving bad code to a different thread makes it not block the UI, but it's still bad code.

## 5. Event listener hygiene

### Passive listeners

By default, the browser must wait for a `touchstart`/`touchmove`/`wheel` listener to finish running (in case it calls `preventDefault()`) before it can start scrolling — which means every one of those handlers sits directly in the critical path of scroll responsiveness, even if the handler never actually cancels anything.

```js
el.addEventListener('touchstart', onTouchStart, { passive: true });
```

Marking a listener `{ passive: true }` tells the browser upfront that it will never call `preventDefault()`, so scrolling can start immediately without waiting on your handler. Modern browsers now default `wheel`/`mousewheel`/`touchstart`/`touchmove` to passive automatically when attached to `window`, `document`, or `document.body` — but listeners attached to other elements, or in contexts relying on older assumptions, should still be marked explicitly. If you genuinely need to cancel scrolling in a specific handler, you must explicitly pass `{ passive: false }` rather than relying on any default.

### Debounce vs. throttle

Both exist to reduce how often an expensive handler runs in response to high-frequency events (`scroll`, `resize`, `input`, `mousemove`) — but they trade off differently:

- **Debounce** — waits until the event stream goes quiet for N ms, then runs once. Good for "the user stopped typing/resizing" scenarios (search-as-you-type, resize-triggered recalculation) where you only care about the final state.
- **Throttle** — runs at most once every N ms while the stream is active. Good for scenarios needing periodic feedback during the interaction itself (a scroll-position progress bar, a drag handler).

```js
function debounce(fn, wait) {
  let t;
  return (...args) => {
    clearTimeout(t);
    t = setTimeout(() => fn(...args), wait);
  };
}

function throttle(fn, limit) {
  let inFlight = false;
  return (...args) => {
    if (inFlight) return;
    inFlight = true;
    requestAnimationFrame(() => { fn(...args); inFlight = false; });
  };
}
```

Pairing throttle with `requestAnimationFrame` (as above) rather than a raw millisecond interval keeps the update cadence aligned with the browser's own paint cycle instead of picking an arbitrary timer value.

## 6. Native, zero-JS loading primitives — reach for these before writing an observer

Before building a custom `IntersectionObserver`-based lazy-loader, check whether the platform already solves it:

- **`<img loading="lazy">` / `<iframe loading="lazy">`** — native, browser-scheduled deferred loading for below-the-fold images and iframes. No JS required; use this for plain image lazy-loading and reserve `IntersectionObserver` for cases needing extra logic (swapping a different resource, triggering a component mount, tracking analytics).
- **`fetchpriority="high"` / `"low"`** — overrides the browser's default resource-priority heuristic. The highest-leverage single-attribute fix for a slow LCP is usually `fetchpriority="high"` on the actual LCP element (commonly a hero image) — documented real-world gains have ranged from roughly single-digit to ~25–30% LCP improvement depending on the site, entirely from this one attribute, because it corrects cases where the browser's default heuristics under-prioritize an image that's actually critical (e.g., loaded via JS, or positioned after other images in the HTML).
- **`<link rel="preload">`** — fetches a specific resource this page needs, at high priority, without executing/applying it yet. Best for late-discovered critical resources (a CSS background image, a font referenced only inside a stylesheet) that the browser's preload scanner wouldn't otherwise find early. For an LCP `<img>` already in the HTML, `fetchpriority="high"` alone is usually sufficient — adding a redundant `preload` on top rarely adds further benefit and can even cost bandwidth if overused.
- **`<link rel="prefetch">`** — fetches a resource likely needed on the *next* navigation, at the lowest priority, cached for later. Not supported in Safari; treat as a progressive enhancement, not a dependency.
- **`<link rel="preconnect">`** — performs DNS + TCP + TLS setup for a critical cross-origin resource ahead of the actual request. Reserve this for the 3–4 genuinely critical third-party origins on your critical path (a font CDN, your image CDN) — preconnecting to everything wastes the client's limited number of early connections and can *slow down* the resources that matter most.
- **`<link rel="dns-prefetch">`** — the lighter-weight version: resolves DNS only. Appropriate for the long tail of third-party origins (analytics, chat widgets, ad networks) where a full `preconnect` isn't worth the cost.
- **Dynamic `import()`** — the standard code-splitting primitive. Splitting a bundle so route-specific or rarely-used feature code loads only when needed keeps the initial JS payload (and therefore parse/compile/execute cost, and therefore long-task risk on page load) smaller.

**A rule of thumb worth internalizing:** resource hints reorder *what you already have* — they don't fix an oversized hero image, an unoptimized bundle, or a genuinely bloated third-party script. Testing consistently shows that pages with excessive numbers of `preload` hints (roughly ten or more) load *slower* than pages with a handful of well-chosen ones, because every preload competes for the same limited early bandwidth as resources the browser would have discovered and prioritized correctly on its own. Use hints surgically on the two to four resources that are actually on the critical rendering path.

## 7. Decision guide

**"I need to know when an element becomes visible."**
→ `IntersectionObserver` (or native `loading="lazy"` if it's a plain image/iframe with no extra logic needed).

**"I need to know when an element's size changes for any reason, not just window resize."**
→ `ResizeObserver`.

**"I need to react when third-party or dynamically-injected content changes the DOM."**
→ `MutationObserver`, scoped as narrowly as possible.

**"I need to find out where my INP problem is coming from."**
→ `PerformanceObserver` with `entryType: "longtask"` (or `"long-animation-frame"` for more detail) feeding into RUM, then a DevTools Performance trace to zoom into the specific script.

**"I have a visual update that should happen every frame."**
→ `requestAnimationFrame`, self-scheduling — never `setInterval`.

**"I have genuinely non-urgent background work."**
→ `requestIdleCallback` with a `timeout`, or `scheduler.postTask({ priority: 'background' })` where supported.

**"An interaction handler does meaningful work and INP is suffering."**
→ Slice the work with `scheduler.yield()` (feature-detected) or the rAF→setTimeout pattern; move genuinely CPU-heavy portions to a Web Worker.

**"I have expensive canvas/WebGL rendering that must stay smooth regardless of main-thread load."**
→ `OffscreenCanvas` inside a Worker.

**"My scroll/resize/input handler runs too often and is janky."**
→ Debounce (final-state-only use cases) or throttle (needs periodic feedback), and mark touch/wheel listeners `{ passive: true }` unless you specifically need to cancel the default action.

**"My LCP is slow and the hero image loads late."**
→ `fetchpriority="high"` on the element first; add `<link rel="preload">` only if it's discovered late (via CSS or JS) rather than present in the initial HTML.

## 8. Anti-patterns checklist

- ❌ Polling `getBoundingClientRect()` in a `scroll` listener instead of `IntersectionObserver`.
- ❌ Using `MutationObserver` on `style`/`class` attributes to detect size changes — use `ResizeObserver`.
- ❌ Forgetting to `disconnect()`/`unobserve()` observers on unmount, leaking callbacks and their closures.
- ❌ Mutating the DOM inside a `requestIdleCallback` callback.
- ❌ Using `setInterval` for animation loops instead of self-scheduling `requestAnimationFrame`.
- ❌ Putting correctness-critical or user-visible work inside `requestIdleCallback` (it may never run before unload).
- ❌ Non-passive `touchstart`/`wheel` listeners with no actual need to call `preventDefault()`.
- ❌ Spinning up a Web Worker for trivially cheap computation — the `postMessage` serialization overhead can exceed the savings.
- ❌ More than a handful of `<link rel="preload">` hints, or `preconnect` to every third-party origin on the page — both actively compete with the resources that matter for bandwidth.
- ❌ Treating any of these APIs as a substitute for fixing an actually bad algorithm or an oversized bundle — they change *when* and *where* work happens, not how much of it there is.

## 9. Quick-reference cheat sheet

```js
// Lazy-load with a head start
new IntersectionObserver(cb, { rootMargin: '200px', threshold: 0 }).observe(el);

// React to real size changes (not just window resize)
new ResizeObserver((entries) => { /* entries[0].contentBoxSize[0].inlineSize */ }).observe(el);

// Watch injected DOM content
new MutationObserver(cb).observe(el, { childList: true, subtree: true });

// Find your INP culprit
new PerformanceObserver((list) => list.getEntries().forEach(reportLongTask))
  .observe({ type: 'longtask', buffered: true });

// Smooth per-frame visual update
function loop(t) { /* ...update... */ requestAnimationFrame(loop); }
requestAnimationFrame(loop);

// Non-urgent background slice
requestIdleCallback((deadline) => {
  while (deadline.timeRemaining() > 1 && queue.length) doWork(queue.shift());
});

// Offload real computation
const worker = new Worker('worker.js');
worker.postMessage(data);
worker.onmessage = (e) => useResult(e.data);

// Passive scroll-adjacent listener
el.addEventListener('touchstart', handler, { passive: true });
```

```html
<!-- Native lazy image -->
<img src="photo.jpg" loading="lazy" alt="…" />

<!-- LCP hero image -->
<img src="hero.webp" fetchpriority="high" alt="…" />

<!-- Late-discovered critical resource -->
<link rel="preload" href="/fonts/body.woff2" as="font" crossorigin />

<!-- Critical third-party origin -->
<link rel="preconnect" href="https://cdn.example.com" />
```
