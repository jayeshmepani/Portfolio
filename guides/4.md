# CSS Rendering Performance: content-visibility, will-change, contain, and Friends

A practical, in-depth reference for the CSS properties that exist purely to make browsers render less, render lazier, and render smarter. Covers what each one actually does under the hood, exactly where to use it, where *not* to, and how they interact.

---

## 1. The rendering pipeline, briefly

Every optimization property in this guide is a lever on one or more stages of the browser's rendering pipeline:

1. **Style** — compute which CSS rules apply to which elements.
2. **Layout (reflow)** — compute geometry: size and position of every box.
3. **Paint** — turn each box into pixels (fills, borders, text, shadows) as ordered paint records.
4. **Composite** — combine painted layers on the GPU, applying transforms/opacity cheaply without repainting.

Anything that forces layout or paint on a large subtree — resizing a container, injecting content, even scrolling past thousands of hidden nodes — is expensive because it forces steps 2 and 3 to run again. Containment and `content-visibility` attack steps 2–3 directly (by letting the browser skip them for subtrees). `will-change` attacks step 4 (by promoting elements to their own composited layer ahead of time). Everything else in this guide is a variation on those two ideas.

## 2. `contain` — telling the browser a subtree is independent

### What it does

`contain` declares that an element's internals are isolated from the rest of the page along one or more axes, so the browser doesn't have to walk back out to the document root when recalculating that axis. The property is a space-separated list drawn from size, layout, style, and paint, or one of two shorthand values.

**Values:**

| Value | What it isolates |
|---|---|
| `size` (or `inline-size`) | The element's size can be computed without looking at its children — it lays out as if empty. |
| `layout` | Internal layout is fully isolated: floats, margins, and absolutely/fixed-positioned descendants inside don't affect (or get affected by) anything outside. |
| `style` | Counters and quotes are scoped to the element and its contents rather than the whole document. |
| `paint` | Descendants can't paint outside the element's box — if the box is offscreen, nothing inside it needs to be painted either. |
| `content` | Shorthand for `layout paint style` — a safe, widely-applicable default since it skips size containment. |
| `strict` | Shorthand for all four (`size layout paint style`) — the strongest containment, but riskier since size containment can collapse a box to zero size if you don't give it explicit dimensions. |

A useful side effect: applying layout, paint, content, or strict containment creates a new containing block for absolutely/fixed-positioned descendants — handy, but also a gotcha if you were relying on a `position: fixed` child escaping to the viewport.

### When to use it

- **Independent repeating sections** — cards, list items, comment threads, article previews — where you know styling/layout changes inside one item should never ripple out to siblings.
- **Widget boundaries** — a chat widget, a map embed, a rich-text editor pane: anything self-contained that gets frequent internal DOM churn.
- Any large sibling group where the browser currently has to do more layout/paint work than necessary because it *can't prove* independence on its own.

### How to use it

```css
.card {
  contain: content; /* layout + paint + style, no size */
}

.chat-widget {
  contain: strict;
  width: 360px;
  height: 480px; /* required: strict includes size containment */
}
```

Start with `content` for most cases. Reach for `strict`/`size` only when you can give the element explicit, reliable dimensions — otherwise a zero-height collapse is a real risk.

### When *not* to use it

- On elements whose height must be derived from their content and that content is otherwise unpredictable (with `size`/`strict`), unless paired with `contain-intrinsic-size`.
- On elements that intentionally need to overflow visibly (tooltips, dropdown menus, box-shadows that bleed outside the box) — `paint`/`strict`/`content` clip descendants to the border box.
- Sprinkled indiscriminately across every div "just in case." Containment isn't free to evaluate either; apply it where there's a real, currently-unoptimized subtree boundary.
- As a substitute for fixing an actually bad layout (excessive nesting, huge unvirtualized lists) — it reduces the *cost* of recalculation, not the amount of DOM.

## 3. `content-visibility` — skipping rendering work entirely

### What it does

content-visibility controls whether an element renders its contents at all, forcing a strong set of containments so the user agent can skip layout and paint work for that subtree until it's actually needed. This is the single biggest lever in this guide for long pages — it's how browsers themselves optimize things like `<details>` and how `hidden=until-found` is implemented under the hood.

**Values:**

- `visible` — no effect; content renders normally.
- `hidden` — contents are skipped and unreachable by find-in-page, tab order, or any selection/focus interaction. Functionally similar to `display: none` for rendering cost, but the element still keeps its box (unlike `display: none`) and DOM state (form values, scroll position) is preserved.
- `auto` — the browser applies containment and skips rendering **only while the element is off-screen** (not intersecting the viewport, and not focused/selected), and renders it normally the instant it's needed. This is the one you'll use most.

### When to use `auto`

- **Long, mostly-offscreen pages**: long articles, changelogs, infinite-scroll feeds, huge tables, chat histories — anywhere there's a lot of DOM below/above the fold that isn't being interacted with right now.
- As a lighter-weight alternative to full list virtualization (react-window, etc.) when you don't want to manage windowing logic yourself, or want it to gracefully degrade (real DOM stays in place, so browser find-in-page, Ctrl+F, and SEO crawling of the full page still generally work with `auto`, unlike virtualization that unmounts nodes).
- Wrapping each "section" of a page that's logically chunky and independent (each blog post preview, each accordion panel, each table's `<tbody>`… though `<tbody>` containment support varies).

### When to use `hidden`

- Content that's fully hidden and not meant to be discoverable — think a step of a multi-step form that hasn't been reached yet, or a tab panel that's not the active tab, where you want the state/DOM preserved but zero rendering cost while inactive, and you explicitly don't want it in find-in-page or accessibility.
- Prefer the HTML `hidden="until-found"` attribute (see §6) instead when you *do* want it to remain findable and accessible — that's the standards-track replacement for the old `content-visibility: hidden-matchable` idea.

### How to use it — the essential pairing with `contain-intrinsic-size`

This is the part people get wrong. Skipping rendering means the browser doesn't know how tall the skipped content actually is, so scrolling through many `content-visibility: auto` sections without any hint can cause visible layout shift and scrollbar jumpiness as each one snaps to its real height when it enters the viewport.

```css
.article-section {
  content-visibility: auto;
  contain-intrinsic-size: auto 500px; /* placeholder until first real render */
}
```

- The plain length form (`contain-intrinsic-size: 500px`) always uses that as the placeholder size, every time the element is off-screen — even after it's been rendered once.
- The `auto <length>` form lets the browser remember the last real rendered size and reuse it as the placeholder the next time the element goes off-screen, falling back to your specified length only the first time, before anything has been measured. This is almost always what you want — set it as your default.
- You can size each axis independently with `contain-intrinsic-block-size` / `contain-intrinsic-inline-size` when width and height need different placeholder values.
- As of the `content-visibility: auto` spec update, browsers now apply `contain-intrinsic-size: auto` implicitly to `auto` elements in many cases — but explicitly setting a placeholder value is still the safer, more portable choice, and it's the only way to control the *first-render* placeholder height.

**Estimate the placeholder as closely as you reasonably can.** A wildly wrong guess (e.g., guessing 200px for a 2000px section) causes a bigger jump when the real size resolves than not guessing at all in some layouts — but leaving it at `0` (the default when `contain-intrinsic-size` isn't set) is worse, since the browser then assumes a height of 0 for the whole offscreen section, which can produce a confusing, jumpy scrollbar.

### Watch out for: accessibility and find-in-page

- `auto` is designed to keep content in the accessibility tree and findable — but implementation quality varies by engine, and Safari has had bugs where skipped `content-visibility: auto` content wasn't reliably findable via in-page search; check current browser behavior before relying on it for critical findability.
- `hidden` deliberately removes content from accessibility tree, tab order, and find-in-page. Don't reach for `hidden` on content a screen-reader or keyboard user should ever be able to reach — use `hidden="until-found"` or a proper show/hide toggle instead.
- Animating `content-visibility` for reveal transitions needs `transition-behavior: allow-discrete` (it's a discrete, not interpolable, property) plus `@starting-style` — a plain `transition: content-visibility 300ms` on its own won't animate anything.

### The `contentvisibilityautostatechange` event

This event fires on any element with `content-visibility: auto` whenever its rendering starts or stops being skipped — useful for pausing/resuming expensive JS work (canvas drawing, video, WebGL, polling) tied to an element's actual visibility, without wiring up a separate `IntersectionObserver`.

```js
el.addEventListener('contentvisibilityautostatechange', (e) => {
  if (e.skipped) pauseCanvasLoop();
  else resumeCanvasLoop();
});
```

### When *not* to use `content-visibility`

- On content that's visible on initial load, above the fold, or likely to be needed immediately — it adds containment overhead for no skip benefit and can occasionally make things *slower* (see the LogRocket benchmark note below) if the intrinsic-size hint is missing or wrong.
- On very small, cheap-to-render elements — the containment bookkeeping isn't free, and the payoff is proportional to how much rendering work you're actually able to skip.
- As a replacement for `display: none` on content that should truly be gone from the page (e.g., a closed modal that shouldn't occupy any box or be reachable at all) — `content-visibility: hidden` still participates in normal flow the way `display: none` doesn't (actually it doesn't take up layout space either since size containment collapses it, but subtle differences remain — test rather than assume equivalence).
- Where you need guaranteed layout stability and can't tolerate any shift risk, and you haven't benchmarked with a realistic `contain-intrinsic-size` guess.

## 4. `will-change` — pre-warming the compositor

### What it does

will-change is a rendering hint telling the browser which properties on an element are expected to change soon, so the browser can set up optimizations (like promoting the element to its own compositor layer) ahead of time rather than scrambling when the change actually starts.

```css
will-change: transform;
will-change: opacity, transform; /* comma-separated list */
will-change: scroll-position;
will-change: contents;
```

### The core rule: use it as a scalpel, applied and removed via script, not a permanent stylesheet declaration

will-change is intended to be used as a last resort to deal with an existing, measured performance problem — not preemptively, "just in case." If your animation is already smooth, there's no need to add it.

The reason it's dangerous as a blanket stylesheet rule: the browser's normal behavior is to drop optimizations as soon as possible and return to a normal render state, but a `will-change` declaration sitting permanently in a stylesheet tells the browser the element is *always* a moment away from changing, so the browser holds the optimization — and its resource cost — far longer than it would otherwise. Some of the stronger optimizations tied to `will-change` are resource-intensive, and overusing the property can slow the page down instead of speeding it up.

### How to use it correctly

Toggle it on right before the change and off right after — via JavaScript, not a static rule:

```js
const el = document.querySelector('.panel');

el.addEventListener('mouseenter', () => {
  el.style.willChange = 'transform';
});

el.addEventListener('transitionend', () => {
  el.style.willChange = 'auto'; // release the hint promptly
});
```

For animations that are about to run (not hover-triggered), set it a frame or two before the animation starts and clear it once it finishes — enough lead time for the browser to promote the layer, but not so long that the hint sits idle.

### When to use it

- You've profiled a specific animation/transition in DevTools and confirmed it's janky (dropped frames, paint/composite spikes) — not before.
- Complex, expensive-to-repaint effects that are about to animate: `filter`, `clip-path`, `box-shadow`, `backdrop-filter` on elements that also move or fade.
- A fixed/sticky element whose repaint is visibly laggy during scroll on lower-end devices, where you've confirmed layer promotion actually helps (see §5's caveat about non-transform ancestors below sticky elements).

### When *not* to use it

- As blanket "performance insurance" scattered across a stylesheet with no evidence of a problem — this is explicitly the anti-pattern MDN and every serious source on this property warns against.
- On more than a handful of elements simultaneously. There's deliberately no `all` value for `will-change`, precisely because applying it broadly harms performance — each promoted layer costs GPU memory and adds compositing overhead.
- Left on indefinitely on elements that only animate occasionally (a hover card, a modal). Leaving the hint permanently active for something that changes rarely wastes memory the rest of the time for no benefit.
- On elements where the actual bottleneck is layout thrashing (properties like `width`, `top`, `margin` that trigger reflow) rather than paint/composite cost — `will-change` doesn't fix layout-triggering property changes; the fix there is to animate `transform`/`opacity` instead of layout-affecting properties in the first place.

## 5. GPU layers, compositing, and the `translateZ(0)` hack — context you need

You'll still see `transform: translateZ(0)` (or `translate3d(0,0,0)`) in older code and some current workarounds. Know what it is and why `will-change` mostly superseded it.

- Both techniques do fundamentally the same underlying thing: force the browser to promote an element onto its own compositor layer so that transform/opacity changes on it can be handled by the GPU without a full repaint.
- `translateZ(0)` is a **static, one-time** promotion — it doesn't carry `will-change`'s "please undo this later" semantics, so it's cheaper to leave in place permanently on an element that genuinely benefits from staying on its own layer (e.g., a `position: sticky` header with a known WebKit repaint bug), but you lose the browser's ability to reclaim the layer memory when it isn't needed.
- `will-change` is more honest about intent and (when toggled correctly) more memory-efficient, but if left as a permanent static rule it has exactly the downside described in §4.
- Neither is free. Promoting an element to its own layer triggers the same expensive setup either way — painting the layer to a separate surface, preparing layer data, and uploading it to the GPU — and in some cases this initial promotion is itself slower than an incremental repaint would have been. Applying either hack indiscriminately across many elements offloads too much to the GPU, and on lower-end/mobile devices with limited VRAM this causes noticeable lag rather than the intended speedup.
- **Rule of thumb for 2026:** prefer animating `transform`/`opacity` via CSS transitions/animations (which auto-promote a layer for the animation's duration on modern engines) over manually forcing a layer. Reach for an explicit `will-change` (toggled) or a static `translateZ(0)` only when you've confirmed via the DevTools Layers/Rendering panel that a specific element genuinely needs a standing layer — e.g., a sticky/fixed element with a proven repaint bug on a specific engine.
- `backface-visibility: hidden` is sometimes paired with these hacks as an extra nudge for layer promotion in older WebKit, but it's no longer necessary in current engines for the primary use case (3D transforms) — don't cargo-cult it onto 2D layouts.
- `isolation: isolate` is a different, narrower tool: it creates a new stacking context (useful for scoping `mix-blend-mode`/z-index behavior) without necessarily implying GPU layer promotion or rendering-cost containment — don't confuse it with `contain` or `will-change`.

## 6. `hidden="until-found"` — the accessible way to hide-and-defer

For collapsible content you want hidden by default but still discoverable, this HTML attribute (not a CSS property, but built directly on `content-visibility`) is usually the right tool instead of manually toggling `content-visibility: hidden`/`auto`.

```html
<div hidden="until-found">
  This text is invisible and unrendered, but Ctrl+F search or a
  same-page anchor link will reveal it automatically.
</div>
```

```js
el.addEventListener('beforematch', () => {
  // fires right before the browser reveals the element via find-in-page
  // or fragment navigation — sync any related UI state here
});
```

- hidden="until-found" applies content-visibility: hidden under the hood instead of display: none, which is exactly what allows the browser to search the otherwise-hidden text.
- Unlike a plain `hidden` attribute, content revealed this way is accessible to search engines too — Google Search can even deep-link directly to the revealed fragment.
- Once text is revealed via find-in-page, it stays revealed even after the search is closed or a new search starts — factor that into any UI state you're syncing via `beforematch`.
- **Browser support caveat (check before relying on it):** support has been rolling out unevenly — Chrome had it earliest, Firefox added it later, and Safari's position has lagged, so verify current support before treating it as universally available; provide a JS fallback that expands content for engines that don't fire `beforematch` at all.

## 7. Other properties worth knowing for rendering-cost control

| Property | What it helps with | Notes |
|---|---|---|
| `contain-intrinsic-width` / `-height` / `-block-size` / `-inline-size` | Per-axis placeholder sizing, paired with `size`/`content-visibility` containment | Use when width and height need genuinely different placeholder logic instead of the shorthand. |
| `content-visibility: hidden` vs `display: none` vs `visibility: hidden` | Three different "make it disappear" tools with different tradeoffs | `display: none` removes from layout and accessibility tree entirely, no DOM/state cost benefit. `visibility: hidden` keeps layout space, still costs paint of descendants in some cases, but preserves clickability of ancestors' other content. `content-visibility: hidden` keeps DOM state and skips rendering cost, doesn't reserve layout space (size containment collapses it), removes from accessibility tree/find-in-page. Pick based on which of "keeps layout space," "keeps accessibility," and "keeps rendering cost" you actually need. |
| `image-rendering` | Avoids expensive resampling for pixel-art/large raster scaling | `pixelated` / `crisp-edges` skip smoothing interpolation cost; not a layout/paint containment tool but a genuine paint-cost lever. |
| `filter` / `backdrop-filter` | Both are notoriously expensive to paint and repaint, especially at large element sizes or when animated | Combine with `will-change` (toggled) only when genuinely animating them, and prefer smaller/blurred elements over full-viewport ones where possible. |
| `@layer` (cascade layers) | Not a rendering-cost tool — a style-authoring/specificity tool | Mentioned only to avoid confusion with `contain: style`, which is the actual rendering isolation mechanism for counters/quotes. |
| `aspect-ratio` | Reserves layout space for media without JS, reducing layout shift | Complementary to `contain-intrinsic-size` for different scenarios (known-ratio media vs. unknown-height text sections). |

## 8. Decision guide — which tool, when

**"I have a long page with a lot of offscreen content (feed, article, table, changelog)."**
→ `content-visibility: auto` + `contain-intrinsic-size: auto <estimate>` on each repeating section.

**"I have independent, repeating components (cards, list items) and want to stop layout/paint changes in one from rippling to siblings."**
→ `contain: content` (or `contain: layout paint` if you specifically don't need style scoping).

**"I have a fixed-size, self-contained widget with heavy internal DOM churn."**
→ `contain: strict` with explicit width/height set.

**"An animation/transition is measurably janky in DevTools."**
→ Toggle `will-change` via JS right before the change, clear it right after. Prefer animating `transform`/`opacity` over layout-affecting properties in the first place.

**"I want to hide content but keep it discoverable via search/accessibility."**
→ `hidden="until-found"` with a `beforematch` listener, not manual `content-visibility: hidden` toggling.

**"I want to hide content completely — not discoverable, not accessible, state preserved."**
→ `content-visibility: hidden` (inactive tab panels, unreached form steps) or `display: none` if you don't need DOM state preserved and don't mind removing layout box entirely.

**"A sticky/fixed element has a specific, confirmed repaint bug on one engine."**
→ A static `transform: translateZ(0)` (or `will-change: transform` left in place) directly on that element, after confirming via DevTools that it's actually needed — not preemptively.

**"My page just feels generally slow and I don't have a specific diagnosis yet."**
→ Don't reach for any of these first. Profile with DevTools Performance panel, find the actual bottleneck (layout thrashing? paint cost? too many composited layers already? just too much DOM?), then apply the specific tool from this guide that matches that bottleneck.

## 9. Measuring, not guessing

- **Chrome/Edge DevTools → Performance panel**: record an interaction, look for long "Layout" (purple) or "Paint" (green) blocks, and for repeated forced-reflow warnings.
- **Layers panel**: shows every composited layer and its memory cost — the direct way to see if `will-change`/`translateZ(0)` usage has gotten out of hand.
- **Rendering tab → "Layer borders" / "Paint flashing"**: visualizes exactly which regions repaint on each frame, and which elements are on their own layer.
- Use `content-visibility: auto` primarily for off-screen content, but test the actual performance impact rather than assuming — pair it with `contain-intrinsic-size` and apply it selectively so you don't delay rendering of content that actually matters, and verify across the specific browsers/devices you target. A documented real-world test found that adding `content-visibility: auto` alone to a component *without* a matching `contain-intrinsic-size` hint made rendering measurably worse, and only got faster once an accurate placeholder size was supplied — the pairing isn't optional polish, it's load-bearing.
- `contentvisibilityautostatechange` (§3) is your hook for tying expensive JS work to actual visibility state instead of guessing with scroll listeners.

## 10. Anti-patterns checklist

- ❌ `will-change` left permanently in a stylesheet rule instead of toggled by script.
- ❌ `will-change: all` or `will-change` applied to dozens of elements at once (and note `all` isn't even a valid value for exactly this reason).
- ❌ `content-visibility: auto` with no `contain-intrinsic-size` on content with meaningfully large or unpredictable height.
- ❌ `contain: strict`/`size` on an element with no explicit dimensions, risking a zero-height collapse.
- ❌ `content-visibility: hidden` used for content that should stay accessible/findable — use `hidden="until-found"` instead.
- ❌ `translateZ(0)`/`will-change` sprayed across a page "for smoothness" with no profiling to justify it.
- ❌ Treating `contain`/`content-visibility` as a fix for a fundamentally bloated DOM — they reduce recalculation cost, not element count; real virtualization or pagination still wins for genuinely massive lists.
- ❌ Assuming `content-visibility: auto` behaves identically across engines for find-in-page/accessibility — verify current behavior in your target browsers rather than assuming parity.

## 11. Quick-reference cheat sheet

```css
/* Long page, offscreen sections */
.section {
  content-visibility: auto;
  contain-intrinsic-size: auto 600px; /* your best real estimate */
}

/* Independent repeating component, unknown height */
.card {
  contain: content;
}

/* Fixed-size self-contained widget */
.widget {
  contain: strict;
  width: 320px;
  height: 240px;
}

/* Confirmed-janky animation — toggle in JS, don't leave static */
/* el.style.willChange = 'transform' right before; 'auto' right after */

/* Accessible hide-until-searched content */
<div hidden="until-found"> ... </div>
```
